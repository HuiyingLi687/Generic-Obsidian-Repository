# 数据库迁移规范

汉考宝的改表流程。目标只有一个：**让「代码上线」和「数据库变更」成为同一个动作，消灭漏迁。**

## 一、目标状态

```
代码仓库                                    执行时机
db/migration/
├── V1__baseline.sql                        首次接入时标记为已执行，不实际运行
├── V2__product_i18n.sql                    部署前自动执行
└── V3__exam_deduction.sql                  部署前自动执行
         │
         ▼
   Flyway 容器（docker compose 的一个 init 服务）
         │  读 flyway_schema_history，只跑没跑过的
         ▼
   业务服务启动（依赖 migrate 成功退出）
```

关键点：**迁移失败 → 业务容器不启动**。这样「忘记迁移」不再是可能的失误，而是服务起不来，立刻可见。

## 二、目录与命名

| 项 | 规定 |
|---|---|
| 目录 | 项目根 `db/migration/`（不是各模块，因为共库） |
| 前缀 | `V` = 版本化脚本，`T` = 模板（不执行），`R` = 可重复执行（慎用） |
| 命名 | `V{序号}__{蛇形描述}.sql`，序号从 1 递增，**不用小数** |
| 示例 | `V2__add_product_name_localizations.sql`、`V7__create_csca_wrong_book.sql` |
| 编码 | UTF-8，无 BOM |
| 分隔符 | 版本号与描述之间是**两个下划线** |

**为什么不用 `V1.1`**：小数版本号排序容易出错（`V1.10` 会排在 `V1.9` 前面），且多人开分支时极易撞号。递增整数 + 提交前先 `git pull` 确认已占用的最大号，就够用。

## 三、脚本头部注释（四行模板）

每个 `V*.sql` 开头必须写这四行。**这不是形式主义**——第 3 行「需回填」是漏了就会出事的项。

```sql
-- 变更：product / product_sku 增加 name_en、name_vi 字段
-- 影响：manage-service（录入）、pay-service（展示）
-- 回填：是，存量商品先用 name 填充，避免英文站空白
-- 回滚：DROP COLUMN 即可，但会丢失已录入译文
```

四条分别回答：改了什么、影响谁、要不要动存量数据、出错怎么退。

**第 3 行为什么最重要**：`ALTER TABLE ADD COLUMN` 只是让列存在。存量行的值是 `NULL`，功能代码上线后读到空值，页面直接空白——但此时「迁移已执行」是成立的，查历史表看不出问题。这种情况比漏迁更难排查。

## 四、三条纪律

**1. 已上线的脚本永不修改**

Flyway 记录每个文件的校验和，改一个字 `validate` 就失败，应用起不来。写错了只能新增一条 `V8__fix_v7_xxx.sql` 去修正。

这条纪律的副作用是好的：它强迫你把「修正」当成新变更记录，而不是偷偷改历史。

**2. 结构变更必须版本化，不允许手工连库执行**

包括 `ALTER TABLE`、`CREATE TABLE`、加索引、改字符集。一旦开了「这次急，先手工跑」的口子，下次就会漏。

**3. 生产执行前必须备份**

```bash
mysqldump -h 43.99.57.11 -u root -p --single-transaction --no-data xuexitest > backup_schema_$(date +%Y%m%d%H%M).sql
```

`--no-data` 只备结构，几秒完成。数据备份另存，见第七节。

## 五、新功能开发流程

以「新增错题本功能」为例：

```
1. 设计阶段   确定表结构 → 查 [[01表归属矩阵]] 确认影响哪些服务
              → 查 [[02变更台账]] 看有没有改过相关表

2. 编码阶段   写 db/migration/V5__create_wrong_book.sql（含四行注释）
              写 Java 实体和 Mapper（同一个 commit）

3. 提交阶段   SQL 与代码在同一个 commit，commit message 写清楚
              git add db/migration/ src/ → 一次提交

4. 部署阶段   docker compose up → Flyway 自动执行 → 日志确认
              "Successfully applied 1 migration"

5. 记录阶段   在 [[02变更台账]] 顶部加一行
```

第 2 步「同一个 commit」是核心。分开提交就会出现「代码上了、SQL 忘了」——正是现在的问题。

## 六、上线检查（三条，30 秒）

```
□ 迁移脚本已提交（git status 无未跟踪的 .sql）
□ 生产库已备份（或有当日备份）
□ 启动日志出现 Successfully applied N migrations
```

第三条是关键：不是「看到容器起来了」，而是**看到这一行日志**。N=0 也正常，说明没有新迁移，但要确认这一行存在，才能证明 Flyway 真的跑了。

## 七、历史脚本处置

`tmp/` 下 141 个文件、约 6MB，**当前完全未纳入 git**。分批处理：

| 类别 | 数量 | 处置 |
|---|---|---|
| `_rollback_*` | 128 | 全部入库到 `docs/sql-history/rollback/`，按年月分目录 |
| `fill_*` / `_seed_*` | 20 | 入库到 `docs/sql-history/data/` |
| `_backup_*` 数据快照 | 12 | **先自查是否含用户数据**，含敏感信息的转储不入库 |

**为什么不转成 `V*.sql`**：这些脚本已经在生产执行过。转成版本化脚本后，Flyway 会尝试重新执行，`ADD COLUMN` 直接报 `Duplicate column name`。

正确做法是 `V1__baseline.sql` 用生产库当前结构快照生成，历史脚本作为**存档**保留，不进 `db/migration/`。

入库前在 `docs/sql-history/README.md` 写一张对照表：哪个脚本对应哪次提交、在哪个环境执行过。这张表比脚本本身更重要，因为脚本看不出执行环境。

## 八、环境一致性

同一套结构跑在四个地址上：

| 环境 | 地址 | 迁移方式 |
|---|---|---|
| PROD | `43.99.57.11:3306` | 部署时自动或手工 `flyway migrate` |
| TEST | `8.138.185.11:3306` | 同上 |
| TEST 备用 | `124.227.194.80:184` | 同上，容易遗忘 |
| 本地 | `localhost:3306` | `docker compose up` 时自动 |

**TEST 备用那个地址最容易漏**，只在 `system-service/application-test.yml` 里出现一次。建议合并环境或明确废弃，否则每次迁移都要记三个地方。

## 九、如果暂时不接 Flyway

不接也能解决 80% 的问题，代价是要靠人执行：

1. 建 `db/migration/` 目录，新变更一律放这里，命名 `V{序号}__{描述}.sql`
2. `tmp/` 全部入库，至少保住那 128 个回滚脚本
3. 每次上线前执行 `ls db/migration/ | sort -V`，对照生产库手工核对
4. 执行后在 [[00变更台账/变更台账模板]] 记一行，注明「手动执行」

**这条路的唯一缺口**：没有强制点，第 3 步仍然可能被跳过。如果近期上线频率高，建议还是接 Flyway。
