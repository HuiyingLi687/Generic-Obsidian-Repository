# 变更台账

数据库结构变更的时间线。**回答一个问题：这个字段为什么在这儿。**

## 一、台账记什么，不记什么

| 内容 | 记不记 | 为什么 |
|---|---|---|
| 改了什么表、哪些字段 | ✅ 记 | SQL 里也有，但这里能一眼看全时间线 |
| 为什么改、对应哪个功能 | ✅ **重点记** | commit message 通常只写「翻译相关文案」，看不出加了什么 |
| 影响哪些服务 | ✅ 记 | 共库架构下这是最需要提前知道的 |
| 有没有数据回填 | ✅ **重点记** | 最容易漏，漏了功能就是坏的 |
| SQL 正文 | ❌ 不记 | 在 `db/migration/V*.sql` 里，抄过来必然不同步 |
| 线上执行状态 | ❌ 不记 | 一条 SQL 查 `flyway_schema_history`，手工维护必然过期 |

**判断标准**：这段信息在 git 里能不能查到？查不到的才值得写在这儿。

## 四、怎么查线上到底执行了什么

接入 Flyway 后，唯一事实来源是历史表，**不要凭记忆**：

```sql
-- 在生产库执行：所有已应用的迁移
SELECT version, description, success, installed_on, execution_time
FROM flyway_schema_history
ORDER BY installed_rank DESC;

-- 只看失败的（有输出就说明有问题）
SELECT version, description, installed_on
FROM flyway_schema_history
WHERE success = 0;
```

接入 Flyway 之前，这个问题**没有答案**——只能翻 `tmp/` 猜。这正是要接入它的主要原因。

## 五、维护规则

1. **一次变更一行**，写在表格顶部（倒序），不要按模块分表
2. **不留空列**：不确定就写「待确认」，不要留空，否则看起来像已完成
3. **版本列跟 Flyway 对齐**：`V1`、`V2`，历史遗留写 `—`
4. **不写 SQL 正文**，只写表名和字段名
5. 一次上线涉及多个变更时，可以合并为一行，但「影响服务」要列全
