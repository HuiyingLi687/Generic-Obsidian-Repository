## 0. 通用约定

### 0.1 返回包装

与写字课一致：统一 `com.hsktreasure.common.result.Result<T>`，**HTTP 状态码恒为 200**，业务结果看 `code`。

```json
{ "code": 200, "message": "操作成功", "data": { } }
```

`data` 为 `null` 时字段仍保留（不省略）。异常统一由 `GlobalExceptionHandler` 兜住。

### 0.2 鉴权与客户端类型

**拼音课的全部接口都免登录。** 这是与写字课最大的一处结构差异：

| | 写字课 | 拼音课 |
|---|---|---|
| 内容类接口 | 免登录 | 免登录 |
| 进度类接口 | **必须登录**（`/course/progress/**`、`/course/writing/groups`） | **不存在** |
| 需鉴权的端点数 | 3 | **0** |

原因：拼音课**不做学习进度**（2026-09-17 产品确认）——纯学习/浏览，没有任何与用户相关的数据。

- 因此拼音课**不调用** `requireAuthenticatedAppUserId(...)`，也不读 `X-Client-Type`
- `userId` 不参与任何拼音课查询，**没有"刷别人进度"的攻击面**
- 唯一带鉴权语义的是共享接口 `/course/catalog`，但那也是免登录的

> **对前端的影响**：拼音课整条链路可以在**未登录状态**下完整跑通；写字课的练习页则必须先登录。这个差异要在客户端路由守卫里体现出来。

### 0.3 多语言

沿用同一手法：请求头 `Accept-Language` → 服务端取完译文后**只回一个字符串**（工具类 `com.hsktreasure.course.common.support.LanguageSupport`，在 `course-service` 内、两课共用。⚠️ 它**不在** `common` 模块里 —— 本文其余位置的 `common/xxx` 均指 `course-service` 的 `com/hsktreasure/course/common/`，见 §4.2 的类清单）。

| 头值 | 行为 |
|---|---|
| `zh` / 缺省 | 返回中文原文 |
| `en` | 返回 `*_en` 列，**为空则回退中文** |
| `vi` | 返回 `*_vi` 列，**为空则回退中文** |
| 其他（`ja`、`*` 等） | 一律回落 `zh` |

**但与写字课有一处关键差异：拼音课能翻译的字段只有一个 `description`。**

| 字段 | 是否走多语言 | 原因 |
|---|---|---|
| `description` | ✅ 走 `_en` / `_vi` 回退 | 唯一一条自由文本说明（轻声 / 变调的讲解） |
| `letter`（`b` / `ü` / `ā`） | ❌ **绝不翻译** | 它就是要学的内容本体 |
| `toneValue`（`55` / `214`） | ❌ | 语言学固定值 |
| `exampleText`（`妈 mā`） | ❌ **绝不翻译** | 「汉字 + 拼音」本身就是内容，英文/越南语都只能原样展示 |
| tab 标题（声母/韵母/声调） | ❌ 不进接口 | 走**前端 i18n 字典**（`categoryCode` 是键） |
| 韵母分组标题（单韵母/双韵母·鼻韵母/复韵母） | ❌ 不进接口 | 走前端 i18n 字典（`nodeType` 是键） |
| 调序红标签（一声…四声） | ❌ 不进接口 | 走前端 i18n 字典（`toneName` 是键） |
| 调型名（阴平/阳平/上声/去声） | ❌ 不进接口 | 走前端 i18n 字典（**`toneValue` 是键**，见 §4.1） |

> ⚠️ **`exampleText` 不翻译这一条很容易被误做**。它长得像文案，实际是教学内容——「妈 mā」翻成英文就废了。管理端录入时也不应提供 `example_text_en` / `example_text_vi`（表里也确实没有这两列，✅ 一致）。

### 0.4 ID 序列化（2026-09-20 定稿：**不做全局 Long → String**）

与写字课**同一结论**，此处只给要点；完整论证（含逐项位数核对、边界条件与「将来怎么撤回」）见 `写字课-接口设计文档.md` §0.4：

- 项目主键是雪花 ID（19 位 Long），**理论上**超过 JS `Number.MAX_SAFE_INTEGER` —— 但**本服务响应里没有这个量级的数**：拼音课下发的 `id` 全是 `301`–`314`（3 位）、`courseId` 是 `900`（3 位）
- 唯一带雪花的是 `userId`，而拼音课**全部接口免登录**，响应里根本没有它
- 所以**既不配全局序列化器，也不挂字段级注解**；曾短暂存在的 `course-service/config/JacksonConfig.java` 及其配套类**已删除**，别照旧版文档加回来
- **因此本文所有 JSON 示例中的 id 一律写成数字**（`"id": 301`）。请求参数传字符串或数字都能被 Spring 转回 `Long`，**响应一律是数字**

> 拼音课的 ID 字段本就比写字课少（只有 `id` 与 `courseId`，没有 `exampleCharIds` / `itemId` 这类 id 数组），现在结论也更简单：**都不字符串化**。

### 0.5 错误码

复用 `ErrorCode`，拼音课不需要新增：

| code | 含义 | 触发场景 |
|---|---|---|
| `200` | 成功 | — |
| `400` | 参数错误 | `category` 不在 4 值枚举内；`id` 不是数字 |
| `500` | 服务端错误 | 未预期异常 |
| `404` | 内容不存在 | `GET /course/pinyin/items/{id}` 查无此条（或用业务码，见 §4.3 第 10 条） |

**注意**：拼音课**不会出现** `401` / `403` / `409` —— 没有需登录的接口，也没有写库（进度）操作。这三个码在写字课文档里存在，本文不适用。

### 0.6 枚举与版本号

**`course.data_version`** 是离线缓存的唯一判据（方案 §2.0.4）：

- 拼音课的 `data_version` 取自 `course` 表 `code='PINYIN'` 那一行（**当前值 `1789613781244`**）
- 它覆盖 `course_pinyin_item` + 本课 `course_intro_section`
- 管理端**每次保存拼音内容**都要把它改成当前毫秒时间戳，只增不减
- 客户端把它存进 IndexedDB，往下拉数据前先比一次

> **2026-09-17 修订**：本版在首页版本号口径上有三处变化，若你手上是旧版请对照 ——
> ① `course_home_entry` **新增 `data_version` 列**（原先用它的 `updated_time` 参与聚合），首页版本号的两个来源现在是**同一种列**，不再有时间戳量纲耦合；
> ② `/course/catalog` 与 `/course/catalog/version` 的聚合表达式**必须带 `COALESCE(…, 0)`**（见 [3.1.1](#311-get-coursecatalog) 第 4 条）——`course_home_entry` 只有一行，软删即「无行」，`MAX()` 返回 `NULL` 会被 `GREATEST` 传染成整体 `NULL`；
> ③ 客户端比对语义明确为**「不相等」而非「大于」**（见 [3.1.2](#312-get-coursecatalogversion)）。
> ⚠️ 以上只影响**首页**版本号（`/course/catalog*`）。本文其余接口用的是拼音课自己的 `course(900).data_version`，口径不变。
>
> **2026-09-18**：3.1.1 的「业务逻辑」压成 5 条短句（SQL 与长解释移出），**新增「数据流向」小节**（放在「涉及表」之后）：查库 → 加工 → 组装 三步流程 + 响应字段映射对照 + 版本号 SQL。
>
> **2026-09-20 修订**：本次改动**不涉及拼音课的任何接口** —— 写字课 `course_writing_rule.group_code` 的取值口径变更（多行组填组内首行 `id`、单行填自身 `id`，列 `NOT NULL`），拼音课没有这一列。本文只同步修正 §3.3「三层逻辑」下方一句对写字课的描述：原写「写字课需要 XML 是因为有 `COUNT(DISTINCT group_code)` 这类聚合」**是错的**，写字课的 `cardCount` 同样在 Java 侧对已加载集合去重，**两门课都不需要 mapper XML**。
>
> **2026-09-19**：「数据流向」**已补齐到本文全部 7 个端点**（此前只有 3.1.1 有）。约定随之固定为**每节七段**，第七段「数据流向」= 入参/查库 → 加工 → 组装 的 ASCII 流程 + 响应字段映射对照 + 关键 SQL 与 ⚠️ 要点。3.2.5 与写字课 §3.2.7 同表同逻辑，该节只列拼音课的实际数据。
>
> **2026-09-20 修订（当日第四版）**：**§0.4 的「ID 序列化」结论反转** ——
> 原来写的「必须全局配置 `Long → String`」**已作废**：本服务响应里没有超 2^53 的数（下发的 `id` 全是 `301`–`314`、`courseId` 是 `900`，都只有 3 位），而唯一带雪花的 `userId` 在拼音课**根本不存在**（全部接口免登录）。因此**既不配全局序列化器、也不挂字段级注解**，**全文 JSON 示例中的 id 一律由字符串改为数字**（共 **34 处**）。§0.4 已改写为同结论的摘要版，完整论证（含边界条件）见 `写字课-接口设计文档.md` §0.4。
> 另：附录字段表里 `items[].id` 的类型标注由 `String` 改为 `Long`。
> ⚠️ **本次不涉及拼音课的任何接口逻辑**，只改了 id 的类型表示。

**缓存边界 —— 拼音课比写字课简单得多：**

| 接口产出 | 与用户相关？ | 可缓存？ |
|---|---|---|
| 全部内容（catalog / 单条目 / 简介） | **否** | ✅ 可长期进 IndexedDB，靠 `dataVersion` 失效 |
| — | — | **没有例外** |

> 写字课有一条「进度不可缓存」的例外（`/groups`、`/progress` 必须现拉）。**拼音课没有这个例外**——整门课可以被客户端完整离线缓存，包括弹窗要用的视频/音频（媒体另走 MinIO 的 HTTP 缓存）。
>
> 这也是拼音课不需要"分包下发"的原因：实测全量 catalog 仅 **3.1 KB**（见 §2.1），不需要像写字课的 `/chars` 那样按组拆。

## 1. 用户操作流程与接口对照

### 1.1 页面流转

```
首页
 └─[中文入门课] 入口卡片                          ── GET /course/catalog
     └─[拼音课] 课程卡片
         │
         ├─ 简介页：认识汉语拼音（文字卡片 + 条目）   ── GET /course/pinyin/intro
         │
         └─ 主页面（顶部标签栏：声母 / 韵母 / 声调 [· 整体认读待定]）
             │                                       ── GET /course/pinyin/catalog（一次拿全部 tab）
             │
             ├─ 声母 tab：单一扁平网格（无分组标题）
             │   └─ 点某个字母「b」 → 发音教学弹窗     ── 数据已在 catalog 里，无需再请求
             │       ├─ 大字 b + 口型发音视频（videoUrl）
             │       ├─ 播放标准发音（audioUrl）
             │       ├─ 4 个调值 chips「bā bá bǎ bà」 ── 前端按标调规则实时派生，音频按命名约定
             │       └─ 「3 步提示」                   ── ⚠️ 数据承载待确认，见 §4.4 第 4 条
             │
             ├─ 韵母 tab：三个分组网格
             │   ├─ 单韵母 a o e i u ü
             │   ├─ 双韵母·鼻韵母 ai ei … an en … ang eng …
             │   └─ 复韵母 ia ie … ua uo … üe …
             │   └─ 点某个韵母 → 弹窗同上
             │
             └─ 声调 tab：竖向卡片列表
                 ├─ 4 张声调卡「ā 一声 阴平·55 妈 mā」  ── 点卡片播放调值音频
                 ├─ 1 条轻声通栏行「不标调号，读得又轻又短」
                 └─ 2 条变调规则行「一」「不」
```

**两个"无需请求"点**（与写字课同构，是 catalog 全量返回带来的收益）：

1. **发音弹窗不用额外请求** —— `letter` / `videoUrl` / `audioUrl` / `exampleText` 都已在 catalog 里
2. **调值 chips 不用额外请求** —— 它是「同一韵母 × 4 个调」的**派生视图**，由前端按标调规则生成（方案 §3.1 明确「不入库」），对应的音频走命名约定而非数据库行

### 1.2 场景 → 接口对照表

| # | 用户看到的东西 | 用户动作 | 接口 | 登录 | 可缓存 |
|---|---|---|---|---|---|
| 1 | 首页「中文入门课」入口卡片 | 打开 App 首页 | `GET /course/catalog` | 否 | ✅ |
| 2 | 首页卡片是否要刷新 | 下拉刷新 | `GET /course/catalog/version` | 否 | — |
| 3 | 拼音课卡片 | 点进拼音课 | `GET /course/pinyin/catalog` | 否 | ✅ |
| 4 | 简介页「认识汉语拼音」卡片 + 3 个条目 | 进入简介页 | `GET /course/pinyin/intro` | 否 | ✅ |
| 5 | 3 个 tab + 声母网格 | 进入主页面 | `GET /course/pinyin/catalog` | 否 | ✅ |
| 6 | 发音教学弹窗（大字 + 视频 + 音频） | 点某个字母 | **无需请求**（`videoUrl` / `audioUrl` 已在 catalog 里） | 否 | ✅ |
| 7 | 弹窗里 4 个调值 chips `bā bá bǎ bà` | — | **无需请求**（前端派生 + 命名约定音频） | 否 | ✅ |
| 8 | 韵母三组网格 | 切到韵母 tab | **无需请求**（已在 catalog 里） | 否 | ✅ |
| 9 | 声调 4 卡 + 轻声条 + 2 条变调 | 切到声调 tab | **无需请求**（已在 catalog 里） | 否 | ✅ |
| 10 | 某个标签页的完整条目列表 | 切 tab / 单独刷新 / 管理端预览 | `GET /course/pinyin/items?category=INITIAL` | 否 | ✅ |
| 11 | 单条目详情（含视频） | 深链进入 / 分享 / 重试 | `GET /course/pinyin/items/301` | 否 | ✅ |
| 12 | 课程内容更新了 | 再次进入 | `GET /course/pinyin/catalog/version` 比对 | 否 | — |

**对比写字课的 18 条**：拼音课只有 12 条，且**没有一条需要登录**、**没有一条不可缓存**。差异全部来自"不做进度"这一个决定。

### 1.3 一次完整会话的调用时序

以「首次进入 → 看简介 → 看声母 → 点开 b 的发音弹窗 → 切到声调页」为例：

```
①  GET /course/catalog                      → 拿到拼音课卡片（courseId=900）
②  GET /course/pinyin/catalog               → 3-4 个 tab + 68 条目 + dataVersion
    ③  写入 IndexedDB（key: pinyin-catalog@{dataVersion}）
④  GET /course/pinyin/intro                 → 简介页两级结构
⑤  （点字母 b）无需请求 —— 弹窗数据已在 ②
    ⑥  播放 audio/pinyin/b.mp3；视频播 videoUrl（当前为 null → 降级为封面+音频）
⑦  （切声调 tab）无需请求 —— 数据已在 ②
    ⑧  点声调卡 → 播放 audio/pinyin/tone1.mp3；4 个 chips 的音频按命名约定推导
```

**第二次进入**（缓存命中）：只走 ① → ② 的版本比对 → 版本没变则**直接用 IndexedDB，一次业务请求都不发**（简介和条目都在同一份缓存里）。

> 这是拼音课相对写字课的一个明显优势：写字课因为进度不可缓存，二次进入至少还要打 `/groups` + `/progress` 两个请求；拼音课可以做到**纯离线冷启动**。

### 1.4 离线与缓存

| 场景 | 行为 |
|---|---|
| **完全离线进入拼音课** | ✅ **全功能可用**：tab / 网格 / 所有弹窗数据都在 IndexedDB 里 |
| **离线首次进入**（从未拉过） | ❌ 不可用（没有进度这类可降级的数据，内容就是全部） |
| **内容更新后** | 客户端比对 `dataVersion` 变化 → **整门课全量失效重拉**（一次请求即可，因为只有 3 KB） |
| **媒体资源** | 音频/视频走 MinIO 的 HTTP 缓存，与 `dataVersion` 无关；未就绪时前端降级（见 §4.4 第 5 条） |
| **跨设备** | **无状态**。拼音课没有用户数据，换设备不需要同步任何东西 |

|---|---|---|---|---|---|---|
| 1 | `GET` | `/course/catalog` | 首页入口 + 课程卡片列表（与写字课共用） | 否 | ✅ | < 2 KB |
| 2 | `GET` | `/course/catalog/version` | 首页内容版本探测（补漏，§0.7） | 否 | — | < 200 B |
| 3 | `GET` | `/course/pinyin/catalog` | **核心**：全部 tab + 全部条目 | 否 | ✅ | **3.1 KB**（14 条实测）；满量 68 条约 **15 KB** |
| 4 | `GET` | `/course/pinyin/catalog/version` | 拼音课内容版本探测 | 否 | — | < 200 B |
| 5 | `GET` | `/course/pinyin/items?category=` | 单标签页条目列表（**新增**） | 否 | ✅ | 声母页约 5 KB（满量 23 条） |
| 6 | `GET` | `/course/pinyin/items/{id}` | 单条目详情（**新增**） | 否 | ✅ | < 500 B |
| 7 | `GET` | `/course/pinyin/intro` | 拼音课简介页（两级结构） | 否 | ✅ | ~1 KB |

> **量级依据（测试库实测，非估算）**
>
> | 项 | 实测值 |
> |---|---|
> | `/course/pinyin/catalog` 完整 JSON（14 条） | **2 863 字符 / 3 118 字节** |
> | 单条目平均 | **约 205 字符** |
> | 满量 68 条推算 | 约 **14 K 字符 ≈ 15 KB** |
> | 若 `description` 三语齐备（当前测试数据全为 NULL） | 约 **30 KB** |
>
> **结论：拼音课永远不需要分包下发。** 即便满量 + 三语齐备也只有 30 KB，比写字课单组汉字（10 KB）大不了多少，却是"整门课一次拉完"。这与写字课 `/chars` 必须按组的结论**形成对照**，原因在数据形态：拼音条目是短文本，写字汉字带 MB 级 SVG 路径。
>
> ⚠️ 注意测试库当前**只有 14 条**（3 声母 + 4 韵母 + 7 声调页），远少于方案 §0.1 的 68 条目标。满量推算成立的前提是条目平均体量不变——**条目越长（如变调规则的 `description` 写得很长），推算越偏**。

|---|---|---|---|

## 3. 接口详细设计

> 每节固定七段：**接口用处 / 入参 / 返回 JSON / 业务逻辑 / 三层逻辑 / 涉及表 / 数据流向**。
> 返回示例均为**测试库 `xuexitest` 真实数据**（courseId=900 拼音课）。

### 3.1 入口层（通用）

#### 3.1.1 GET /course/catalog

##### 接口用处

App 首页的「中文入门课」聚合入口 + 课程卡片列表。**拼音课流程的第 1 步**——为拿到拼音课的 `courseId`（后续 `/pinyin/**` 接口虽然多数用 `code` 定位，但弹窗、埋点、路由都要 `courseId`）。

本接口与写字课**完全共用**，实现细节见 `写字课-接口设计文档.md` §3.1.1，本文只列拼音课视角下的要点。

##### 入参

| 参数 | 位置 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| `Accept-Language` | Header | String | 否 | 内容语言，缺省 `zh` |

无 Query 参数。

##### 返回 JSON

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "homeEntry": {
      "id": 950,
      "code": "BEGINNER_COURSE",
      "title": "中文入门课",
      "subtitle": "从零开始，学会拼音与汉字书写",
      "coverUrl": null,
      "badge": "NEW",
      "badgeEnabled": true,
      "sortOrder": 1
    },
    "courses": [
      {
        "id": 900,
        "code": "PINYIN",
        "name": "拼音课",
        "subtitle": "从声母、韵母和声调开始，学习中文发音",
        "bannerUrl": null,
        "sortOrder": 1
      },
      {
        "id": 901,
        "code": "HANDWRITING",
        "name": "写字课",
        "subtitle": "从笔画和笔顺开始，学会书写汉字",
        "bannerUrl": null,
        "sortOrder": 2
      }
    ],
    "dataVersion": 1789613781244
  }
}
```

**拼音课侧要取的是 `courses[code='PINYIN']` 这一项**（`id = "900"`、`sortOrder = 1`）。前端按 `code` 分流，**不要按数组下标取**——写字课是 `courses[1]`，将来加课程还会变。

##### 业务逻辑

1. **查入口卡片**：`course_home_entry` 里 `code='BEGINNER_COURSE'`、启用且未删的那一行。正常只有一行。
2. **查课程列表**：`course` 里 `home_id='BEGINNER'`、启用且未删的行，按 `sort_order, id` 排序。**拼音课与写字课都在里面**。
3. **取文案**：`name` / `subtitle` / `title` 按 `Accept-Language` 从 `_en` / `_vi` 回退，缺了用中文。
4. **算版本号**：两张表各自的 `MAX(data_version)` 取较大者。任一边被改过，这个号就会变（SQL 见下方「数据流向」）。
5. **组装返回**：入口卡片查不到就返回 `null`，不报错。

> ⚠️ **注意本接口的 `dataVersion` 是"两门课的最大值"**，与 `/course/pinyin/catalog/version`（只回拼音课的 `data_version`）**口径不同**。前者用于首页卡片缓存，后者用于课程内容缓存，**不要混用**。

##### 三层逻辑

| 层 | 类 / 方法 | 职责 |
|---|---|---|
| Controller | `common/controller/CourseCatalogController.getCatalog(HttpServletRequest)` | 解析语言、调 Service、包 `Result` |
| Service | `common/service/CourseCatalogService#getCatalog(String lang) → CourseCatalogResponse` | 两次查询、i18n 回退、`GREATEST` 版本计算、组装 |
| Mapper | `common/mapper/CourseHomeEntryMapper`、`common/mapper/CourseMapper` | MyBatis-Plus `selectOne` / `selectList` |

##### 涉及表

| 表 | 操作 | 用到的列 |
|---|---|---|
| `course_home_entry` | SELECT | `code` / `title`+`_en`+`_vi` / `subtitle`+`_en`+`_vi` / `cover_url` / `badge` / `badge_enabled` / `sort_order` / `enabled` / `deleted` / `data_version`（仅版本计算用，`updated_time` 已不再参与） |
| `course` | SELECT | `id` / `code` / `name`+`_en`+`_vi` / `subtitle`+`_en`+`_vi` / `banner_url` / `home_id` / `sort_order` / `enabled` / `deleted` / `data_version` |

##### 数据流向

**① 查库 → ② 加工 → ③ 组装**

```
① 查库    course_home_entry  ──selectOne ──→  入口卡片（1 行）
           course             ──selectList──→  课程卡片（N 行）

② 加工    name / title / subtitle  ──Accept-Language──→  单语文案
           course.data_version       ──┐
           （各自 MAX）                ├──GREATEST──→  dataVersion
           course_home_entry.…       ──┘

③ 组装    CourseCatalogResponse { homeEntry, courses[], dataVersion }  ──→  JSON
```

**映射对照**

| 响应字段 | 来自 | 取法 |
|---|---|---|
| `homeEntry` | `course_home_entry` 那 1 行 | 直取；`title` / `subtitle` 做语言回退 |
| `courses[]` | `course` 的 N 行 | 按 `sort_order, id` 排序；`name` / `subtitle` 做语言回退 |
| `dataVersion` | 两张表的 `data_version` | `GREATEST(两边 MAX)`，见下方 SQL |

**版本号 SQL**

```sql
GREATEST(
  COALESCE((SELECT MAX(data_version) FROM course            WHERE home_id='BEGINNER' AND enabled=1 AND deleted=0), 0),
  COALESCE((SELECT MAX(data_version) FROM course_home_entry WHERE code='BEGINNER_COURSE' AND deleted=0), 0)
)
```

> ⚠️ **`COALESCE(…, 0)` 不能省**：`MAX()` 在「一行都没有」时返回 `NULL`（**与列是否 `NOT NULL` 无关**），而 `GREATEST` 遇 `NULL` 会整体返回 `NULL` → 首页 `dataVersion` 变成 `null`。`course_home_entry` 只有一行，软删即触发。
> ⚠️ **两个来源缺一不可**：只取课程的号 → 改入口文案 / 下架入口时号不动，客户端永远不刷新；只取入口的号 → 改课程名 / 上下架课程时同样不刷新。
> 不取 `MAX(updated_time)` 的原因见方案 §2.0.4。

#### 3.1.2 GET /course/catalog/version

##### 接口用处

首页的**极轻量**版本探测。客户端已有缓存时，先问一句"变了吗"，没变就完全不走 `/course/catalog`。

##### 入参

无。

##### 返回 JSON

```json
{ "code": 200, "message": "操作成功", "data": { "dataVersion": 1789613781244 } }
```

##### 业务逻辑

与 [3.1.1](#311-get-coursecatalog) 第 4 条**同一个 `GREATEST` 表达式**，只回一个 Long。抽成 `CourseCatalogService#resolveHomeDataVersion()` 供两处共用。

**⚠️ 客户端的比对语义：用「不相等」，不要用「大于」。** `remote > cached` 在版本号降级时（聚合链路的 `COALESCE` 兜成 `0`、或历史缓存里存的是 `null`）恒为 `false` → 客户端**永远**认为没变、且**不会自愈**；`remote !== cached` 最坏只是白拉一次 2 KB。

##### 三层逻辑

| 层 | 类 / 方法 | 职责 |
|---|---|---|
| Controller | `CourseCatalogController.getCatalogVersion()` | 直接转发 |
| Service | `CourseCatalogService#resolveHomeDataVersion() → Long` | 唯一版本计算入口 |
| Mapper | `CourseHomeEntryMapper`、`CourseMapper` | 两个聚合查询 |

##### 涉及表

| 表 | 操作 | 用到的列 |
|---|---|---|
| `course` | SELECT MAX | `data_version` / `home_id` / `enabled` / `deleted` |
| `course_home_entry` | SELECT MAX | `data_version` / `code` / `deleted` |

##### 数据流向

**① 查库 → ② 加工 → ③ 组装**

```
① 查库    course             ──SELECT MAX(data_version)──→  课程侧最大号
           course_home_entry  ──SELECT MAX(data_version)──→  入口侧最大号

② 加工    课程侧号  ──┐
           （各自 MAX）├──GREATEST(COALESCE(.,0), COALESCE(.,0))──→  一个号
           入口侧号  ──┘

③ 组装    DataVersionResponse { dataVersion }  ──→  JSON
```

**映射对照**

| 响应字段 | 来自 | 取法 |
|---|---|---|
| `dataVersion` | `course` + `course_home_entry` 各自的 `data_version` | 两侧先 `MAX`，再 `GREATEST`；与 3.1.1 第 4 条**同一个表达式、同一个方法** |

**版本号 SQL**

```sql
GREATEST(
  COALESCE((SELECT MAX(data_version) FROM course            WHERE home_id='BEGINNER' AND enabled=1 AND deleted=0), 0),
  COALESCE((SELECT MAX(data_version) FROM course_home_entry WHERE code='BEGINNER_COURSE' AND deleted=0), 0)
)
```

> ⚠️ **必须抽成 `CourseCatalogService#resolveHomeDataVersion()` 与 3.1.1 共用**，不要各写一份 —— 两处口径一旦漂移，客户端就会"版本说没变、拉下来却发现变了"。
> ⚠️ `COALESCE(…, 0)` 不能省（`MAX()` 无行返回 `NULL`，`GREATEST` 遇 `NULL` 整体返 `NULL`）；两个来源缺一不可。理由见 3.1.1 的同名小节。

| `items[].audioUrl` | String / 省略 | 标准发音音频地址 |
| `items[].sortOrder` | Number | 同标签页内排序 |

**不下发**：`extJson` / `descriptionEn` / `descriptionVi`（已回退到 `description`）/ `enabled` / `deleted` / `createdBy` / `updateBy` / `createdTime` / `updatedTime`。

##### 关键：网格空位怎么还原

这是本接口**唯一需要精心实现的地方**，也是原型数据里最容易被忽略的细节。

方案 §0.2 记录原型的声母页是**二维数组**、且 `g k h` 那行后面有 `null` 占位：

```js
initials: { rows: [['b','p','m','f'], …, ['y','w',null,null]], … }
```

数据库里**不存占位行**（方案 §3.1 原话：「空位不建行，前端补占位」），只存 `row_index` / `col_index`。所以还原规则是：

1. 前端按 `colCount` × `rowCount` 建一个空网格
2. 把每个 item 放到 `[rowIndex][colIndex]` 格里
3. **没被占用的格子渲染为占位**（不出卡片）

接口层要做的是**把 `colCount` / `rowCount` 算准**：

```
colCount = MAX(col_index) over items in block（忽略 NULL）
rowCount = MAX(row_index) over items in block（忽略 NULL）
```

**服务端不做插空、不补齐 null 项**——补空是渲染细节，不该让传输层承担（否则 68 条数据里会混入一堆 `null`，既浪费带宽又让"共N个"的计数变复杂）。

> ⚠️ **告警条件**：同一 block 内**部分有行列号、部分没有**（比如 23 个声母里只有 20 个填了 `row_index`）。这会产生一个说不清的渲染结果——填了的按格摆放、没填的不知往哪塞。**建议服务端检测到这种混用就打 warn 日志**，管理端应保证同一 tab 内要么全填、要么全不填。

##### 业务逻辑

1. **定位课程**：`SELECT id, code, name, subtitle, banner_url, data_version FROM course WHERE code='PINYIN' AND enabled=1 AND deleted=0`。查不到 → 抛 `BusinessException`（建议用业务码 `COURSE_NOT_CONFIGURED`，见 §4.3 第 10 条）。**不要静默返回空 tabs** —— 课程没配置是部署事故，必须暴露。
2. **一次查询取全量条目**（不做 JOIN、不分页）：
   ```sql
   SELECT * FROM course_pinyin_item
   WHERE enabled = 1 AND deleted = 0
   ORDER BY category_code, sort_order, id;
   ```
3. **按 `category_code` 分组 → 再按 `node_type` 分组**，得到 `tabs[].blocks[].items[]` 三层结构。
4. ⚠️ **`category_code` 的排序不能用 SQL 的 `ORDER BY`**。字典序会得到 `FINAL, INITIAL, TONE, WHOLE_SYLLABLE`，**和产品要求的「声母 → 韵母 → 声调」正好相反**。必须在 Java 里按固定常量排序：
   ```java
   // 标签页固定顺序，与产品标签栏一致
   private static final List<String> TAB_ORDER =
       List.of("INITIAL", "FINAL", "TONE", "WHOLE_SYLLABLE");
   ```
   常量用 `List.of` 而非枚举 `ordinal()`——将来加 tab 时不会因为枚举声明顺序变化而悄悄改掉前端顺序。
5. ⚠️ **`node_type` 的 block 顺序同样不能用字典序**。韵母页要求「单韵母 → 双韵母·鼻韵母 → 复韵母」，字典序却是 `COMPOUND_FINAL, DOUBLE_NASAL_FINAL, SIMPLE_FINAL`（**完全颠倒**）；声调页要求「声调卡 → 轻声 → 变调」，字典序是 `NEUTRAL, SANDHI, TONE`。同样用固定常量：
   ```java
   private static final List<String> BLOCK_ORDER = List.of(
       "PHONEME",
       "SIMPLE_FINAL", "DOUBLE_NASAL_FINAL", "COMPOUND_FINAL",
       "TONE", "NEUTRAL", "SANDHI");
   ```
   > 这两条是**本接口最容易写错、且错了很难发现**的地方：数据都在、结构也对，只是顺序反了，测试时若不是逐个比对截图不会注意到。
6. **`layout` 由 `node_type` 派生**（常量映射，不落库）：
   | `nodeType` | `layout` |
   |---|---|
   | `PHONEME` / `SIMPLE_FINAL` / `DOUBLE_NASAL_FINAL` / `COMPOUND_FINAL` | `GRID` |
   | `TONE` | `CARD_LIST` |
   | `NEUTRAL` | `FULL_ROW` |
   | `SANDHI` | `LIST_ROW` |
7. **计算 `colCount` / `rowCount`**：见上「网格空位怎么还原」。**只在 `GRID` 类 block 计算**；非网格 block 两个字段都不下发。
8. **条目排序**：block 内按 `sortOrder`，相同则按 `id` 兜底（保证顺序稳定）。
9. **i18n**：**只对 `description` 做 `_en` / `_vi` 回退**。`letter` / `exampleText` / `toneValue` 原样返回（§0.3 的表）。
10. **`itemCount`**：tab 级 = 该 tab 全部 block 的条目数之和；block 级 = 该 block 的条目数。**用 Java 侧集合的 `size()`**，不要为计数再发一条 `COUNT(*)` SQL（数据已经全在手里了）。
11. **`WHOLE_SYLLABLE` 不做特殊处理**：有数据就返回，没数据就不出现这个 tab。前端是否展示第 4 个标签栏由它自己的配置决定（方案 §3.1：数据层已兼容两种做法）。
12. **不要按 `letter` 去重**：同一个 `letter` 在**不同 tab 是两行**（`b` 既在声母页、也可能在整体认读页）——方案 §2.0.2 原话「`node_type='PHONEME'` 同时出现在声母页与整体认读页」。去重会把其中一个 tab 的卡片吃掉。
13. **无缓存穿透风险**：本接口不按用户维度变化，可以做 HTTP 层或本地缓存（`Cache-Control: public`），但**必须与 `dataVersion` 联动**——最简做法是交客户端 IndexedDB，服务端不引入缓存组件。

##### 三层逻辑

| 层 | 类 / 方法 | 职责 |
|---|---|---|
| Controller | `pinyin/controller/PinyinCatalogController#getCatalog(HttpServletRequest request)` | 解析语言（`LanguageSupport.resolve`）；调 Service；包 `Result.success`。**不含业务判断** |
| Service | `pinyin/service/PinyinCatalogService#getCatalog(String lang) → PinyinCatalogResponse` | ① 定位课程；② 全量查询；③ 两级分组；④ **按固定常量排序 tab 与 block**；⑤ 派生 `layout`；⑥ 算 `colCount`/`rowCount`；⑦ i18n；⑧ 组装 |
| Mapper | `pinyin/mapper/CoursePinyinItemMapper`、`common/mapper/CourseMapper` | MyBatis-Plus `selectList` + `LambdaQueryWrapper`（`enabled=1`、`deleted=0`、`orderByAsc(categoryCode, sortOrder, id)`） |

> **`CoursePinyinItemMapper` 不需要 XML**：本接口没有任何自定义 SQL（分组、排序、计数全在 Service 层用 Java 集合做）。写字课同样如此 —— 它的 `cardCount` 也是在 Java 侧对已加载集合去重，不写 `COUNT(DISTINCT …)`；两门课都不需要 mapper XML。

| `course_pinyin_item` | SELECT | `id` / `category_code` / `node_type` / `letter` / `tone_name` / `tone_value` / `example_text` / `description`+`_en`+`_vi` / `row_index` / `col_index` / `video_url` / `audio_url` / `sort_order` / `enabled` / `deleted` |

##### 数据流向

**① 查库 → ② 分组排序 → ③ 算尺寸 → ④ 加工 → ⑤ 组装**

```
① 查库    course             ──selectOne──→  课程（1 行：id / 文案 / data_version）
           course_pinyin_item ──selectList──→  全部条目（测试库 14 行，满量 68 行）

② 分组    条目  ──按 category_code 分组──→  tabs
           条目  ──再按 node_type 分组──→  blocks
           两组键  ──TAB_ORDER / BLOCK_ORDER 常量排序──→  固定产品顺序

③ 算尺寸  block 内 row_index / col_index  ──MAX（忽略 NULL）──→  rowCount / colCount
            （仅 GRID 类 block；非网格两个字段都不下发）

④ 加工    node_type  ──固定映射──→  layout（纯派生，库里无此列）
           description  ──Accept-Language──→  单语
           （letter / toneValue / exampleText 绝不翻译）

⑤ 组装    PinyinCatalogResponse { 课程字段, dataVersion, tabs[].blocks[].items[] }  ──→  JSON
```

**映射对照**

| 响应字段 | 来自 | 取法 |
|---|---|---|
| `courseId` / `courseCode` / `name` / `subtitle` / `bannerUrl` | `course` 那 1 行 | 直取；`name` / `subtitle` 语言回退 |
| `dataVersion` | `course.data_version` | 直取（与 3.2.2 同源） |
| `tabs[]` | `course_pinyin_item` | 按 `category_code` 分组，**只含有条目的 tab**；顺序走 `TAB_ORDER` 常量 |
| `tabs[].itemCount` | 同上 | 该 tab 各 block 条目数之和（Java `size()`，不再发 `COUNT(*)`） |
| `blocks[]` | 同上 | 再按 `node_type` 分组；顺序走 `BLOCK_ORDER` 常量 |
| `blocks[].layout` | `node_type` | **常量映射**（GRID / CARD_LIST / FULL_ROW / LIST_ROW），不落库 |
| `blocks[].rowCount` / `colCount` | `row_index` / `col_index` | 仅 GRID 类：各自取 `MAX`；全无行列号时两个字段整体不下发 |
| `items[].id` / `letter` / `toneName` / `toneValue` / `exampleText` / `videoUrl` / `audioUrl` / `sortOrder` | `course_pinyin_item` | 直取（**不翻译**）；空字段在列表场景省略 |
| `items[].description` | 同上 | **唯一走多语言**的字段 |
| `blocks[].colCount` 等 | — | 不下发 `extJson` / `descriptionEn` / `descriptionVi` / `enabled` / `deleted` / 审计列 |

**关键 SQL**

```sql
/* ① 定位课程 */
SELECT id, code, name, name_en, name_vi, subtitle, subtitle_en, subtitle_vi, banner_url, data_version
FROM course
WHERE code = 'PINYIN' AND enabled = 1 AND deleted = 0;

/* ② 全量条目（一次取完，不分页、不 JOIN） */
SELECT * FROM course_pinyin_item
WHERE enabled = 1 AND deleted = 0
ORDER BY category_code, sort_order, id;
```

> ⚠️ **SQL 里的 `ORDER BY category_code` 只是给分组前定序，不能当作最终顺序**：`category_code` 的字典序是 `FINAL, INITIAL, TONE, WHOLE_SYLLABLE`，**与产品要求的「声母 → 韵母 → 声调」正好相反**；`node_type` 同样颠倒（韵母页字典序是 `COMPOUND_FINAL, DOUBLE_NASAL_FINAL, SIMPLE_FINAL`）。最终顺序必须由 `TAB_ORDER` / `BLOCK_ORDER` 常量决定，也**不要用枚举 `ordinal()`**。这是本接口"错了很难发现"的地方 —— 数据都在、结构也对，只是顺序反了。
> ⚠️ **不按 `letter` 去重** —— 同一个 `letter` 在不同 tab 是两条数据（`b` 既在声母页、也出现在整体认读页）。
> ⚠️ 服务端**不插空、不补 null 项**：网格空位靠前端按 `rowCount × colCount` 建格 + 行列号摆放还原；同一 block 内"部分有行列号、部分没有"属脏数据，打 warn。

#### 3.2.2 GET /course/pinyin/catalog/version

##### 接口用处

拼音课的离线缓存版本探测。客户端 IndexedDB 里存着上一次的 `dataVersion`，进课程前先比一次；没变就跳过 `/course/pinyin/catalog`——**拼音课甚至可以做到完全离线冷启动**（见 §1.3）。

##### 入参

无。

##### 返回 JSON

```json
{ "code": 200, "message": "操作成功", "data": { "dataVersion": 1789613781244 } }
```

##### 业务逻辑

```sql
SELECT data_version FROM course WHERE code='PINYIN' AND enabled=1 AND deleted=0;
```

**与 `/course/pinyin/catalog` 的 `dataVersion` 必须同源**，抽同一个 Service 方法（`PinyinCatalogService#resolveDataVersion()`）。

> **与 `/course/catalog/version` 的区别**：这个只回拼音课自己的 `data_version`，那个回两门课的 `MAX` + 入口 `course_home_entry` 的 `data_version`。**别把两个接口实现成同一个方法。**

> `data_version` 覆盖 `course_pinyin_item` **和本课 `course_intro_section`**，所以简介页缓存也应挂在同一个版本号上——本接口一次探测即可同时失效 catalog 与 intro 两份缓存。

| 层 | 类 / 方法 | 职责 |

| Service | `PinyinCatalogService#resolveDataVersion() → Long` | 唯一入口，与 3.2.1 共用 |
| Mapper | `common/mapper/CourseMapper` | 单行查询 |

##### 涉及表

| 表 | 操作 | 用到的列 |
|---|---|---|
| `course` | SELECT | `data_version` / `code` / `enabled` / `deleted` |

##### 数据流向

**① 入参 → ② 查库 → ③ 组装**

```
① 入参    无

② 查库    course  ──SELECT data_version──→  拼音课自己的号

③ 组装    DataVersionResponse { dataVersion }  ──→  JSON
```

**映射对照**

| 响应字段 | 来自 | 取法 |
|---|---|---|
| `dataVersion` | `course.data_version` | 单行直取；与 3.2.1 的 `dataVersion` **必须同源**（同一个 `resolveDataVersion()`） |

**关键 SQL**

```sql
SELECT data_version FROM course
WHERE code = 'PINYIN' AND enabled = 1 AND deleted = 0;
```

> ⚠️ 这个号覆盖 `course_pinyin_item` **以及本课 `course_intro_section`**，所以一次探测可同时失效 catalog 与 intro 两份缓存。
> ⚠️ **与 `/course/catalog/version` 不是一回事**：那个是"两门课 + 入口"的聚合号，这个是拼音课单课号，**不要共用一个方法**。

| `dataVersion` | `course.data_version` | 直取（与 3.2.1 / 3.2.2 同源） |
| `blocks[]` | `course_pinyin_item` | **与 3.2.1 的单个 `tabs[]` 元素结构完全一致**（同一 `buildBlocks` 产出） |
| `blocks[].layout` / `rowCount` / `colCount` / `items[]` | 同上 | 取法同 3.2.1 映射表 |

**关键 SQL**

```sql
SELECT data_version FROM course
WHERE code = 'PINYIN' AND enabled = 1 AND deleted = 0;

SELECT * FROM course_pinyin_item
WHERE category_code = ? AND enabled = 1 AND deleted = 0
ORDER BY sort_order, id;
```

> ⚠️ **非法 `category` 一律 `400`、不静默返回空列表**（打错分类名要立刻暴露）；但**合法分类查不到数据是正常的** —— `WHOLE_SYLLABLE` 当前无数据，应回 `itemCount: 0, blocks: []`。
> ⚠️ **block 顺序同样由 `BLOCK_ORDER` 常量决定**，不能沿用 SQL 的字典序（理由与 3.2.1 相同）。

**单个条目的完整详情**，含发音弹窗需要的全部字段。用于：

##### 业务逻辑

1. 查询：`SELECT ... FROM course_pinyin_item WHERE id=? AND enabled=1 AND deleted=0`。
2. **查不到 / 已禁用 / 已删除 → 一律返回"不存在"**（不区分这三种情况，避免把禁用条目的存在性暴露给客户端）。
3. `courseId` 与 `dataVersion` **冗余返回**：本接口会被独立调用（深链场景没有 catalog 上下文），前端需要知道这是哪门课的哪一版，才能决定要不要把结果并入本地缓存。
4. `layout` 同样按 `node_type` 派生返回（规则见 3.2.1 第 6 条）。
5. i18n 同 3.2.1。`toneName` / `toneValue` / `rowIndex` / `colIndex` **为 null 时保留字段**（不省略）——本接口是"单条完整对象"，字段集固定比"按需省略"更好用；这与 3.2.1 里"列表场景省略空字段"的做法**刻意不同**，理由是列表要省带宽、单条不要。

##### 三层逻辑

| 层 | 类 / 方法 | 职责 |

| Controller | `PinyinCatalogController#getItem(@PathVariable Long id, HttpServletRequest request)` | 解析语言；调 Service；包 `Result` |

| Mapper | `pinyin/mapper/CoursePinyinItemMapper` | `selectById`（**注意要额外判 `enabled` / `deleted`**，`selectById` 走不了逻辑删除插件时需显式加条件） |

##### 涉及表

| 表 | 操作 | 用到的列 |
|---|---|---|
| `course_pinyin_item` | SELECT | 全部业务列（`id` / `category_code` / `node_type` / `letter` / `tone_name` / `tone_value` / `example_text` / `description`+`_en`+`_vi` / `row_index` / `col_index` / `video_url` / `audio_url` / `sort_order` / `enabled` / `deleted`） |
| `course` | SELECT | `id` / `code` / `data_version` |

##### 数据流向

**① 入参 → ② 查库 → ③ 加工 → ④ 组装**

```
① 入参    id  ──主键──→  唯一入参

② 查库    course_pinyin_item  ──selectById + enabled/deleted 条件──→  条目 1 行

           （toneName / toneValue / rowIndex / colIndex 为 null 时**保留字段**，不省略）

④ 组装    PinyinItemDetailResponse { 全部字段 + courseId + dataVersion }  ──→  JSON
```

**映射对照**

| 响应字段 | 来自 | 取法 |
|---|---|---|
| `id` / `categoryCode` / `nodeType` / `letter` / `toneName` / `toneValue` / `exampleText` / `rowIndex` / `colIndex` / `sortOrder` / `videoUrl` / `audioUrl` | `course_pinyin_item` 那 1 行 | 直取（**不翻译**）；空值**保留字段** |
| `description` | 同上 | `pick(description, description_en, description_vi, lang)` |
| `layout` | `nodeType` | 常量映射派生（同 3.2.1 第 6 条） |

| `dataVersion` | `course.data_version` | 冗余返回，供前端判断要不要并入本地缓存 |

**关键 SQL**


> ⚠️ **"查不到 / 已禁用 / 已删除"一律返回同一种"不存在"**，不区分 —— 否则会把禁用条目的存在性暴露给客户端。
> ⚠️ 本接口**刻意不省略空字段**（与 3.2.1 列表场景相反）：单条完整对象字段集固定更好用，列表才需要省带宽。

| 调序红标签 | `TONE1`…`TONE4` / `NEUTRAL` | 一声 / 二声 / 三声 / 四声 / 轻声 |
| 调型名 | `toneValue` 的 4 个值：`55` / `35` / `214` / `51` | 阴平 / 阳平 / 上声 / 去声 |

> ⚠️ 最后一行**键是调值不是枚举**，很容易做错。方案 §2.0.2 明确：「调型名属语言学固定术语，与调值一一对应，故不落库，由前端 i18n 字典**按 `tone_value` 映射**得到」。

### 4.3 待确认事项

| # | 事项 | 影响 | 建议 |
|---|---|---|---|
| 1 | `GET /course/pinyin/items?category=` 与 `GET /course/pinyin/items/{id}` 是**新增端点** | 接口数量 | 见 [3.2.3](#323-get-coursepinyinitemscategory) / [3.2.4](#324-get-coursepinyinitemsid)。**若确认不做深链与管理端预览，两个都可以砍掉**；catalog 已含全部数据 |
| 2 | **「3 步提示」无数据承载** | 发音弹窗内容 | 见 §4.4 第 4 条 |
| 3 | **4 个调值音频的命名约定未定** | 弹窗 chips 能否播放 | 方案 §4 问题 12 建议 `ai.mp3` / `ai1.mp3`…`ai4.mp3`；**测试库实际是每条目显式 `audio_url` + 共享 `tone0-4.mp3`**，两者不一致。需定一种并让前端写死推导规则 |
| 4 | **「共N个」是写死文案还是 `COUNT(*)`** | 网格标题 | 方案 §4 问题 6 未决。接口已同时给出 `tabs[].itemCount` 与 `blocks[].itemCount`，**两种做法都支持** |
| 5 | **韵母到底多少个** | `itemCount` 正确性 | 方案 §4 问题 6：PRD 记 24、原型标签写「共34个」、按网格数是 36。**需产品给准数** |
| 6 | **整体认读是否上第 4 个 tab** | 标签栏数量 | 方案 §4 问题 8 未决。数据层已兼容（`WHOLE_SYLLABLE`），接口按"有数据就返回"处理 |
| 7 | **`ext_json` 列无使用场景** | 表结构冗余 | 测试库全部为 `NULL`，无任何写入方。建议要么定键集、要么删列（当前接口不下发它） |
| 8 | **`audio_url` 是相对路径** | 播放可用性 | 测试库是 `audio/pinyin/b.mp3`（**无域名**）。生产必须落 MinIO 绝对 URL，否则客户端拼不出地址 |
| 9 | **`video_url` 全部为 `NULL`** | 弹窗降级 | 68 个条目各一段视频是硬成本（方案 §4 问题 10）。未就绪时前端按"封面 + 音频"降级（PRD 异常处理已允许） |
| 10 | **错误码：课程未配置 / 条目不存在** | 错误处理 | `ErrorCode` 无 404 通用项。建议补一组 `COURSE_*` 业务码（与写字课文档 §4.3 第 6 条合并处理），如 `COURSE_ITEM_NOT_FOUND(7001)` / `COURSE_NOT_CONFIGURED(7002)` |
| 11 | `course_pinyin_item` **无唯一键**，同一 tab 可重复录入同一 `letter` | 数据质量 | 数据库拦不住，**必须由管理后台在保存前做唯一性校验**（同 `category_code` 下 `letter` 唯一）。否则网格出现重复卡片、「共N个」多算 |

### 4.4 文档与实现的差异

编码前建议一并处理（按你的规矩，**未确认我不动文档**，此处只登记）：

| # | 位置 | 差异 | 建议 |
|---|---|---|---|
| 1 | 方案 §2.2 DDL 的 `course_pinyin_item.category_code` 注释 | 写的是「`INITIAL`声母 / `FINAL`韵母 / `TONE`声调」（**3 值**），但 schema 第 143 行是 **4 值**（含 `WHOLE_SYLLABLE`），枚举类 `PinyinCategoryCode` 也是 4 值 | 以 schema / 枚举为准，把 DDL 注释补上 `WHOLE_SYLLABLE整体认读音节` |
| 2 | 方案 §2.0.2 的「`category_code` —— 标签页」表格 | **只有 3 行**（`INITIAL` / `FINAL` / `TONE`），漏了 `WHOLE_SYLLABLE`；而同一份文档 §3.1 又写了「整体认读音节 16 个 → `category_code='WHOLE_SYLLABLE'`」 | 表格补第 4 行 |
| 3 | 方案 §3.1 | 写「简介页**两张卡片**」，测试库拼音课（`course_id=900`）**只有 1 个 `SECTION`**（「认识汉语拼音」） | 要么补第 2 个区块数据，要么改文档措辞 |
| 4 | 方案 §0.1 | 写拼音课详情形态是「发音教学弹窗（**视频 + 3 步提示**）」，但 `course_pinyin_item` **没有任何列能装这 3 条提示**（只有单值 `description`），§3.1 的映射表也没提它 | 三选一：① 若 3 条提示对每个字母相同 → 走前端 i18n；② 若逐字母不同 → 并入 `description`（但只有一条，装不下 3 条）；③ 确需结构化 → 加列或约定 `ext_json` 键集。**建议先向产品确认这 3 条提示是否逐字母不同** |
| 5 | 方案 §0.3 第 5 条 / §4 问题 10、12 | 「拼音课、写字课汉字的读音音频都可用 ai-service TTS **预生成**后落 MinIO」——**实际 audio_url 是相对占位路径**（`audio/pinyin/*.mp3`），音频文件尚未生成；`video_url` 全为 `NULL` | 素材未就绪是已知状态，但文档措辞应写明"当前为占位路径"，避免后人以为已就绪 |
| 6 | 方案 §1.5 URL 清单 | 漏了 `/course/catalog/version`（§2.0.4 提到了） | 补进清单（与写字课文档 §4.4 第 5 条是同一处遗漏） |
| 7 | 方案 §1.4 包结构 | 写 `dto/{request,response}/`，实际 `practice-service` 用扁平 `dto/` | 以实际代码风格为准，更新 §1.4 |
| 8 | 方案 §1.5 数据量评估 | 「拼音课 ~68 条…**一次性全量返回（几十 KB）**」——实测 14 条 3.1 KB，满量 68 条约 15 KB（三语约 30 KB） | 「几十 KB」偏保守但方向对；可改成实测值。**"不做分页"的结论不变** |
