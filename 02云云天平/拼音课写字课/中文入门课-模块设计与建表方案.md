## 0. 需求速览

### 0.1 两门课的能力对比

| 维度 | 拼音课 | 写字课 |
|---|---|---|
| 入口 | 首页 →「中文入门课」→ 拼音课卡片 | 首页 →「中文入门课」→ 写字课卡片 |
| 顶部标签栏 | 声母 / 韵母 / 声调（+整体认读音节待定） | 基本笔画 / 横起折笔 / 竖起折笔 / 竖复合 / 撇起折笔 / 独立折笔 |
| 内容粒度 | 字母条目（23 声母 + 36 韵母 + 4 声调卡 + 轻声 + 变调规则 + 16 整体认读） | 32 种笔画 + HSK1-6 汉字（每组 10 字） |
| 详情形态 | 发音教学**弹窗**（视频 + 3 步提示） | 笔画**动画弹窗**（田字格 + 逐帧动画 + 例字） |
| 交互练习 | 无（纯学习/浏览） | **有**：手写轨迹识别、笔顺判定、方向检测、吸附 |
| 进度记录 | **不做**（2026-09-17 确认） | **明确要求**：未开始/进行中/已完成，**支持跨设备同步** |
| 媒体资源 | 每字母的发音视频 + 音频 | 每笔画的动画 + 每汉字的读音音频 |

### 0.2 原型里的真实数据结构（比 PRD 示例更准）

**拼音课** —— `pinyinCourseData`（原型只有 3 个分类，**没有整体认读音节**）：
```js
initials: { label:'声母', rows: [['b','p','m','f'], …, ['y','w',null,null]], speak: { b:'bō', … } }
finals:   { label:'韵母', items: ['a','o','e','i','u','ü', … 'ong'],     speak: { a:'ā', 'ü':'ǖ', … } }
tones:    { label:'声调', items: ['ā','á','ǎ','à','a'],                  speak: { 'ā':'mā', a:'ma' } }
```
注意 `initials` 用 **rows 二维数组**（`g k h` 后是 `null` 占位），`finals`/`tones` 用一维 items —— 前者必须靠 `row_index`/`col_index` 还原排布。

> 上面是**旧版原型**的数据。最新原型截图（03–08）已扩展：声母 23 个；韵母按「单韵母 / 双韵母·鼻韵母 / 复韵母」三组铺开，共 36 格；声调页含 4 张声调卡 + 1 条轻声 + 2 条变调规则。落库以最新截图为准。

**写字课** —— 6 个数据结构：
```js
writingPracticeData  // HSK1-6 → [ [10个汉字], [10个汉字] ]  ← 原型每个等级只有 2 组（demo）
strokeCategories     // 6 个分类：key/label/fullLabel/note
strokeLibrary        // 32 种笔画：{ no, label, pinyin, symbol, category, examples }
strokeDemoPaths      // 笔画动画帧：{ heng:['M22 50 L78 50'], hengzhe:['M22 34 L72 34','M72 34 L72 78'] }
writingCharLibrary   // 汉字：{ '六': { pinyin:'liù', strokes:['M49 22 L51 28', …] } }
introReferenceSteps  // 永字八法 8 个要点（img 是 base64 PNG）
introTechniqueTips   // 书写技法提示
```

### 0.3 七个必须提前知道的现状

1. **写字课的"笔顺判定"缺关键数据**。`writingCharLibrary` 只给了每笔的 SVG 路径，**没有"这个字由哪些笔画、按什么顺序组成"的笔画 ID 序列**。而 PRD 4.5 要求「比对标准笔顺」。所以 `course_writing_char` 表**必须有 `stroke_ids` 字段**（指向 `course_writing_stroke.id`），这是原型的缺口，不是可选项。
2. **原型媒体全是占位**。拼音课视频是 base64 demo，发音靠浏览器 `speechSynthesis`；写字课的永字八法用 base64 PNG。生产必须补真实素材并落 MinIO。
3. **写字课进度要跨设备**，但原型用 `localStorage`。必须有后端进度表和接口。
4. **拼音课不做进度**（2026-09-17 确认）。原文「拼音课进度 PRD 没提，但两门课统一进度模型成本极低，建议一次做掉」的建议**作废**。进度表按写字课的两类对象设计（`CHAR` / `STROKE`）；`LETTER` / `CATEGORY` 两个枚举值保留在代码里但**暂不使用**，将来拼音若要记进度无需改表结构。
5. **`ai-service` 已有现成发音能力**：`GET /tts/pinyin?character=妈&pinyin=ma1`（讯飞 `vixy` 发音人支持 `字[=拼音声调]` 注音）。拼音课、写字课汉字的读音音频都可复用它**预生成**后落 MinIO。
6. **写字符号有增补平面字符**。32 笔里有 `𠃍`(U+200CD)、`𠃊` 等 BMP 外字符，表必须 `utf8mb4`，驱动/连接串不能退化成 utf8。
7. **排序规则会咬人**。拼音的 `ü`/`u`、`ā`/`a`，以及笔画 `pinyin` 的声调差异，在默认 `utf8mb4_unicode_ci`（重音不敏感）下会被判为**相等**，唯一键会直接拒插。相关列必须声明 `COLLATE utf8mb4_bin`。

## 1. 架构方案（修订版）

### 1.1 结论：**新建 `course-service` 微服务**

### 1.2 为什么改主意：这是一条独立的业务域

现有服务的划分逻辑是**按业务域**，不是按功能点：

| 服务 | 端口 | 业务域 |
|---|---|---|
| exam-service | 8084 | 试卷 / 题库 / 考试记录 |
| practice-service | 8087 | HSK **技能练习**（听力/阅读/口语/写作） |
| course-service | **8188** | **课程内容**（中文入门课 → 拼音课/写字课/…） |
| user-service | 8082 | 用户 |
| system-service | 8086 | 文件 / 字典 |
| ai-service | 8083 | TTS / AI 能力 |
| auth-service | 8081 | 认证 |
| manage | 8085 | 后台管理 |

判断依据：

1. **语义不同**。practice-service 是"**练**"（答题、判定、出报告）；中文入门课是"**学**"（看内容、跟写、记进度）。两者除了共用 `common`，没有一处业务耦合。
2. **未来会横向长**。"其他课程不是只有拼音课"——按上一版方案，practice-service 会陆续长出 `course/pinyin`、`course/handwriting`、`course/xxx`，把一个技能练习服务慢慢变成课程容器，这才是真的乱。
3. **命名已经要打架**。practice-service 下已存在 `com.hsktreasure.practice.writing`（HSK **写作练习**）。写字课若也放进去，就出现"两个 writing 不是一个意思"的长期认知负担。独立服务后，`com.hsktreasure.course.writing` 语义干净。
4. **成本是一次性的、且项目已有成熟模板**。7 个服务都有 Dockerfile，docker-compose/Nacos/Jenkins 链路齐全，加第 8 个是**复制既有范式**，不是探索新风险。

### 1.3 新建服务的真实成本（一次性的，约半天）

| # | 事项 | 说明 |
|---|---|---|
| 1 | Maven 模块 | 根 `pom.xml` 加 `<module>course-service</module>`，新 pom 继承 `HSK_treasure-parent`，依赖 `common` |
| 2 | 端口 | 8080-8087 已占用，**用 8188**（跳出 80xx 段，避开容器/监控类进程常占端口） |
| 3 | Nacos | 建 `course-service-prod.yml` 配置（数据源指向 `43.99.57.11:3306/xuexitest`），服务自动注册 |
| 4 | 网关路由 | ⚠️ 网关路由**不在本地 yml，在 Nacos**（`gateway/src/main/resources/application.yml` 里没有 routes）。需在 Nacos 的网关配置里加 `/course/**` → `lb://course-service` |
| 5 | Dockerfile | 复制 practice-service 的改一下 jar 名/端口 |
| 6 | docker-compose | 加 `course-service` 服务块 |
| 7 | Jenkins | 加一条流水线（与其它服务同构） |

> 顺带发现一处既有不一致：`docker-compose.yml` 里 `manage-service` 映射的是 `8087:8087`，而 `manage/src/main/resources/application.yml` 写的是 `8085`。两者对不上（可能靠 Nacos 覆盖）。**新服务不要踩 8087**，用 8188 并保持三处一致。

### 1.4 包结构

```

├── Dockerfile
└── src/main/
    ├── java/com/hsktreasure/course/

    │   │   ├── controller/  service/ + impl/  entity/
    │   │   ├── mapper/      dto/{request,response}/  vo/
    │   │   └── enums/                       CourseCode / ProgressStatus / ItemType
    │   ├── pinyin/                          ② 拼音课
    │   │   ├── controller/                  PinyinCatalogController
```

**隔离纪律**（保证"新模块不和别的功能写在一起"）：
- `course-service` **不 import** practice/exam 任何业务类，只依赖 `common`（`BaseEntity`/`Result`/`ErrorCode`）
- 三块内容 `common` / `pinyin` / `writing` 之间也**不互相 import**，各自持有一套 Mapper/Service/DTO
- 写字课只通过 `course_learning_progress` 这一张通用表与通用层交互，不反向依赖

### 1.5 URL 规范

沿用项目现有风格（`/listening`、`/reading`、`/writing` 都是**无前缀短路径**），course-service 用 `/course` 开头：

```http
GET  /course/catalog                    # 首页入口 + 课程列表（拼音课/写字课卡片）
GET  /course/pinyin/catalog             # 拼音课完整配置（标签页 + 条目，含声调页的轻声与变调规则）
GET  /course/pinyin/catalog/version     # 轻量版本探测（离线缓存比对）
GET  /course/pinyin/intro               # 拼音课简介页

GET  /course/writing/catalog            # 写字课轻量配置：32 笔画（含动画帧）+ 26 条规则，一次返回
GET  /course/writing/strokes?category=HORIZONTAL   # 按分类查笔画列表
GET  /course/writing/strokes/{id}       # 单笔画详情（动画帧 + 例字）；按主键取，与 2.0.3 一致
GET  /course/writing/chars?level=HSK1&groupNo=1    # 某组的 10 个汉字 + 逐笔路径 + 引导底图（重接口，按组拉）
GET  /course/writing/chars?ids=1001,1002,1003   # 按 id 批量取笔顺（规则页「例字演示弹窗」用；id 用英文逗号分隔）
GET  /course/writing/intro              # 写字课简介页（笔画/笔顺/永字八法）

POST /course/progress/report            # 上报学习进度（写字课：单字完成 / 笔画练习）；组通关由服务端聚合，不上报
GET  /course/progress?courseId=…        # 拉取进度（跨设备同步；支持按等级/组筛选）
```

**数据量评估**：拼音课 ~68 条（`course_pinyin_item`）+ 写字课 32 笔画 + 26 条规则（`course_writing_stroke` / `course_writing_rule`）都是**一次性全量返回**（几十 KB），不做分页。真正的大文件是视频/音频，走 MinIO + 客户端缓存。

⚠️ **唯独 `course_writing_char` 必须分包下发**。它的 `stroke_paths`（逐笔 SVG）与 `guide_svg`（`MEDIUMTEXT` 引导底图）单字就是几十 KB，若跟着 catalog 一起返回，接口会从几十 KB 涨到几 MB。所以：

- `GET /course/writing/catalog` —— **只含笔画与规则**，绝不含汉字笔顺数据
- `GET /course/writing/chars?level=HSK1&groupNo=1` —— **按组**下发，一次 10 个字
- `GET /course/writing/chars?ids=1001,1002,1003` —— **按 id 批量**取笔顺，供规则页「例字演示弹窗」使用。例字来自 `course_writing_rule.example_char_ids`（指向 `course_writing_char.id`），前端把该行的 id 数组一次请求取回全部例字
- 前端把字包按组缓存进 IndexedDB，`course.data_version` 变化即全量失效重拉（该列的语义与维护规则见 2.0.4）；练习页只拉当前这一组

### 1.6 管理端（配置 CRUD）放哪

**`manage` 模块**（方案 A，与现状一致）。manage 现在就是内容管理、Excel 导入、MinIO 上传的所在地，且它**本来就重复定义**了一份 `Question`/`ExamPaper` 实体——跨服务复制实体是这个项目的既有做法，不引入新坏味道。

管理端接口建议 `/api/manage/course/**`，功能：
- 课程/入口/简介配置
- 拼音条目 CRUD + Excel 批量导入
- 笔画/汉字 CRUD + 批量导入
- **「一键生成音频」**：调 ai-service TTS 回填 `audio_url`
- 媒体上传到 MinIO 回填 URL

## 2. 数据库表结构

### 2.0 全局约定

- 库：**`xuexitest`**（与其它服务共用同一个库，不做独立库）
- 主键 `id BIGINT NOT NULL`，应用层雪花 ID（`IdType.ASSIGN_ID`）
- 审计：`deleted INT DEFAULT 0`、`created_by`/`update_by` BIGINT、`created_time`/`updated_time` **BIGINT 毫秒**
- `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4`，每列每表都有 `COMMENT`
- 建表脚本路径：`course-service/src/main/resources/db/course-init/00-schema.sql`

#### 2.0.1 多语言字段规范（已定：分列，不用 JSON）

命名规则：**`主字段 + _en / _vi`**。与项目现有惯例一致（`practice_init.sql` 的 `content_name_en`、`type_name_en`、`ability_description_en/_vi`）。

| 表 | 多语言列 | 列数 |
|---|---|---|
| `course` | `name_en` / `name_vi`、`subtitle_en` / `subtitle_vi` | 4 |
| `course_home_entry` | `title_en` / `title_vi`、`subtitle_en` / `subtitle_vi` | 4 |
| `course_intro_section` | `tag_en` / `tag_vi`、`title_en` / `title_vi`、`content_en` / `content_vi` | 6 |
| `course_pinyin_item` | `description_en` / `description_vi` | 2 |
| `course_writing_stroke` | `name_en` / `name_vi` | 2 |
| `course_writing_rule` | `title_en` / `title_vi`、`description_en` / `description_vi` | 4 |

> `course_writing_rule` 的标签文案（`tags`）不在这张表里 —— 它已合成一列 JSON，多语言写在数组项内（`text` / `textEn` / `textVi`），见 2.0.2。

共 6 张表 / 22 列。`_en`、`_vi` 列长度统一比主列宽一档（英文/越南语的字符数通常多于中文），是有意为之。**文案类多语言列允许为空，表示"未翻译"，前端回退中文**——若设 `NOT NULL`，译文没跟上时就无法录入数据。

> tab 标题「声母 / 韵母 / 声调」、分组标题「单韵母 / 双韵母·鼻韵母 / 复韵母」、「一声 / 二声」标签、调型名「阴平 / 阳平 / 上声 / 去声」、笔画分类名「横起折笔」、规则区块标题「基本笔顺规则」**不走多语言列**，走前端 i18n 字典——它们都是封闭枚举的映射文案，见 2.0.2。

**有意不加多语言列的字段**（不是遗漏）：

- `course_writing_char.hanzi` / `course_writing_char.pinyin` —— 汉字与读音本身不翻译，多语言只是界面语言不同
- `course_writing_stroke.examples` / `course_writing_rule.examples`——例字是汉字，同上；`example_char_ids` 是 id 数组，更不需要翻译
- 所有 `code` / 枚举列（`category_code`、`node_type`、`rule_type`、`tone_name`、`tags[].style` / `tags[].position`）—— 封闭集合，文案在前端字典或前端主题，**不翻译**，所以不需要 `_en` / `_vi`
- `course_writing_rule.tags` —— 标签文案是**运营手填的自由文本**（不是枚举），译文随数组项一起写在同一列内（`textEn` / `textVi`），因此表上不需要独立的 `tag_en` / `tag_vi` 列

**不采用 JSON 单列的原因**：① 项目已有分列先例；② 分列可直接建索引，后台按名称排序/搜索零成本，JSON 要 `JSON_EXTRACT` + 生成列 + 索引；③ MyBatis-Plus 零配置映射成 `String`，JSON 需 `JacksonTypeHandler`；④ Excel 导入/后台表单一列对一字段；⑤ MySQL 的 JSON 列**不支持 DEFAULT 值**。

> **例外：`course_writing_rule.tags` 用一列 JSON，上面五条都不适用。** 它不是「同一段文案的三语拷贝」，而是「**N 条各自独立的标签**，每条自带文案 + 样式 + 位置」——拆成 `tag` / `tag_en` / `tag_vi` / `tag_style` / `tag_position` 五列后，全靠**下标手工配对**，任一列漏填或顺序错位就整体错乱；而且标签文案是**自由文本、可能自带逗号**（「先外框，再内部」），字符串型逗号分隔的多值列直接不成立。合成对象数组后，「哪条文案配哪个样式、放哪个位置」在一条记录内自洽，列数还净减 3。上面五条的适用前提（要建索引/排序、单值映射、可逐行导入）对标签都不成立——标签不查询、不排序、不参与 Excel 导入。

> `course_intro_section` 的 `title` / `content` / `tag` 已确认入库并配 `_en` / `_vi`（见该表 DDL），不再属于"待定"。

#### 2.0.2 枚举值规范（code 列统一存英文枚举，不存中文）

**原则**：**封闭集合存枚举 + 前端 i18n 字典；自由文本才存 `description` + `_en` / `_vi`。**

code 列一律用 `VARCHAR` 而非 MySQL `ENUM` 类型（加值免 `ALTER`），值统一**全大写英文**，与既有 `node_type`（SECTION/ENTRY）、`display_style`（TEXT_LIST/STEP_GRID）、`item_type`（CHAR/STROKE/LETTER/CATEGORY）同风格。

**`course_pinyin_item.category_code` —— 标签页**

| 枚举值 | 中文 | 说明 |
|---|---|---|
| `INITIAL` | 声母 | 23 个，一个扁平网格 |
| `FINAL` | 韵母 | 分三组 |
| `TONE` | 声调 | 声调卡 + 轻声条 + 变调规则 |

**`course_pinyin_item.node_type` —— 行类型 / 区块（同时决定渲染形态与分组）**

| 枚举值 | 中文 | 渲染形态 |
|---|---|---|
| `PHONEME` | 声母 / 整体认读的音素卡 | 网格卡（不分组） |
| `SIMPLE_FINAL` | 单韵母 | 网格卡 + 组标题 |
| `DOUBLE_NASAL_FINAL` | 双韵母·鼻韵母 | 网格卡 + 组标题 |
| `COMPOUND_FINAL` | 复韵母 | 网格卡 + 组标题 |
| `TONE` | 声调卡 | 卡片 |

**为什么这些文案不入库**：tab 标题、分组标题、「一声 / 二声」红标签、调型名「阴平 / 阳平 / 上声 / 去声」都是上面枚举的 i18n 映射（中/英/越三套在前端字典维护），加一门语言只改前端、不动表。此前 `course_pinyin_category` 删除后「tab 标题无处安放」的问题由此消失。

**`node_type` 为什么可以合并掉 `item_type` 和 `group_code`**：两列在同一行**永远不会同时有信息量**——`item_type` 有值时 `group_code` 必为空（TONE/NEUTRAL/SANDHI）；`group_code` 有值时 `item_type` 恒为 `PHONEME`（常量，无信息量）。故并为一列 `node_type`。代价是列语义从「韵母分组」升格为「行类型/区块」；若未来出现「同一分组内两种卡片形态」这类正交需求，需拆回两列并做数据迁移（当前 6 类内容无此需求）。

⚠️ **`category_code` 不能并入 `node_type`**：`node_type='PHONEME'` 同时出现在声母页与整体认读页，只看 `node_type` 判断不出进哪个 tab，tab 维度必须独立保留。

**`course_writing_rule.group_code` —— 分组键（显式，非空）**

一条规则若在原型里被拆成多个子块（如「半包围结构」按包围方向分三情况），就**拆成多行**，这些行共享同一个 `group_code`：

| 行 | `group_code` | `title` | `sort_order` | 例字 |
|---|---|---|---|---|
| 半包围·左上包围 | `'405'` | 半包围结构 | 1 | 厅,房,居,厌 |
| 半包围·右上包围 | `'405'` | 半包围结构 | 2 | 句,包,载 |
| 半包围·左下包围 | `'405'` | 半包围结构 | 3 | 远,这,建,延 |
| 全包围结构 | `'408'` | 全包围结构 | 4 | 国,园,田 |

- **每行都填值**：多行组填「组内首行的 `id`」（半包围三行都填 `'405'`，**首行也填自己的 `id`**），**单行规则填自身 `id`**。于是**每行都有值、且天然唯一** —— 单行规则的分组键就是它自己的主键，不可能与别人撞。所以列保持 `NOT NULL`，也不存在「没有分组」这个需要特判的值：前端拿到的永远是一个非空且唯一的分组键，只做「按它合并」一件事。
- **为什么不用「单行留 `NULL`」表达「独立成卡」**（评估过、已弃用）：`NULL` 语义上确实能表达「无组」，但 ① 列要改成可空，而 `NULL` 前端用不了，仍得靠服务端回填成 `id`，等于绕一圈才拿到本来就有值的东西；② 更麻烦的是写 SQL 时 `GROUP BY group_code` / `COUNT(DISTINCT group_code)` 会把所有 `NULL` 归成**同一组** —— 一次手滑就把全部单行规则粘成一张卡，是隐蔽且不会报错的坑。而「引用一个已经唯一的值」不增加任何决策负担。
- **为什么不用 `parent_id` 自引用**：自引用必须有一个父行，「半包围」会变成「1 个组头 + 3 个子块」共 4 行，而需求是 3 行平铺；`group_code` 没有父行概念，更贴合。
- **为什么不让 `title` 兼作分组键**：`title` 是显示文案、还带 `title_en` / `title_vi` 三份，改一个字或漏抄一份翻译，一组就会裂成两张卡片。分组键必须是稳定码。
- **`group_code` 不是外键**（值虽是 id 的字符串形式，但不建约束、不做 join），因此不归 2.0.3「关联一律用主键 id」管。**列保持 `VARCHAR(32)`，不改 `BIGINT`** —— 它同时是出参字段（`WritingRuleRowResponse.groupCode`），改类型会让 JSON 从 string 变 number，前端合并逻辑要跟着调；主键最大 950 / 雪花 19 位，`VARCHAR(32)` 都够。
- **删首行不破坏分组**：分组只是「值相等」，不建外键，405 删了，406/407 仍共享 `'405'`，照样合并成一张卡。

**`course_writing_rule.tags` —— 卡片标签（JSON 数组：自由文本、不限数量）**

标签文案**由运营手填**，不再走「枚举 + 前端字典」——因为同一张卡片上要挂的东西（「半包围」「厂·广·尸」「按包围方向分三情况」）语义各异、随时会改，做成枚举就要不断加值、每次都要发版。每项是一个对象：

```json
[
  {"text":"半包围","textEn":"semi-enclosed","textVi":"nua bao","style":"BADGE","position":"CARD_CORNER"},
  {"text":"按包围方向分三情况","style":"HINT","position":"TITLE_RIGHT"},
  {"text":"厂·广·尸","style":"HINT","position":"DESCRIPTION_LEFT"}
]
```

| 键 | 必填 | 说明 |
|---|---|---|
| `text` | 是 | 标签文案（中文），同时是其他语言的回退值 |
| `textEn` / `textVi` | 否 | 英文 / 越南语文案，空则回退 `text`（与 `description_en` 同一手法） |
| `style` | 否 | 取值见下，缺省 `PLAIN` |
| `position` | 是 | 摆放位置，取值见下 |

**取舍**：无标签时整列留 `NULL`，不写 `[]`；**数组顺序 = 同一位置内多个标签的渲染顺序**；数组长度不限（原来「最多两个值」的限制取消）。

**`tags[].style` —— 标签样式（3 值，前端主题映射到具体色值）**

| 枚举值 | 中文 | 外观 | 原型用例 |
|---|---|---|---|
| `BADGE` | 圆角标签 | 带底色的胶囊形 | 「半包围」「高频易错」「极易错」 |
| `HINT` | 灰色提示字 | 无底色小字 | 「厂·广·尸」「按包围方向分三情况」 |
| `PLAIN` | 普通正文 | 与说明同字号同色 | 子块标题「左上包围」「右上包围」 |

**`tags[].position` —— 标签位置（7 值）**

| 枚举值 | 锚点 | 渲染位置 |
|---|---|---|
| `RULE_TYPE_LEFT` | 区块标题 | 区块标题左侧 |
| `RULE_TYPE_RIGHT` | 区块标题 | 区块标题右侧 |
| `TITLE_LEFT` | 规则名 | 规则名左侧，同一行 |
| `TITLE_RIGHT` | 规则名 | 规则名右侧，同一行 |
| `DESCRIPTION_LEFT` | 说明 | 说明左侧 |
| `DESCRIPTION_RIGHT` | 说明 | 说明右侧 |
| `CARD_CORNER` | 卡片 | 卡片右上角（「高频易错」用） |

三个锚点**只有左右两位，没有上下位**（原 `TITLE_ABOVE` 已删除）。

**多行合并后，标签怎么归位**（「半包围」这类拆行卡片）

1. **行级**（`DESCRIPTION_LEFT` / `DESCRIPTION_RIGHT`）：各子行写自己的，渲染在该子块里。
2. **卡片级**（`TITLE_LEFT` / `TITLE_RIGHT` / `CARD_CORNER`）：只取组内 `sort_order` 最小那一行的值——写多行会重复渲染。
3. **区块级**（`RULE_TYPE_LEFT` / `RULE_TYPE_RIGHT`）：`rule_type` 是**区块级**、不是行级，一个区块横跨多行甚至多组，因此**只取该区块 `sort_order` 最小那一行的值**，每个区块渲染一次。区块级标签落在这张表的首行上（没有为它单独建表/建列，见 3.2）。

> **为什么位置和样式都要落库**：标签文案改成自由文本后，「哪个是红底标签、哪个是灰色提示字」「贴在标题右还是说明左」在数据里没有任何可派生的线索。样式若走前端字典，键是什么？文案一改就失配——所以 `style` 与 `position` 必须跟文案一起存。

> ### ⚠️ 两个必须遵守的字符集约定
> 1. **重音敏感列一律 `COLLATE utf8mb4_bin`**：`course_pinyin_item.letter`、`course_writing_stroke.pinyin`/`symbol`、`course_writing_char.hanzi`/`pinyin`。默认 `utf8mb4_unicode_ci` 是重音不敏感，`u`≡`ü`、`a`≡`ā`，会导致判等、去重、`GROUP BY`、排序全部失真（若这类列将来加唯一键，还会把 `u` / `ü` 判成重复直接拒插）。
> 2. **增补平面字符**：笔画符号 `𠃍` / `𠃊` 等属 BMP 外，要求表、连接串全程 `utf8mb4`（jdbc url 已带 `characterEncoding=UTF-8`，不要改成 utf8）。

#### 2.0.3 关联规范：一律用主键 id（硬规范）

**内容表之间的引用，一律存被引用行的主键 `id`，不存业务编码、不存名称、不存汉字。** 全库引用点如下，无例外：

| 引用语义 | 引用列（为准） | 指向 | 人读副本 |
|---|---|---|---|
| 例字 | `course_writing_stroke.example_char_ids`、`course_writing_rule.example_char_ids` | `course_writing_char.id` | `examples`（汉字串） |
| 汉字的标准笔顺 | `course_writing_char.stroke_ids` | `course_writing_stroke.id` | 无（按 id 联表即得 `code`/`name`） |
| 学习进度对象 | `course_learning_progress.item_id` | 按 `item_type` 指向 `course_writing_char.id`（`CHAR`）/ `course_writing_stroke.id`（`STROKE`）；`course_pinyin_item.id`（`LETTER`）/ `course.id`（`CATEGORY`）**暂不使用**（拼音课已确认不做进度） | `item_key`（汉字 / 笔画 code） |
| 简介页两级结构 | `course_intro_section.parent_id` | `course_intro_section.id`（自引用） | 无 |
| 课程归属 | `course_intro_section.course_id`、`course_home_entry.course_id` | `course.id` | 无 |

三条配套约定：

1. **业务键与名称降级为人读副本**（`examples` / `item_key` / `code` / `hanzi`）——仅用于查库、导出、Excel 导入时对号，**不参与关联、不作为查询依据**，一律由后端保存时按 `id` 回填；两者不一致以 `id` 为准并报警。
2. **多值引用用 JSON 数组**（`example_char_ids` / `stroke_ids`），值为 BIGINT；无引用时留 `NULL`，不写 `[]`。
3. **保存时校验引用命中**：数组里每个 `id` 必须在目标表存在；同时校验「引用数组元素个数 = 冗余副本元素个数」。**全库仍不加外键约束**（见 2.3 索引约定），靠应用层校验兜底。
4. **没有实体就没有 id，也就不做关联、不建进度行**：笔画分类、韵母分组、汉字组这几类「分组」都不是实体（没有对应表），只以枚举 + 前端字典存在；组进度由 `CHAR` 行按 `(level, group_no)` 聚合得出，不占独立进度行（见 3.4）。

**为什么硬到底、不给进度表开口子**：进度表按业务键（汉字）存虽然能扛住内容重导入，但它会让「按 id 取内容」的链路在进度这一环断掉——前端拿到的进度要反查字符才能取笔顺，多一次解析、多一分歧义（多音字按字串无法定位）。改为 `item_id` 为准后链路全程是 id；而**重导入换 id 的风险由 `item_key` 这个副本兜住**——真的发生内容重建时，用 `item_key` ↔ 业务键回填新 `id` 即可修复，副本在这里正好派上用场。

> 代价（写清楚）：**内容表重导入必须保持主键 `id` 稳定，或配套一份「按业务键回填 `item_id`」的修复脚本**。这条要写进运维约定。

#### 2.0.4 内容版本号 `course.data_version`（离线缓存比对）

课程内容合计是 MB 量级（`course_writing_char` 的 `stroke_paths` / `guide_svg` 单字就几十 KB），客户端不可能每次打开都全量拉，必须缓存进 IndexedDB。判断「缓存还能不能用」需要一个**极轻量的信号**——只回一个数字，几百字节。

**粒度：一门课一个号**。`course` 表一行存一个 `data_version`，覆盖**该课程的全部内容**：

| 课程 | `data_version` 覆盖的内容 |
|---|---|
| 拼音课 | `course_pinyin_item` + 本课 `course_intro_section` |
| 写字课 | `course_writing_stroke` / `course_writing_rule` / `course_writing_char` + 本课 `course_intro_section` |

| 接口 | 版本号来源 |
|---|---|
| `GET /course/pinyin/catalog/version` | 拼音课 `course` 行的 `data_version` |
| `GET /course/writing/catalog/version` | 写字课 `course` 行的 `data_version` |
| `GET /course/catalog/version` | `GREATEST(启用课程的最大 data_version, course_home_entry 的最大 data_version)` |

**聚合写法（必须照此实现）**：

```sql
GREATEST(
  COALESCE((SELECT MAX(data_version) FROM course            WHERE home_id = 'BEGINNER' AND enabled = 1 AND deleted = 0), 0),
  COALESCE((SELECT MAX(data_version) FROM course_home_entry WHERE code = 'BEGINNER_COURSE' AND deleted = 0), 0)
)
```

`COALESCE(…, 0)` 兜的是**「一行都没有」**：`MAX()` 在无行时返回 `NULL`，**这与列是否 `NOT NULL` 无关**——`NOT NULL DEFAULT 0` 保护的是「行在、但值为空」（裸 SQL `UPDATE` 漏填等），保护不了「行不存在」。而 `GREATEST` 遇 `NULL` 会**整体返回 `NULL`**（MySQL 8.4.9 实测），首页版本号会直接变成 `null`。**两张表都要兜。**

**维护规则（管理端职责）**：保存上表任一张内容表的任一行后，把本课程的 `data_version` 写成当前毫秒时间戳。**只增不减**。建议在 `manage` 侧收敛为一个统一的「内容保存后 bump」切面 / 服务方法，而不是散落在每个 Controller 里手工写。

`course_home_entry` **同理，但号要独立**：保存首页入口配置（标题 / 副标题 / 配图 / 角标 / 排序 / 启用）后 bump **它自己那一行**的 `data_version`。它不属于任何一门课，**不能借用某门课的号**——借用会让改一句入口文案就误失效某门课 MB 级的内容缓存。

**为什么不取 `MAX(updated_time)` 现算**（看似零维护、不用人工 bump）：

1. **删除会把它变小**。若删掉的恰是最后修改的那一行，`MAX` 回退到更早的值——极小概率下恰好退成客户端本地存的那个数字，客户端误判「没变」，继续用旧缓存。
2. **「改了但其实没变」也推高它**。运营点开一条什么都没改就保存，`updated_time` 照样刷新，客户端白拉一次全量。

`data_version` 由人控制、只增不减，两个问题都不存在。代价是**管理端每个内容写入口都必须记得 bump**，漏一个就会出现「内容更新了但用户永远看不到」——所以 §5 落地清单把它列为强制项。

> **2026-09-17 修订：`course_home_entry` 也加这一列**（原判断为不加、改用它的 `updated_time`）。原判断与本段上面两条反对理由**自相矛盾**——其中「删除会让 `MAX` 回退」在这张表上会**恶化**：它当前只有一行（`code='BEGINNER_COURSE'`），软删即无候选行，`MAX(updated_time)` 返回 `NULL`，经 `GREATEST` 传染后首页版本号整体变 `null`。
>
> 加列的两点收益：① 版本信号收敛为同一种列，不再是「一种列 + 一个 `updated_time`」两种来源混算；② 消除**量纲耦合**——原先的 `GREATEST(data_version, updated_time)` 能成立，全靠两个来源恰好都写毫秒时间戳；若哪届把 `data_version` 改成自增序号，那一路会被静默压制（`GREATEST` 永远取更大的时间戳值），课程内容改了首页却不更新。
>
> ⚠️ 但**加列不解决软删那个场景**：`MAX()` 在无行时对任何列都返回 `NULL`，所以聚合必须带 `COALESCE`（见上方「聚合写法」）。
>
> 原判断里正确的部分保留：它**不属于任何一门课**，所以版本号要独立，**不能共用课程的**。

### 2.1 表清单（8 张）

> **表名前缀约定：课程侧的表一律 `course_` 前缀，全库零例外。**
>
> 本库（`xuexitest`）是 **course-service 与 practice-service 共库**。practice-service 的表前缀是**按业务模块**分的，不按服务分——`reading_*`（阅读练习）、`speaking_*`（口语练习）、`writing_*`（写作练习，9 张）。其中 `writing_` 已被 HSK **写作练习**整块占用，若课程侧的写字课继续用 `writing_stroke` / `writing_rule` / `writing_char`，单看表名分不清 `writing_session`（写作练习场次）和 `writing_stroke`（笔画字典）是不是一个模块。
>
> 所以加服务前缀消歧：`course_writing_*`、`course_pinyin_item`。**只改表名，不动服务内部命名**——服务名 `course-service`、网关前缀 `/course/**`、包根 `com.hsktreasure.course` 已经在 course 命名空间内，`/course/writing/strokes` 与 `course_writing_stroke` 表达的是同一条链（DB 是全局命名空间才需要前缀，服务内部不需要），所以接口路径段与包名 `pinyin` / `writing` 保持不变。

**通用课程层（4 张）**

| 1 | `course` | 课程主表（拼音课/写字课/未来课程），含入口卡片、横幅、数据版本 |

### 2.3 写字课为什么是 3 张表

按内容**形状**切，不按页面切——同形状同表，异形状异表：

| 形状 | 判据 | 表 |
|---|---|---|
| 有**图形符号** + 点开有**动画演示** | 需要 `symbol` / `animation_steps` | `course_writing_stroke` |
| **一条标题 + 一段说明 + 可选例字**，纯只读 | 需要 `title` / `examples` / `description` | `course_writing_rule` |
| 有**笔顺序列 + 逐笔路径 + 引导底图**，可能带等级/组 | 需要 `stroke_ids` / `stroke_paths` / `guide_svg` / `pinyin` / `audio_url`（`hsk_level` / `group_no` 可空） | `course_writing_char` |

`course_writing_rule` 一张表装四类内容（基本规则 8 + 特殊结构 3 + 易错字 14 + 口诀 1），因为它们**形状相同**：截图里的差别只是说明文字排在例字右边还是下面，那是前端按 `rule_type` 分支渲染的事，不该变成数据库结构差异。

**曾被考虑、最终不采用的两版**

| 方案 | 不采用的原因 |
|---|---|
| 合成 1 张 `course_writing_item`（30 列） | `course_writing_char` 的 `guide_svg`(MEDIUMTEXT) + 两个笔顺 JSON 与另外两类内容**字段零交集**；合并后 95% 的行常年背着 5 个大 NULL 列，整表体积与查询都被最重的那几行拖累 |
| 压成 2 张（汉字并入 `course_writing_rule`） | 前提是笔顺数据改由前端字库提供。**已确认跟写笔顺路径从后端拿**，所以 `course_writing_char` 必须独立成表 |

**关键约定：`course_writing_stroke` 是字典表，`course_writing_char.stroke_ids` 引用它的 `id`**

存 `[201,202]`（`course_writing_stroke.id` 数组），不存 `["heng","shu"]`。这是 2.0.3「关联一律用主键 id」的直接应用：`code` 只是导入对号与人工排查用的稳定业务键，不再是关联依据。好处是**全库引用风格统一**——例字（`example_char_ids`）、笔顺（`stroke_ids`）、进度（`item_id`）三处都是 id，前端取数链路全程无需在「id ↔ 业务键」之间来回翻译。后端据此加一道**一致性校验**：`stroke_ids` 里出现的每个 id 都必须在 `course_writing_stroke.id` 中命中，录错当场报错。

> 与之前「code 引用」相比丢掉的唯一好处是：改笔画编码不必动汉字表。实际没有影响——编码几乎不变，且改编码时本就要过一遍导入脚本；真要改，按 id 定位反而更准（code 若被误改成两条相同值，字符串引用会直接歧义）。

**索引约定**：8 张表里**只有 `course_learning_progress` 带唯一键**（理由见 2.2 DDL 末尾），其余一律只有 `PRIMARY KEY`。因此 `course_writing_stroke` / `course_writing_char` **没有唯一约束，重复录入不会被数据库拦住**，需管理后台在保存前查重——否则笔画网格与汉字格会出现重复卡片、「共N种」也会多算。

### 2.4 汉字笔顺库：一份数据供两个页面

`course_writing_char` 的定位是**全课程的汉字笔顺库**，不是练习页专用表。原因是两个页面都要「画出一个字的笔画」：

| 页面 | 入口 | 要什么 |
|---|---|---|
| 练习页 | HSK 等级 → 第 N 组 → 字格「二 八 六 十…」 | 跟写判定：`stroke_ids` + `stroke_paths` + `guide_svg` |
| 笔顺规则页 | 规则行的例字块「十 千 丰」→ 点开弹窗 | 演示：`stroke_paths`（红色笔画）+ `pinyin` + `audio_url`（喇叭） |

弹窗里只有**米字格是纯前端自绘**（虚线框、横竖中线、两条对角线，零数据）；**红色笔画、拼音、读音全部来自 `course_writing_char`**。

**引用方式：例字不存笔顺数据本身，只存指向 `course_writing_char` 的引用——`example_char_ids` 为准，`examples` 是冗余副本。**

两张带例字的表（`course_writing_stroke`、`course_writing_rule`）都成对出现这两列：

| 列 | 作用 | 谁为准 |
|---|---|---|
| `example_char_ids`（JSON，BIGINT 数组） | 机器引用：按 id 批量取笔顺、做一致性校验 | **是** |
| `examples`（英文逗号分隔的汉字串） | 人读副本：直接查库/导出能看出是哪几个字，接口下发也免 join | 否，由后端保存时按 id 回填 |

**为什么 id 为准而不是字串为准**：同一个汉字在 `course_writing_char` 里可能不止一行（多音字「行」xíng/háng 笔顺相同但读音音频不同，需拆行）。这时「十」这种字串引用会歧义，只有 id 能唯一定位到要演示的那一行。后台录入时选字即得 id，`examples` 由后端自动拼出，运营不需要手填两遍。

这与 `course_writing_char.stroke_ids` 存 `[201,202]`、进度表 `item_id` 是同一手法——只存主键引用，被引用实体的主数据留在字典表里（见 2.0.3）。好处是**重合的字只存一行**：截图中「十」既是 HSK1 第 1 组的练习字、又是「先横后竖」的例字，`course_writing_char` 里就是一条记录，练习页与规则页各自按需取用，零重复存储。

判断一个字是否进练习页，看 `hsk_level` / `group_no`：

| 场景 | `hsk_level` | `group_no` |
|---|---|---|
| 练习页的字（如 HSK1 第 1 组的「十」） | `HSK1` | `1` |
| 只被规则页例字引用（如「川」「街」） | `NULL` | `NULL` |

两列**必须同时有值或同时为空**（由管理后台校验），否则「第N组」与「已练习 X/10」会出现归属不明的字。

**由此新增的一道一致性校验**（与 `stroke_ids` ↔ `course_writing_stroke.id` 那道并列）：

> `course_writing_stroke.example_char_ids` / `course_writing_rule.example_char_ids` 里的每个 id，都必须能在 `course_writing_char.id` 中命中——否则弹窗按 id 取不到笔顺就渲染不出来。同时校验 `examples` 与 `example_char_ids` **元素个数相等**（同下标一一对应），不一致即报错。保存时校验。

### 3.4 数据示例（写字课）

> **写库时的分隔符约定**：**字符串型**多值列一律用**英文逗号**分隔，逗号前后不留空格 —— `course_writing_stroke.examples`、`course_writing_rule.examples`。**标签不在此列**：`course_writing_rule.tags` 是 JSON 对象数组——文案自由、本身可能含逗号（「先外框，再内部」），且每项还要带样式与位置，逗号分隔根本不成立。
> **结构化多值列一律 JSON 数组**（不套用上面这条）：`example_char_ids`、`stroke_ids`、`stroke_paths`、`animation_steps`、`tags` —— 它们是结构化数据（或自由文本），JSON 数组天然免歧义、可直接被 `JacksonTypeHandler` 映射。
> 不用顿号「、」的原因：它在中文正文里天然会出现（口诀「从上到下、从左到右」、易错字说明「点、点、撇、捺」），一旦当分隔符用，前端拆分就会误切；而英文逗号不会出现在这些列的取值集合里（汉字、大写英文枚举）。
> **存库值 ≠ 界面文案**：库里是 `十,千,丰`，界面上渲染成三个字格「十 千 丰」。`description` / `example_text` 这类**整段展示文案仍用中文顿号**，因为它们不参与拆分。

前端按 `group_code` 合并这三行后，渲染顺序是：

1. 区块标题「特殊结构笔顺」右侧 → `共3条`（**区块级**，取自本区块首行）
2. 卡片右上角 → `半包围`（红标签）；规则名右侧 → `按包围方向分三情况`（灰字）。这两条是**卡片级**，都只写在 `sort_order=1` 那一行
3. 三个子块各自：说明左侧 → `左上包围 厂·广·尸` / `右上包围 勹` / `左下包围 辶·廴`，右侧 → 说明文字；第 3 个子块多一个 `极易错` 红标签（**行级**，各行写各自的）
4. 「共3条」按分组键去重 = 3（三行同 `'405'`，只算一条规则），序号也只有一个

> 与原型的差异只在一处：截图里半包围的例字分组是「厅房居厌 / 句包载 / 远这建延」共 11 字，而拆分前那唯一一行只能存 4 字（`厅,屋,病,虎`）——**例字归属正是拆行的主要收益**，之前靠 `description` 装子项的做法在这里会丢掉「哪个字属于哪一组」。

> `examples` 为空的四种情况（`CHAR_TIP`、`MOTTO`），`example_char_ids` 一并留 `NULL`（不写 `[]`）——两列必须**同时为空或同时有值**。另外「国」(127) 被「先外后内再封口」与「全包围结构」两行引用，`course_writing_char` 里同样只有一行；「头」(111)、「我」(121) 与笔画表「点」「斜钩」共享同一个 id。

规则 8「点的位置区分」在原型里也有两行子项，但**仍存一条**——那两行只是同一句说明换了行，塞进同一个 `description` 即可。

**拆不拆行的判据**：

| 子项形态 | 处理 | 例子 |
|---|---|---|
| 子项只是文字分两行 | **不拆**，合进同一行的 `description` | 规则 8「点的位置区分」 |
| 子项**各自带例字**、或各自带子标题/标签 | **必须拆行** + 共享「组内首行 id」 | 半包围结构（三组各有例字，拆前只剩 4 字且归属全丢） |

两种情况下「共N条」的口径都成立，因为它按分组键去重、而不是数行。

`item_id` 按 `item_type` 指向不同表：`CHAR` → `course_writing_char.id`、`STROKE` → `course_writing_stroke.id`（`LETTER` → `course_pinyin_item.id`、`CATEGORY` → `course.id` **暂不使用**）。`item_key` 只是给人看的副本。

`progress_detail` 的键**按 `item_type` 分**：`CHAR` 只存 `{"strokes":N}`（已完成笔画数，断点续做用，**不记 `accuracy` / `demoWatched`**——准确率不落库、演示可重复看）；`STROKE` 存 `{"viewed":bool,"practiced":bool}`（看演示 / 已练过，见 3.2）。拼音课已确认不做进度，故表中无 `LETTER` 行。

⚠️ 写入时该列是**整体覆盖**（upsert 取较新一次上报的值），前端每次上报须传**全量** detail，只传增量会把其他键冲掉。

第 3 行是「进行中」的典型：练了一半退出，下次打开从第 3 笔接着来 —— 这就是 `progress_detail` 存在的理由。

**「已练习 2/10」怎么算**

```sql
SELECT COUNT(*) FROM course_learning_progress
WHERE user_id = ? AND course_id = ? AND item_type = 'CHAR'
  AND level = 'HSK1' AND group_no = 1 AND status = 2 AND deleted = 0;
```

一个数同时决定三处 UI：字格灰/绿、「已练习 2/10」、「整组通关」徽标。**因此不建 `GROUP` 进度行**：组进度是这个 `COUNT(*)`，整组通关就是它等于 10；表里只有「某个字练到什么程度」这个事实，汇总一律现算。`GROUP` 若也建行，`item_id` 无处可指（组没有实体主键），还会让同课程下所有组撞同一个唯一键。

写入走 `POST /course/progress/report` 幂等 upsert，靠 `uk_course_progress_item (user_id, course_id, item_type, item_id)` 保证重复上报不会插出第二行。前端点完即本地着色、不等后端返回；离线先写 IndexedDB，联网后补传，服务端按「`status` 取最大、`last_visit_time` 取最新」合并。
