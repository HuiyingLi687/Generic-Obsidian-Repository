## 0. 通用约定

### 0.1 返回包装

所有接口统一返回 `com.hsktreasure.common.result.Result<T>`，**HTTP 状态码恒为 200**，业务结果看 `code`：

```json
{ "code": 200, "message": "操作成功", "data": { } }
```

- `code` = `200` 成功；非 200 见 [0.5 错误码](#05-错误码)
- `data` 为 `null` 时字段仍保留（不省略），前端判 `code` 即可
- 异常统一由 `GlobalExceptionHandler` 兜住，业务异常也返回 HTTP 200 + 错误 `code`

### 0.2 鉴权与客户端类型

沿用项目现状（`BaseController` + `X-Client-Type` 头 + JWT）：

| 场景 | 要求 |
|---|---|
| **内容类接口**（catalog / strokes / chars / intro） | **免登录可读**。内容与用户无关，不传 Token 也能返回 |
| **进度类接口**（`/course/progress/**`、`/course/writing/groups`） | **必须登录**。走 `requireAuthenticatedAppUserId(request, clientType)`，未登录抛 `BusinessException(401, "未登录或Token无效")` |

- 客户端类型头：`X-Client-Type: APP`（写字课是 App 端功能，非 APP 一律按未登录处理）
- Token 顺序：`Authorization: Bearer xxx` → `X-Access-Token` → `?token=`
- **`userId` 一律从 Token 取，绝不由前端传入**（防止刷别人的进度）

### 0.3 多语言

统一由请求头 `Accept-Language` 决定，服务端**取完译文后只回一个字符串**（与 `practice-service` 同一手法，工具类 `LanguageSupport`）：

| 头值 | 行为 |
|---|---|
| `zh` / 缺省 | 返回中文原文 |
| `en` | 返回 `*_en` 列，**为空则回退中文** |
| `vi` | 返回 `*_vi` 列，**为空则回退中文** |
| 其他（`ja`、`*` 等） | 一律回落 `zh` |

**响应里不回 `titleEn` / `titleVi` 这类并列字段**，只回本地化后的 `title`。数据库存三列、接口出一个值。

> 例外：`course_writing_rule.tags[]` 的译文跟着数组项存（`textEn` / `textVi`），服务端同样只在出参时挑一个回填到 `text`。

### 0.4 ID 序列化（2026-09-20 定稿：**不做全局 Long → String**）

**结论：本模块所有 id 一律以 JSON 数字下发 —— 不加全局 `Long → String` 序列化器，也不用字段级注解。**

**这条与初版设计相反，过程说清：** 项目其它服务的做法是把 Long 转成字符串（`practice-service/config/JacksonConfig.java` 就是这么做的），理由是**雪花 ID 是 19 位、超过 JS `Number.MAX_SAFE_INTEGER`（2^53 ≈ 9.007e15）** —— `1400000000000000123` 经 JS 解析会变成 `1400000000000000120`。

**但 course-service 的响应里不存在这个量级的数**，逐项核对过：

| 会出现在响应里的 Long | 位数 | 实际规模 |
|---|---|---|
| 8 张表的主键 `id` | 3 位 | 最大 `950`（号段 101 / 201 / 301 / 400 / 900 起） |
| `lastVisitTime`（毫秒时间戳） | 13 位 | ≈ 1.79e12 |
| `dataVersion`（毫秒时间戳） | 13 位 | ≈ 1.79e12 |

本服务唯一会带雪花 ID 的是 `userId`（19 位，如 `2079768422870163457`），但它**只从 Token 里取、不进任何响应**（`X-User-Id` 请求头 → `CurrentUser`）。所以字符串化对本服务没有收益，反而让所有 id 字段由数字变字符串、客户端每次都要多一层转换。

**因此本文所有 JSON 示例中的 id 一律写成数字**（`"id": 201`）。请求参数传字符串或数字都能被 Spring 转回 `Long`（`/course/writing/strokes/201` 与 `/course/writing/strokes/207` 等价），**响应一律是数字**。

> ⚠️ **这个结论有边界，动它之前先读这里**：
> ① 一旦某个响应开始返回 `userId`，或表主键改用雪花 ID，且客户端经 JS 解析 —— **必须重新评估**。届时用**字段级**序列化器（在字段上挂 `@JsonSerialize(using = ToStringSerializer.class)`），**不要**恢复全局规则 —— 全局会把 `lastVisitTime` / `dataVersion` 这两个毫秒时间戳一起变成字符串，客户端得为两个数单独做特殊处理，得不偿失。
> ② **别去「补」任何 Jackson 配置**：`course-service/src/main/java/com/hsktreasure/course/config/` 目前是个**空目录**（本服务不需要它）；`common/config/JacksonConfig.java` 里那个 `Long → String` 定制器**整个类体是注释掉的**（`common/src/main/java/com/hsktreasure/common/config/JacksonConfig.java:12`），所以即便 common 被组件扫描到也不生效。
> ③ `practice-service` 的 `JacksonConfig` 不属本模块，**未动**。

### 0.5 错误码

复用 `ErrorCode`，写字课不需要新增：

| code | 含义 | 触发场景 |
|---|---|---|
| `200` | 成功 | — |
| `400` | 参数错误 | `category` 不在 6 值枚举内；`level`/`groupNo` **只传一个**、与 `ids` **混传**、或**三者都不传**；`ids` **一个合法 id 都没有**；`ids` 的**合法项超过 50 个**（这几类均见 [3.2.5](#325-get-coursewritingchars) 入参表）；**路径变量不是数字**（`GET /course/writing/strokes/abc`、`/207.5`、`/207abc`）；**路径段为空白**（`GET /course/writing/strokes/%20`） |
| `401` | 未登录 / Token 无效 | 进度类接口未带 Token |
| `403` | 无权限 | `X-Client-Type` 非 `APP` |
| `404` | 资源不存在 | ① **请求路径没匹配到任何接口** —— URL 拼错（少个字母的 `/course/writing/stroke`）或多带路径段（`/course/writing/strokes/227/extra`）→ 固定文案「请求的资源不存在」；② `GET /course/writing/strokes/{id}` 的 `id` 在库中查不到 → `BusinessException(404, "笔画不存在")`（[3.2.4](#324-get-coursewritingstrokesid)）；③ `GET /course/writing/chars?ids=…` 的 id **全部**查不到 → `BusinessException(404, "汉字不存在")`（[3.2.5](#325-get-coursewritingchars)；**个别**查不到只打 warn、不报错） |
| `500` | 服务端错误 | 未预期异常 |
| `409` | 唯一键冲突 | 进度 upsert 并发落库兜底（正常不该出现） |

> 上表的 `code` **一律指响应体里的业务码**：本服务 HTTP 状态码恒为 `200`（见 [§0.1](#01-通用约定)），`404` / `409` 也不例外。
> `404` / `409` 在 `ErrorCode` 里**没有对应项**，是直接写的字面量（与 common 处理 `DuplicateKeyException` 时写 `409` 同一个做法）；是否补一组 `COURSE_*` 业务码见 [4.3](#43-待确认事项) 第 6 条。
>
> ⚠️ 另有**框架本该回 4xx、当前仍落 `500`** 的两类，**尚未处理**（不在本轮范围内）：`HttpRequestMethodNotSupportedException`（该 `405`，如对只支持 GET 的端点发 POST）、`HttpMediaTypeNotSupportedException`（该 `415`）。

业务层抛 `BusinessException` 即可，不用自己包 `Result`。

- 写字课的 `data_version` 覆盖 `course_writing_stroke` / `course_writing_rule` / `course_writing_char` + 本课 `course_intro_section`

> ④ 3.2.5 **按 id 的查询方式更正**：是 `selectList` + `IN` + `enabled` + `deleted`，**不是原先写的 `selectBatchIds`**（后者带不出那两个过滤条件，"已禁用 / 已软删"的行会被当成正常内容下发）。另：§0.5 的 `404` 行补了 chars 的「汉字不存在」，`400` 行补了 chars 的三类参数场景，附录 4.3 第 1 条（曾要求补 `JacksonConfig`）已划掉。

**缓存边界（贯穿全文的一条原则）**：

| 接口产出 | 与用户相关？ | 可缓存？ |
|---|---|---|
| 内容（笔画 / 规则 / 汉字笔顺 / 简介） | 否 | ✅ 可进 IndexedDB，靠 `dataVersion` 失效 |
| 进度（`status` / `progressDetail` / 组汇总） | **是** | ❌ 不可缓存，每次现拉 |

**这条原则是下面 `/chars` 不返回进度、`/groups` 单独存在的根本原因**——最重的那批数据（`stroke_paths` + `guide_svg`）必须保持"用户无关"，才能被安全地长期缓存。

##  1. 用户操作流程与接口对照

### 1.1 页面流转

```
首页
 └─[中文入门课] 入口卡片                     ── GET /course/catalog
     └─[写字课] 课程卡片
         ├─ 简介页                            ── GET /course/writing/intro
         │   ├─ 认识汉字书写（文字条目）
```

以「首次进入 → 看规则 → 练 HSK1 第 1 组 → 写完『十』」为例：

```
①  GET /course/catalog                          → 拿到写字课卡片（courseId=901）
②  GET /course/writing/catalog                  → 32 笔画 + 26 规则 + dataVersion
    ③  写入 IndexedDB（key: writing-catalog@{dataVersion}）
④  GET /course/writing/intro                    → 简介页两级结构
⑤  GET /course/writing/chars?ids=105,123,124    → 规则卡例字「十 千 丰」演示数据

⑩  POST /course/progress/report                 → 写完「十」：status=2, strokes=2

```

### 1.4 离线与跨设备

| 场景 | 行为 |
|---|---|
| **离线进笔画页 / 规则页** | 命中 IndexedDB，完全可用（内容已含动画帧） |
| **离线进练习页** | 组结构 + 进度读本地快照；笔顺数据命中 IndexedDB 则可用 |

### 3.1 入口层（通用）

#### 3.1.1 GET /course/catalog

##### 接口用处

App 首页的「中文入门课」聚合入口 + 课程卡片列表。写字课流程的第 1 步——为拿到写字课的 `courseId`（后续所有接口都要它）与卡片展示文案。

##### 入参

| 参数 | 位置 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| `Accept-Language` | Header | String | 否 | 内容语言，缺省 `zh` |
| `X-Client-Type` | Header | String | 否 | 本接口免登录，传了也不校验 |

无 Query 参数。

##### 返回 JSON

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "homeEntry": {
      "id": 950,
      "code": "BEGINNER_COURSE",
      "title": "中文入门课",
      "subtitle": "从零开始，学会拼音与汉字书写",
      "coverUrl": null,
      "badge": "NEW",
      "badgeEnabled": true,
      "sortOrder": 1
    },
    "courses": [
      {
        "id": 900,
        "code": "PINYIN",
        "name": "拼音课",
        "subtitle": "从声母、韵母和声调开始，学习中文发音",
        "bannerUrl": null,
        "sortOrder": 1
      },
      {
        "id": 901,
        "code": "HANDWRITING",
        "name": "写字课",
        "subtitle": "从笔画和笔顺开始，学会书写汉字",
        "bannerUrl": null,
        "sortOrder": 2
      }
    ],
    "dataVersion": 1789613781244
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `homeEntry` | Object / null | 聚合入口卡片配置，对应 `course_home_entry` 唯一一行 |
| `homeEntry.badgeEnabled` | Boolean | `badge` 文案是否展示；`false` 时前端忽略 `badge` |
| `courses[]` | Array | 启用中的课程，按 `sort_order` |
| `courses[].code` | String | `PINYIN` / `HANDWRITING`，前端据此决定点击跳哪 |
| `dataVersion` | Number | 见下方「数据流向」第 ③ 段 |

##### 业务逻辑

1. **查入口卡片**：`course_home_entry` 里 `code='BEGINNER_COURSE'`、启用且未删的那一行。正常只有一行；多于一行取 `sort_order` 最小者并打 warn 日志。
2. **查课程列表**：`course` 里 `home_id='BEGINNER'`、启用且未删的行，按 `sort_order, id` 排序。**拼音课与写字课都在里面**，前端按 `code` 分流。
3. **取文案**：`title` / `subtitle` / `name` 按 `Accept-Language` 从 `_en` / `_vi` 回退，缺了用中文（`LanguageSupport.pick`）。
4. **算版本号**：两张表各自的 `MAX(data_version)` 取较大者。任一边被改过，这个号就会变（SQL 见下方「数据流向」）。
5. **组装返回**：入口卡片查不到就返回 `null`，不报错。

##### 三层逻辑

| 层 | 类 / 方法 | 职责 |
|---|---|---|
| Controller | `common/controller/CourseCatalogController.getCatalog(HttpServletRequest)` | 取 `Accept-Language` → `LanguageSupport.resolve(request)`；调 Service；包 `Result.success`。**不含业务判断** |
| Service | `common/service/CourseCatalogService#getCatalog(String lang) → CourseCatalogResponse` | 两次查询、i18n 回退、`GREATEST` 版本计算、组装两级结构；`homeEntry` 缺失时返回 `null` 而非异常 |
| Mapper | `common/mapper/CourseHomeEntryMapper`、`common/mapper/CourseMapper` | MyBatis-Plus `selectOne` / `selectList`，条件走 `LambdaQueryWrapper`（`enabled=1`、`deleted=0`、`orderByAsc`） |

##### 涉及表

| 表 | 操作 | 用到的列 |
|---|---|---|
| `course_home_entry` | SELECT | `code` / `title`+`_en`+`_vi` / `subtitle`+`_en`+`_vi` / `cover_url` / `badge` / `badge_enabled` / `sort_order` / `enabled` / `deleted` / `data_version`（仅版本计算用，`updated_time` 已不再参与） |
| `course` | SELECT | `id` / `code` / `name`+`_en`+`_vi` / `subtitle`+`_en`+`_vi` / `banner_url` / `home_id` / `sort_order` / `enabled` / `deleted` / `data_version` |

##### 数据流向

**① 查库 → ② 加工 → ③ 组装**

```
① 查库    course_home_entry  ──selectOne ──→  入口卡片（1 行）
           course             ──selectList──→  课程卡片（N 行）

② 加工    name / title / subtitle  ──Accept-Language──→  单语文案
           course.data_version       ──┐
           （各自 MAX）                ├──GREATEST──→  dataVersion
           course_home_entry.…       ──┘

③ 组装    CourseCatalogResponse { homeEntry, courses[], dataVersion }  ──→  JSON
```

**映射对照**

| 响应字段 | 来自 | 取法 |
|---|---|---|
| `homeEntry` | `course_home_entry` 那 1 行 | 直取；`title` / `subtitle` 做语言回退 |
| `courses[]` | `course` 的 N 行 | 按 `sort_order, id` 排序；`name` / `subtitle` 做语言回退 |
| `dataVersion` | 两张表的 `data_version` | `GREATEST(两边 MAX)`，见下方 SQL |

**版本号 SQL**

```sql
GREATEST(
  COALESCE((SELECT MAX(data_version) FROM course            WHERE home_id='BEGINNER' AND enabled=1 AND deleted=0), 0),
  COALESCE((SELECT MAX(data_version) FROM course_home_entry WHERE code='BEGINNER_COURSE' AND deleted=0), 0)
)
```

> ⚠️ **`COALESCE(…, 0)` 不能省**：`MAX()` 在「一行都没有」时返回 `NULL`（**与列是否 `NOT NULL` 无关**），而 `GREATEST` 遇 `NULL` 会整体返回 `NULL` → 首页 `dataVersion` 变成 `null`。`course_home_entry` 只有一行，软删即触发。
> ⚠️ **两个来源缺一不可**：只取课程的号 → 改入口文案 / 下架入口时号不动，客户端永远不刷新；只取入口的号 → 改课程名 / 上下架课程时同样不刷新。
> 不取 `MAX(updated_time)` 的原因见方案 §2.0.4。

#### 3.1.2 GET /course/catalog/version

##### 接口用处

首页的**极轻量**版本探测。客户端已有缓存时，先问一句"变了吗"，没变就完全不走 `/course/catalog`。响应几百字节。

##### 入参

无（无 Header、无 Query）。

##### 返回 JSON

```json
{ "code": 200, "message": "操作成功", "data": { "dataVersion": 1789613781244 } }
```

##### 业务逻辑

与 [3.1.1](#311-get-coursecatalog) 第 4 条**同一个 `GREATEST` 表达式**，只回一个 Long。

**必须与 `/course/catalog` 返回的 `dataVersion` 完全一致**——两处若用不同口径，客户端会出现"版本说没变、拉下来却发现变了"。建议抽成一个 `CourseCatalogService#resolveHomeDataVersion()` 供两处共用，而不是各写一份 SQL。

**⚠️ 客户端的比对语义：用「不相等」，不要用「大于」。**

| 写法 | 后果 |
|---|---|
| `remote !== cached` ✅ | 最坏是白拉一次 2 KB，**不会漏更新** |
| `remote > cached` ❌ | 版本号一旦降级（如聚合链路的 `COALESCE` 兜成 `0`、或历史缓存里存的是 `null`），`0 > 2` / `null > 2` 恒为 `false` → 客户端**永远**认为没变，且**不会自愈** |

「永远认为没变」的典型后果：首页入口卡片已经下架，用户端却一直渲染旧卡片。所以比对语义必须写死为**不相等**，这条要在前端约定里明确。

##### 三层逻辑

| 层 | 类 / 方法 | 职责 |
|---|---|---|
| Controller | `CourseCatalogController.getCatalogVersion()` | 直接转发，无逻辑 |
| Service | `CourseCatalogService#resolveHomeDataVersion() → Long` | 唯一的版本计算入口（与 3.1.1 共用） |
| Mapper | `CourseHomeEntryMapper`、`CourseMapper` | 两个聚合查询 |

##### 涉及表

| 表 | 操作 | 用到的列 |
|---|---|---|
| `course` | SELECT MAX | `data_version`、`home_id`、`enabled`、`deleted` |
| `course_home_entry` | SELECT MAX | `data_version`、`code`、`deleted` |

##### 数据流向

**① 查库 → ② 加工 → ③ 组装**

```
① 查库    course             ──SELECT MAX(data_version)──→  课程侧最大号
           course_home_entry  ──SELECT MAX(data_version)──→  入口侧最大号

② 加工    课程侧号  ──┐
           （各自 MAX）├──GREATEST(COALESCE(.,0), COALESCE(.,0))──→  一个号
           入口侧号  ──┘

③ 组装    DataVersionResponse { dataVersion }  ──→  JSON
```

**映射对照**

| 响应字段 | 来自 | 取法 |
|---|---|---|
| `dataVersion` | `course` + `course_home_entry` 各自的 `data_version` | 两侧先 `MAX`，再 `GREATEST`；与 3.1.1 第 4 条**同一个表达式、同一个方法** |

**版本号 SQL**

```sql
GREATEST(
  COALESCE((SELECT MAX(data_version) FROM course            WHERE home_id='BEGINNER' AND enabled=1 AND deleted=0), 0),
  COALESCE((SELECT MAX(data_version) FROM course_home_entry WHERE code='BEGINNER_COURSE' AND deleted=0), 0)
)
```

> ⚠️ **必须抽成 `CourseCatalogService#resolveHomeDataVersion()` 与 3.1.1 共用**，不要各写一份 —— 两处口径一旦漂移，客户端就会"版本说没变、拉下来却发现变了"。
> ⚠️ `COALESCE(…, 0)` 不能省（`MAX()` 无行返回 `NULL`，`GREATEST` 遇 `NULL` 整体返 `NULL`）；两个来源缺一不可。理由见 3.1.1 的同名小节。

### 3.2 写字课内容

#### 3.2.1 GET /course/writing/catalog

##### 接口用处

**写字课最重要、最重的配置接口**，一次返回两块内容：

- **笔画类型页的全部数据**：6 个分类 + 32 种笔画（含动画帧、例字、例字 id）
- **笔顺规则页的全部数据**：4 个区块 + 26 条规则（28 行，含标签、例字）

返回后整体写入 IndexedDB，靠 `dataVersion` 失效。**这是"进笔画页 / 规则页只需一个请求"的原因。**

##### 业务逻辑

1. **定位课程**：`SELECT id, name, subtitle, banner_url, data_version FROM course WHERE code='HANDWRITING' AND enabled=1 AND deleted=0`。查不到 → `BusinessException(500, "写字课未配置")`。**不接收前端传的 `courseId`**。
2. **查笔画**：`SELECT * FROM course_writing_stroke WHERE enabled=1 AND deleted=0 ORDER BY category_code, sort_order, id`。在 Java 侧按 `category_code` 分组、补齐 6 个枚举分类（**某分类一条都没有时仍返回空数组**，保证前端 tab 恒定 6 个）。
3. **查规则**：`SELECT * FROM course_writing_rule WHERE enabled=1 AND deleted=0 ORDER BY rule_type, sort_order, id`。按 `rule_type` 分组，补齐 4 个枚举区块；**区块内保持行的原始顺序，不按 `group_code` 折叠**。
4. **取分组键、算条数**：库里 `group_code` 存「本组首行的 `id`」，**单行规则存自身 `id`**，全表非空。逐行取该值写进 `WritingRuleRowResponse.groupCode`（**出参永不为空** —— 仅遇空白脏值时才兜底成本行 `id`）；再 `cardCount = rows.stream().map(<分组键>).distinct().count()`。都在 Java 侧对已加载集合做，不发聚合 SQL（数据总量仅 28 行）。
5. **i18n**：`name` / `subtitle` / 笔画的 `name` / 规则的 `title` / `description` 按语言回退；`tags[]` 逐项用 `pick(text, textEn, textVi, lang)` 回填到 `text`，**出参里不含 `textEn` / `textVi`**。
6. **`tags` 缺省值**：`style` 为 `null` / 空串时回填 `"PLAIN"`。`position` 为空属于脏数据（库约束上应为必填），打 warn 后**丢弃该标签**，不返回 `position: null` 的项（否则前端无法定位渲染位置）。
7. **`examples` 与 `exampleCharIds` 的一致性**：以 id 数组为准；两者长度不等时以 `exampleCharIds` 为准重新拼 `examples`（需 join `course_writing_char.hanzi`）并打 error 日志。**这个校验的主要防线在管理端保存时**（方案 §5 落地清单），接口层只做兜底。
8. **不做**：不加载 `course_writing_char` 的任何笔顺数据；不返回 `data_version` 之外的进度信息。

##### 三层逻辑

| 层 | 类 / 方法 | 职责 |
|---|---|---|
| Controller | `writing/controller/WritingCatalogController#getCatalog(HttpServletRequest request)` | 解析 `Accept-Language`；调 Service；包 `Result`。**不碰任何业务分支** |
| Service | `writing/service/WritingCatalogService#getCatalog(String lang) → WritingCatalogResponse` | ① 定位课程；② 两个列表查询；③ 按枚举分组并补齐空分类/空区块；④ 取 `groupCode`（空白脏值才兜底为本行 `id`）+ `cardCount` 去重计数；⑤ i18n 回退与 `tags` 规范化；⑥ 组装 `strokeSections` + `ruleSections` |
| Mapper | `writing/mapper/CourseWritingStrokeMapper`、`CourseWritingRuleMapper`、`common/mapper/CourseMapper` | 三个 `selectList`（`LambdaQueryWrapper` 带 `enabled/deleted` + `orderBy`） |

**DTO 清单**

| 类 | 说明 |
|---|---|
| `writing/dto/WritingCatalogResponse` | 顶层：课程字段 + `strokeSections` + `ruleSections` |
| `writing/dto/WritingStrokeSectionResponse` | `categoryCode` / `strokeCount` / `strokes[]` |
| `writing/dto/WritingStrokeItemResponse` | 单个笔画（catalog 内的轻量形态，不含 `audioUrl` 之外的媒体） |
| `writing/dto/WritingRuleSectionResponse` | `ruleType` / `cardCount` / `rows[]` |
| `writing/dto/WritingRuleRowResponse` | 单个规则行（`tags` 为 `List<WritingTag>`） |

> `WritingTag` 直接复用已有的 `writing/support/WritingTag`（`text` / `textEn` / `textVi` / `style` / `position`），**按语言回退后只填 `text`**。

##### 涉及表

| 表 | 操作 | 用到的列 |
|---|---|---|
| `course` | SELECT | `id` / `code` / `name`+`_en`+`_vi` / `subtitle`+`_en`+`_vi` / `banner_url` / `data_version` / `enabled` / `deleted` |
| `course_writing_stroke` | SELECT | `id` / `category_code` / `code` / `name`+`_en`+`_vi` / `pinyin` / `symbol` / `examples` / `example_char_ids` / `animation_steps` / `sort_order` |
| `course_writing_rule` | SELECT | `id` / `group_code` / `rule_type` / `title`+`_en`+`_vi` / `tags` / `examples` / `example_char_ids` / `description`+`_en`+`_vi` / `media_url` / `sort_order` |
| `course_writing_char` | SELECT（**仅兜底校验时**） | `id` / `hanzi` |

##### 数据流向

**① 查库 → ② 加工 → ③ 组装**

```
① 查库    course                ──selectOne──→  课程（1 行，取 id / 文案 / data_version）
           course_writing_stroke ──selectList──→  笔画（32 行）
           course_writing_rule   ──selectList──→  规则（28 行）

② 加工    笔画  ──按 category_code 分组──→  6 个分类（缺的补空数组）
           name  ──Accept-Language──→  单语
           规则  ──按 rule_type 分组──→  4 个区块（缺的补空数组）
           group_code ──有值──→  原值（同组=组内首行 id，单行=自身 id）
                      └──空白脏值──→  取本行 id
           ↑ 得到的分组键 ──写入 rows[].groupCode──→  出参（必非空）
           ↑ 得到的分组键 ──distinct().count()──→  cardCount
           tags  ──pick(text,textEn,textVi)──→  只留 text/style/position

③ 组装    WritingCatalogResponse { 课程字段, strokeSections[6], ruleSections[4] }  ──→  JSON
```

**映射对照**

| 响应字段 | 来自 | 取法 |
|---|---|---|
| `courseId` / `courseCode` / `name` / `subtitle` / `bannerUrl` | `course` 那 1 行 | 直取；`name` / `subtitle` 语言回退 |
| `dataVersion` | `course.data_version` | 直取（**本课自己的号**，不是首页那个聚合号） |
| `strokeSections[]` | `course_writing_stroke` | 按 `category_code` 分组，再按 `StrokeCategory` **枚举顺序**补齐到恒定 6 个 |
| `strokeSections[].strokeCount` | 同上 | 该分类条数（Java 侧 `size()`，不再发 `COUNT(*)`） |
| `strokes[]` | 同上 | 分类内按 `sort_order, id`；`name` 语言回退；JSON 列 `examples` / `example_char_ids` / `animation_steps` 直取 |
| `ruleSections[]` | `course_writing_rule` | 按 `rule_type` 分组，再按 `RuleType` **枚举顺序**补齐到恒定 4 个 |
| `ruleSections[].cardCount` | 同上 | 按分组键去重计数（**行数 ≠ 卡片数**，`STRUCT` 半包围是 3 行 1 卡） |
| `rows[].tags` | 同上 | JSON 数组 → 逐项语言回退 → 只回 `text` / `style` / `position` |
| `rows[]` | 同上 | **不折叠**：同组多行都回，前端按 `groupCode` 合并 |
| `rows[].groupCode` | 同上 | 直取 `group_code`（库中每行必有值：同组 = 组内首行 `id`、单行 = 自身 `id`）；仅遇空白脏值时补成本行 `id` —— **出参必非空白** |

**关键 SQL**

```sql
/* ① 定位课程 */
SELECT id, code, name, name_en, name_vi, subtitle, subtitle_en, subtitle_vi, banner_url, data_version
FROM course
WHERE code = 'HANDWRITING' AND enabled = 1 AND deleted = 0;

/* ② 笔画 */
SELECT * FROM course_writing_stroke
WHERE enabled = 1 AND deleted = 0
ORDER BY category_code, sort_order, id;

/* ③ 规则 */
SELECT * FROM course_writing_rule
WHERE enabled = 1 AND deleted = 0
ORDER BY rule_type, sort_order, id;
```

> ⚠️ 上面的 `ORDER BY` 只保证**组内**顺序稳定；**分类与区块之间的顺序由 Java 常量（枚举声明顺序）决定**，不能依赖 `category_code` / `rule_type` 的字典序。
> ⚠️ 本接口**不查 `course_writing_char`**（除 §业务逻辑第 7 条的兜底校验）—— 实测 10 KB，混进汉字笔顺会涨到 MB 级。

#### 3.2.2 GET /course/writing/catalog/version

##### 接口用处

写字课的离线缓存版本探测。客户端 IndexedDB 里存着上一次的 `dataVersion`，进瘦化流程前先比一次；没变就跳过 `/course/writing/catalog`。

##### 入参

无。

##### 返回 JSON

```json
{ "code": 200, "message": "操作成功", "data": { "dataVersion": 1789613781244 } }
```

##### 业务逻辑

`SELECT data_version FROM course WHERE code='HANDWRITING' AND enabled=1 AND deleted=0`。

**与 `/course/writing/catalog` 的 `dataVersion` 必须同源**，抽同一个 Service 方法。

> 注意：`data_version` 覆盖 `course_writing_stroke` / `course_writing_rule` / `course_writing_char` **和本课 `course_intro_section`**。所以简介页缓存也应挂在这个版本号上——本接口一次探测即可同时失效 catalog 与 intro 两份缓存。

##### 三层逻辑

| 层 | 类 / 方法 | 职责 |
|---|---|---|
| Controller | `WritingCatalogController#getCatalogVersion()` | 直转发 |
| Service | `WritingCatalogService#resolveDataVersion() → Long` | 唯一入口，与 3.2.1 共用 |
| Mapper | `common/mapper/CourseMapper` | 单行查询 |

##### 涉及表

| 表 | 操作 | 用到的列 |
|---|---|---|
| `course` | SELECT | `data_version` / `code` / `enabled` / `deleted` |

##### 数据流向

**① 入参 → ② 查库 → ③ 组装**

```
① 入参    无

② 查库    course  ──SELECT data_version──→  写字课自己的号

③ 组装    DataVersionResponse { dataVersion }  ──→  JSON
```

**映射对照**

| 响应字段 | 来自 | 取法 |
|---|---|---|
| `dataVersion` | `course.data_version` | 单行直取；与 3.2.1 的 `dataVersion` **必须同源**（同一个 `resolveDataVersion()`） |

**关键 SQL**

```sql
SELECT data_version FROM course
WHERE code = 'HANDWRITING' AND enabled = 1 AND deleted = 0;
```

> ⚠️ 这个号覆盖 `course_writing_stroke` / `course_writing_rule` / `course_writing_char` **以及本课 `course_intro_section`**，所以一次探测可同时失效 catalog 与 intro 两份缓存。

> ⚠️ **与 `/course/catalog/version` 不是一回事**：那个是"两门课 + 入口"的聚合号，这个是写字课单课号，**不要共用一个方法**。

##### 接口用处

按**分类**查笔画列表。用于：

- 前端切 tab 时单独刷新某个分类（不想重拉整个 catalog）
- 管理端预览某个分类
- `/course/writing/catalog` 之外需要"只要笔画、不要规则"的场景

返回**不含 `animationSteps`**（列表页只要缩略图，动画帧由 catalog 或单笔画详情提供）。

##### 入参

| 参数 | 位置 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| `category` | Query | String | **是** | 6 值枚举：`BASIC` / `HORIZONTAL` / `VERTICAL` / `VERTICAL_COMPOUND` / `LEFT_FALLING` / `INDEPENDENT`。非法值 → `400` |
| `Accept-Language` | Header | String | 否 | 语言 |

##### 返回 JSON

```json
{
  "code": 200,
```

#### 3.2.4 GET /course/writing/strokes/{id}

##### 接口用处

**单个笔画的完整详情**：动画帧 + 例字 + 例字 id。用于：

- 笔画动画弹窗的深链进入（分享链接 / 冷启动直达）
- catalog 缓存损坏时单点重试
- 管理端预览

与 catalog 里的笔画项相比，**唯一多出的是 `animationSteps`**（catalog 已含，本接口是它的独立取数路径）。

##### 入参

| 参数 | 位置 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| `id` | Path | Long | **是** | `course_writing_stroke.id`（**按主键取**，与方案 2.0.3 一致；不接受 `code`） |
| `Accept-Language` | Header | String | 否 | 语言 |

##### 返回 JSON

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "id": 207,
    "categoryCode": "HORIZONTAL",
    "code": "HZ",
    "name": "横折",
    "pinyin": "héngzhé",
    "symbol": "𠃍",
    "sortOrder": 7,
    "animationSteps": null,
    "examples": "口,日,田",
    "exampleCharIds": [118, 119, 120],
    "exampleChars": [
      { "id": 118, "hanzi": "口", "pinyin": "kǒu" },
      { "id": 119, "hanzi": "日", "pinyin": "rì" },
      { "id": 120, "hanzi": "田", "pinyin": "tián" }
    ]
  }
}
```

> **`exampleChars` 是本接口额外补的便捷字段**（catalog 里没有，因为会重复下发汉字串）。弹窗底部要显示例字字格，直接给 `hanzi` 省一次 join。若产品认为没必要，删掉即可 —— `exampleCharIds` 仍在。
>
> **`animationSteps` 当前为 `null`**（测试库该列未导入），结构见 [3.2.1](#321-get-coursewritingcatalog) 的"期望形态"。

##### 业务逻辑

1. 按 id 查 `course_writing_stroke`：`WHERE id=? AND enabled=1 AND deleted=0`。查不到 → `BusinessException(404, "笔画不存在")`。
   > `ErrorCode` 里没有 404 的通用项；写字课的"内容项不存在"统一用 `404`（新增或取 `FAILED` 皆可，建议在 `ErrorCode` 补一组 `COURSE_*` 业务码，见附录 4.3）。
2. 若 `exampleCharIds` 非空，**一次批量查询** `course_writing_char WHERE id IN (...) AND deleted=0`，拼 `exampleChars`（只取 `id` / `hanzi` / `pinyin`，**不取 `stroke_paths` / `guide_svg`** —— 那是点开例字弹窗时由 `/chars?ids=` 才拉的重数据）。
3. **顺序**：`exampleChars` 必须按 `exampleCharIds` 的**原顺序**输出，不能按查询返回顺序。用 `Map<Long, Char>` 做索引再按 id 数组顺序取。
4. i18n：`name` 回退。

##### 三层逻辑

| 层 | 类 / 方法 | 职责 |
|---|---|---|
| Controller | `WritingCatalogController#getStroke(@PathVariable Long id, HttpServletRequest request)` | 接参、解析语言、调 Service |
| Service | `WritingCatalogService#getStroke(Long id, String lang) → WritingStrokeDetailResponse` | ① 查笔画（不存在抛异常）；② 批量查例字；③ 按 id 数组顺序重排；④ i18n；⑤ 组装 |
| Mapper | `CourseWritingStrokeMapper`、`writing/mapper/CourseWritingCharMapper` | `selectById` + `selectBatchIds` |

##### 涉及表

| 表 | 操作 | 用到的列 |
|---|---|---|
| `course_writing_stroke` | SELECT | 全部读列 |
| `course_writing_char` | SELECT | `id` / `hanzi` / `pinyin` |

##### 数据流向

**① 入参 → ② 查库 → ③ 加工 → ④ 组装**

```
① 入参    id  ──主键──→  唯一入参

② 查库    course_writing_stroke  ──selectById──→  该笔画 1 行（无 → 404）
           course_writing_char    ──selectBatchIds(exampleCharIds)──→  例字 M 行
                                               （只取 id / hanzi / pinyin）

③ 加工    M 行  ──按 exampleCharIds 原顺序重排──→  exampleChars[]
           name  ──Accept-Language──→  单语

④ 组装    WritingStrokeDetailResponse { 笔画全字段, animationSteps, exampleChars[] }  ──→  JSON
```

**映射对照**

| 响应字段 | 来自 | 取法 |
|---|---|---|
| `id` / `categoryCode` / `code` / `pinyin` / `symbol` / `sortOrder` / `animationSteps` / `examples` | `course_writing_stroke` 那 1 行 | 直取 |
| `name` | 同上 | `pick(name, name_en, name_vi, lang)` |
| `exampleCharIds` | 同上 | JSON 数组列直取 |

**关键 SQL**

```sql
/* ① 主查询 */
SELECT * FROM course_writing_stroke
WHERE id = ? AND enabled = 1 AND deleted = 0;

/* ② 例字（一次批量，按 IN 查；顺序由 Java 重排保证） */
SELECT id, hanzi, pinyin FROM course_writing_char
WHERE id IN (?, ?, …) AND deleted = 0;
```

> ⚠️ **顺序必须按 `exampleCharIds` 原顺序** —— `IN` 查询的返回顺序不保证，直接回显会让例字字格错位。
> ⚠️ 例字查询**只取 3 列**：`stroke_paths` / `guide_svg` 是点开例字弹窗时才由 `/chars?ids=` 拉的重数据。

#### 3.2.5 GET /course/writing/chars

##### 接口用处

**汉字笔顺数据的唯一出口**，两种取数模式共用一个路径：

| 模式 | 参数 | 谁在用 | 含 `guideSvg` |
|---|---|---|---|
| **按组** | `level` + `groupNo` | 练习页某组的 10 个字 | ✅ 含（跟写判定要底图） |
| **按 id 批量** | `ids` | 规则页 / 笔画卡的**例字演示弹窗** | ❌ 不含（弹窗只要红色笔画） |

**这是全模块最重的接口**（~2.4 KB/字，单组 10 字 ≈ 25 KB），所以：**必须分包下发**，且**必须保持"用户无关"以便进 IndexedDB 长期缓存**。

##### 入参

| 参数 | 位置 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| `level` | Query | String | 二选一 | `HSK1`-`HSK6` |
| `groupNo` | Query | Integer | 二选一 | 组号，从 1 开始 |
| `ids` | Query | String | 二选一 | 汉字 id，**英文逗号分隔**：`ids=105,123,124`。**合法 id 最多 50 个**（超了 `400`） |
| `Accept-Language` | Header | String | 否 | 语言（本接口无多语言文案字段，仅预留） |

**参数互斥规则（必须校验）**：

| 传入 | 行为 |
|---|---|
| `level` + `groupNo` | 按组模式 |
| 只传 `level` 或只传 `groupNo` | **`400`** —— 「第N组」必须两者同时有值，只传一个会取到跨等级的同号组 |
| `ids` | 按 id 模式 |
| `ids` 与 `level`/`groupNo` 同时传 | **`400`** —— 不用"优先取某个"的隐式规则，歧义接口是 bug 温床 |
| 三者都不传 | **`400`** |
| `ids=` **空串 / 纯空白** | **不算传** —— 与「没传」同义。单独传它 → `400`「缺少必要参数」；与 `level`+`groupNo` 同传 → 按组模式 `200`。理由：空白值不携带信息，放行会让它变成一个"合法但永远查不到东西"的值（客户端拼串时多一个逗号就静默拿到空结果） |
| `ids` 有内容、但**一个合法 id 都没有**（`ids=abc`、`ids=,,`） | **`400`** —— 此时没有可降级的内容，静默回空数组会让前端以为"这些字都没数据" |
| `ids` 里**个别**项不是数字（`ids=105,abc,123`） | **跳过该项并打 warn**，其余照常返回 —— 与「id 不存在」同一处置思路（少一个字 &gt; 整窗打不开），不让一个手滑的字符毁掉整个弹窗 |
| `ids` 的**合法项超过 50 个** | **`400`**（防止一次拉爆内存与响应体）。⚠️ 计数发生在**过滤掉非法项之后**：51 个 token 里若只有 50 个是数字，依然合法 |

> **判定顺序：先判互斥、再判缺参。** 所以 `ids=abc&level=HSK1` 报的是「混传」、不是「ids 非法」—— 一次只报一个原因，避免客户端按第一条消息改完又撞第二条。
> `level` 的取值**不做枚举校验**：传 `HSK1`–`HSK6` 以外的值等同**空组**，返回 `chars: []`（与「组里没字」同一出口）。

**两种模式的字段差异（重要）**

> 📌 **示例约定**：上面两个 JSON 中，`strokePaths` 与 `guideSvg` 的值用 `…` 截断（真实值是完整的 SVG 路径 / SVG 文档），按组示例只列了 6 个字里的 2 个（`charCount` 是真实总数）。

| 字段 | 按组 | 按 id | 原因 |
|---|---|---|---|
| `level` / `groupNo` / `charCount` | ✅ | ❌ **键不出现** | 按 id 模式没有组概念 |
| `ids`（回显请求顺序） | ❌ **键不出现** | ✅ | 前端要按请求顺序渲染字格。⚠️ 回显的是**解析后的合法值序列**（已跳过非法 token），**不是原始入参串** —— `ids=105,abc,123` 回显 `[105, 123]` |
| `sortOrder` | ✅ | ❌ **键不出现** | 按 id 模式以请求顺序为准 |
| `guideSvg` | ✅ | ❌ **键不出现** | 弹窗只要红色笔画；`guideSvg` 是 `MEDIUMTEXT`，带上会让例字弹窗从 ~7 KB 涨到 ~30 KB |
| `strokePaths` | ✅ | ✅ | 弹窗红笔画 = 这个 |
| `strokeIds` / `strokeCount` | ✅ | ✅ | 跟写判定 / 断点续做 |
| `audioUrl` | ✅ | ✅ | 两种模式都可能用到（当前库里全为 `null`） |
| `videoUrl` | ✅ | ✅ | 汉字自身的内容字段，**没有模式之分**；当前库中该列全为 `NULL`（素材未就绪），**键仍在**，见下 |

> ⚠️ **`videoUrl` / `audioUrl` 为什么不像上面那两个字段一样省键？**
> 省键靠的是**字段级 `@JsonInclude(NON_NULL)`**，全文只有 `sortOrder` / `guideSvg` 挂了它 —— 它们"按 id 模式没有值"是**模式决定的**，键不出现才对。
> 而 `videoUrl` / `audioUrl` 不是模式相关字段，是汉字自身的**可空内容列**（方案 §2.3 把 `video_url` 注为「书写演示视频地址（可选）」）：**值为空是内容状态、不是模式状态**，所以两种模式下键一律保留 —— 前端不必区分"这个字没有视频"与"服务端没给我这个字段"。
> 当前测试库 51/51 行 `video_url` 皆为 `NULL`，**那是素材还没做**（方案 §4 问题 10 的已知状态），不是接口行为：一旦有视频入库，两种模式都会带出真实地址。

> **若将来弹窗也要"描红底图"**，给按 id 模式加一个可选 `withGuide=true`（缺省 `false`），**不要改成默认返回** —— 会把所有例字弹窗的流量放大 4 倍。

##### 业务逻辑

1. **参数校验**：按上表规则判定模式；互斥与缺参一律 `400`，错误信息写清"该传哪几个"。`ids` 的解析边界（空白 = 没传 / 个别非法项跳过 + warn / 一个合法项都没有 → `400` / 合法项 &gt; 50 → `400`）与**判定顺序（先互斥、后缺参）**见入参表下的两条脚注。
2. **定位课程**：查 `course` 拿写字课 id 与 `data_version`（放响应里供缓存）。
3. **按组查询**：`WHERE hsk_level=? AND group_no=? AND enabled=1 AND deleted=0 ORDER BY sort_order, id`。
   - **组内数量由文档保证是 10，但不硬校验**（示例数据只有 6 个是正常现象）；`charCount` = 实际条数。
   - 空组返回 `chars: []`，**不报错**（前端显示空态）。
4. **按 id 查询**：`WHERE id IN (?) AND enabled=1 AND deleted=0`，**然后按请求的 `ids` 顺序重排**（`IN` 查询返回顺序不保证）。
   - `IN` 的参数用**去重后**的 id —— 纯为省 SQL 参数，**不影响输出顺序**（顺序由下面按请求数组遍历决定），更**不影响"重复 id 出现两次"**；
   - 传了**不存在的 id**：**忽略该 id 并打 warn**，不做 404（例字弹窗少一个字比整窗打不开好）；
   - 若**全部** id 都不存在 → `404`「汉字不存在」。⚠️ 这与第 3 条「空组回 `chars: []`」的处置**刻意不同**：这边调用方手里有一份"这些 id 应该存在"的清单，全落空说明客户端或内容侧出了问题，必须让它暴露出来。
5. **`strokeCount`**：`strokeIds.size()`。**不做额外查询**——`JSON_LENGTH(stroke_ids)` 是 SQL 能算，但数据已在内存里。
6. **`strokeIds` 顺序不可排序、不可去重**：「二」= `[201, 201]`（两个横），**同一 id 允许重复出现**，顺序即书写顺序。任何 `distinct` 或 `sort` 都会破坏笔顺判定。
7. **`strokePaths` 与 `strokeIds` 同为下标对应**：`strokePaths[i]` 是第 `i` 笔的路径。长度不等时说明导入有问题，打 error 日志并按较短者截断（避免前端下标越界）。
8. **不做**：不返回进度（保持用户无关 → 可缓存）；不返回 `hskLevel` / `groupNo`（请求里已经有了）。
9. **`guideSvg` 原样返回**：它是完整 SVG 字符串（含 `<svg>` 标签），服务端**不做压缩也不做转义**，以字符串字段下发，前端直接 `innerHTML`。

##### 三层逻辑

| 层 | 类 / 方法 | 职责 |
|---|---|---|
| Controller | `WritingCatalogController#listChars(String level, Integer groupNo, String ids, HttpServletRequest request)` | 接 3 个可选参数原样透传；**参数模式判定放在 Service**（Controller 不写业务分支） |
| Service | `WritingCatalogService#listChars(String level, Integer groupNo, String ids) → WritingCharsResponse` | ① 模式判定与互斥校验；② `ids` 解析（逗号切分 → `Long`，非法即 `400`）；③ 查询；④ 按请求顺序重排；⑤ `strokeCount` 计算；⑥ 长度一致性校验与日志；⑦ 组装 |
| Mapper | `writing/mapper/CourseWritingCharMapper`、`common/mapper/CourseMapper` | **两种模式都是 `selectList` + Wrapper**（按组带 `hsk_level`/`group_no`，按 id 带 `IN`）。⚠️ 按 id 模式**不用 `selectBatchIds`** —— 它只能按主键取，带不出 `enabled` / `deleted` 过滤，"已禁用 / 已软删"的行会被当成正常内容下发给客户端 |

**DTO 清单**

##### 数据流向

**① 校验入参 → ② 查库 → ③ 加工 → ④ 组装**

```
① 入参    level / groupNo / ids  ──互斥校验──→  只有两种合法组合：level+groupNo，或 ids
           （只传其一 / 混传 / 全不传 → 400）

② 查库    course                 ──selectOne──→  写字课 id + data_version
           按组模式：
           course_writing_char   ──selectList(hsk_level, group_no)──→  N 行
           按 id 模式：
           course_writing_char   ──selectList(id IN + enabled + deleted)──→  M 行

③ 加工    M 行  ──按请求 ids 顺序重排──→  chars[]（按 id 模式）
           stroke_ids  ──JSON_LENGTH / size()──→  strokeCount
           stroke_paths × stroke_ids  ──长度校验──→  一致 / 截断 + error 日志

④ 组装    WritingCharsResponse { level/ids, charCount, dataVersion, chars[] }  ──→  JSON
```

**映射对照**

| 响应字段 | 来自 | 取法 |
|---|---|---|
| `level` / `groupNo` / `charCount` | 请求参数 + 查询结果 | **仅按组模式**；`charCount` = 实际条数（空组回 `[]`） |
| `ids` | 请求参数 | **仅按 id 模式**，按请求原顺序回显 |
| `dataVersion` | `course.data_version` | 直取（与 3.2.2 同源），供客户端给这批 chars 打版本 |
| `chars[].id` / `hanzi` / `pinyin` / `sortOrder` | `course_writing_char` | 直取；`sortOrder` **仅按组模式**下发 |
| `chars[].strokeIds` | 同上 | JSON 列直取，**不排序、不去重**（`二` = `[201, 201]`，顺序即书写顺序） |
| `chars[].strokeCount` | 同上 | `strokeIds.size()`，不额外查库 |
| `chars[].strokePaths` | 同上 | JSON 列直取，与 `strokeIds` **同下标对应** |
| `chars[].guideSvg` | 同上 | **仅按组模式**；完整 SVG 字符串原样返回（不压缩、不转义） |
| `chars[].audioUrl` / `videoUrl` | 同上 | 直取，**两种模式一致**（内容字段，没有模式差别）；为空时**键仍保留**（见字段差异表下的 ⚠️） |
| 进度 | — | **一律不返回** —— 本接口必须保持"用户无关"才能进 IndexedDB |

**关键 SQL**

```sql
/* ① 定位课程（取 data_version 供缓存） */
SELECT id, code, data_version FROM course
WHERE code = 'HANDWRITING' AND enabled = 1 AND deleted = 0;

/* ② 按组模式 */
SELECT * FROM course_writing_char
WHERE hsk_level = ? AND group_no = ? AND enabled = 1 AND deleted = 0
ORDER BY sort_order, id;

/* ③ 按 id 模式（顺序由 Java 按请求 ids 重排） */
SELECT * FROM course_writing_char
WHERE id IN (?, ?, …) AND enabled = 1 AND deleted = 0;
```

> ⚠️ 按 id 模式**不做去重、不做排序**：重复 id 原样保留、顺序以请求为准。
> ⚠️ 传了不存在的 id **忽略并打 warn**（例字弹窗少一个字好过整窗打不开）；**全部**不存在才 `404`。

#### 3.2.6 GET /course/writing/groups

> ⚠️ **本接口为本次新增**，设计文档 §1.5 未定义。理由与备选方案见本节末尾。

##### 接口用处

**练习页的等级落地页**：一次拿到「HSK1-6 六个等级 tab + 每个等级下的组列表 + 每组的已练习数 / 是否通关 / **已通过的字及其组内序号**」。

最后一项（`passedChars`）的用途：让**落地页本身就能画出进度**——不必先调 `/chars` 拉整组字（那是全模块最重的接口）就能标出"第 1、2 个字已完成"。进组之后再按正常流程用 `/chars` 渲染字格。

解决的是这个问题：组结构（有哪些组、每组几字）来自 `course_writing_char`，而通关状态来自 `course_learning_progress` —— **客户端拿不到任何一边的全量**（拿组结构要先拉全量 chars，那是最重的那批数据；拿进度只有自己的明细行，推不出"每组几字"）。所以必须服务端聚合。

##### 入参

| 参数 | 位置 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| `level` | Query | String | 否（**建议传**） | `HSK1`-`HSK6`。**建议前端总是传**，即按等级拉：本接口不可缓存、每次进练习页都要重拉，而用户通常只停留在一个等级 —— 传了单等级满练完约 **25 KB**，不传要返回全部 6 个等级、满量全练完约 **130 KB**。不传仍合法，留给"一次性预热所有 tab"的场景 |
| `X-Client-Type` | Header | String | **是** | 必须 `APP` |
| `Authorization` | Header | String | **是** | JWT |

##### 返回 JSON

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "courseId": 901,
    "levels": [
      {
        "level": "HSK1",
        "groupCount": 1,
        "charCount": 6,
        "practicedCount": 2,
        "groups": [
          {
            "groupNo": 1,
            "charCount": 6,
            "practicedCount": 2,
            "completed": false,
            "lastVisitTime": 1789613781244,
            "passedChars": [
              { "index": 1, "charId": 102, "hanzi": "二" },
              { "index": 2, "charId": 109, "hanzi": "八" }
            ]
          }
        ]
      }
    ]
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `levels[].level` | String | `HSK1`-`HSK6`。**只返回有字的等级**（没有字的等级前端不渲染 tab）；若要恒定 6 个 tab，前端用固定枚举兜底 |
| `levels[].groupCount` | Integer | 该等级组数 |
| `levels[].charCount` | Integer | 该等级总字数 |
| `levels[].practicedCount` | Integer | 该等级已通关字数（`status=2` 计数） |
| `groups[].groupNo` | Integer | 组号。**组标题「第N组」由前端拼**，不落库不下发 |
| `groups[].charCount` | Integer | 该组总字数（目标值，通常 10） |
| `groups[].practicedCount` | Integer | **「已练习 X/10」的 X**：该组 `status=2` 的字数 |
| `groups[].completed` | Boolean | **整组通关** = `practicedCount == charCount`。**服务端算好**，不要指望前端比大小（口径只应有一处实现） |
| `groups[].lastVisitTime` | Long / null | 该组最近一次访问时间，用于"继续上次的组" |
| `groups[].passedChars[]` | Array | **该组已通过（`status=2`）的字**，按 `index` 升序。**未通过的字不返回**（整组字表由 `/chars?level=&groupNo=` 给）。空数组 = 该组一个都没通过 |
| `groups[].passedChars[].index` | Integer | **组内序号**，1 起 = 该字在「按 `sort_order, id` 排序」后的位置。前端直接拿它定位"第几个字格"。`/chars?level=&groupNo=` 的返回顺序用的是同一个 `sort_order, id`，所以它的数组下标 + 1 与本值天然对齐 |
| `groups[].passedChars[].charId` | Long | `course_writing_char.id`，**等于进度表里的 `item_id`** |
| `groups[].passedChars[].hanzi` | String | 该字。取自 `course_writing_char.hanzi`（内容侧明细已带出，不另查） |

> ⚠️ **`index` 与库里的 `sort_order` 不是一回事，别混用**：`sort_order` 是**录入排序键**，可能跳号（如 10/20/30）或在脏数据下重复；`index` 是服务端**按排序位置重新编号的连续 1..N**，可直接用于字格定位。当前测试库 `sort_order` 恰好是 1..6 连续，两者数值相同 —— 但**实现时必须算 `index`，不要直接回显 `sort_order`**。
>
> ⚠️ `hanzi` 用内容侧的值而不是进度行的 `item_key`：`item_key` 是**写入那一刻的副本**，汉字录入修正后它不会跟着变，会显示错字。

##### 业务逻辑

1. **取 userId**：`requireAuthenticatedAppUserId(request, clientType)`，`X-Client-Type` 非 `APP` → `403`；无 Token → `401`。
2. **定位课程**：`course.code='HANDWRITING'` → `courseId=901`。
3. **组结构查询**（内容侧）——**取明细，不再 `GROUP BY`**。要给出"字的序号"就必须拿到组内**有序列表**，聚合数字里没有这个信息：
   ```sql
   SELECT id, hanzi, sort_order, hsk_level, group_no
   FROM course_writing_char
   WHERE hsk_level IS NOT NULL AND group_no IS NOT NULL
     AND enabled = 1 AND deleted = 0
   ORDER BY hsk_level, group_no, sort_order, id;
   ```
   - `hsk_level` / `group_no` **必须同时有值**才是练习字（方案 §2.4）；条件里两个 `IS NOT NULL` 是这条约束的 SQL 表达。
   - ⚠️ **只选这 5 列**。本表还有 `stroke_paths` / `guide_svg`（单字平均 2.4 KB、最大 5.4 KB），用 `SELECT *` 会把满量约 7 MB 的笔顺数据全部拉回内存 —— 而这里一个字都用不上。
   - Java 侧按 `(hsk_level, group_no)` 分组：`charCount` = 组内条数，**组内顺序即 `index` 的来源（1 起）**。满量 3000 字仅 5 列，内存与耗时都可忽略。
4. **进度明细查询**（用户侧）——同样取明细：
   ```sql
   SELECT level, group_no, item_id, status, last_visit_time
   FROM course_learning_progress
   WHERE user_id = ? AND course_id = ? AND item_type = 'CHAR'
     AND level IS NOT NULL AND group_no IS NOT NULL AND deleted = 0;
   ```
   - **已通过必须是 `status = 2`** —— `status=1`（练到一半）的行也在表里，用"该组有进度行"来数会把练一半的字算成已通过。
   - `lastVisitTime` 取该组**全部行**（含 `status=1`）的 `MAX(last_visit_time)` —— "继续上次的组"应该认最近一次进去过的组，哪怕没练完。
5. **合并**（Java 侧，**按 `item_id` 逐字匹配**）：
   - 用户侧建 `Map<itemId, ProgressRow>` 索引；
   - 遍历内容侧每组的**有序**字列表，位置即 `index`；命中 `ProgressRow` 且 `status = 2` → `practicedCount++` 并追加 `passedChars[] = { index, charId, hanzi }`；
   - 一个字都没命中 → `passedChars: []`、`practicedCount=0`、`lastVisitTime=null`、`completed=false`。
6. **排序**：`levels` 按 `HSK1…HSK6` 自然序（不是字典序，`HSK10` 不存在所以字符串序恰好也对，但**显式按枚举序排序**更稳）；`groups` 按 `groupNo` 升序。
7. **`level` 参数过滤**：内容侧加 `AND hsk_level = ?`、用户侧加 `AND level = ?`。用户侧这条尤其重要 —— 不带过滤时会把该用户**全部等级**的进度行拉回来，响应也从单等级约 25 KB 涨到满量约 130 KB。**前端建议总是传 `level`**（见上方入参表）。
8. **不做**：不返回**未通过**的字（本接口只回「序号 + 已通过的字」，整组字表由 `/chars?level=&groupNo=` 提供，不重复下发）；不返回 `dataVersion`（本接口不可缓存，版本号无意义）。

##### 与 `/course/progress` 的分工

| 接口 | 粒度 | 用途 |
|---|---|---|
| `/course/writing/groups` | **组级聚合 + 已通过字的序号** | 练习页落地页（组列表 + 计数 + 通关 + 哪几个格子已完成） |
| `/course/progress` | **行级明细** | 笔画页的 `viewed`/`practiced`；练习页单字状态校正；多设备对账 |

`groups.practicedCount` 在数值上等于对本组 `CHAR` 明细里 `status=2` 的行计数，但**由服务端统一实现**，避免前后端两套口径漂移。

两者都能回答"某个字通过了没有"，**分工的界是"要不要 `status=1` 与 `progress_detail`"**：`groups` 只回**已通过**（`status=2`）且只到"序号 + 字"，是给落地页画进度用的；`progress` 回全部状态与明细，还能用 `updatedSince` 做增量对账。

**两者唯一的交集是「`status = 2` 的字集」，这是刻意保留、不是设计失误。** 把能力摊开看：

| 信息 | `/groups` | `/progress` |
|---|---|---|
| 有哪些组、每组几字（组结构） | ✅ | — （0 进度的组在进度表里根本不存在，推不出来） |
| 组内序号 `index` | ✅ | — （进度行没有「位置」这个概念） |
| **已通过的字集（`status = 2`）** | ✅ | ✅ ← **唯一交集** |
| 断笔数（`status=1` 的 `strokes`） | — | ✅ |
| STROKE 进度（已看演示 / 已练过） | — | ✅ |
| 增量对账（`updatedSince`） | — | ✅ |

**为什么保留这个交集**：落地页的**组列表卡片要直接渲染「已完成的字」**（产品已确认），必须拿到字本身而不只是序号。若不给 `passedChars`，落地页就得为每个组各调一次 `/chars`（约 25 KB/组）才能知道格子顺序 —— 比这点冗余贵得多。

**为什么不算「两套口径」**：只有 `/groups` 做**判定**（`status=2` 才算通过、按排序位置重编号成 `index`），`/progress` 只**原样透传** `status`，不做任何判断。`status = 2 即已通过`这条规则全模块只实现一次，不会漂移。

##### 三层逻辑

| 层 | 类 / 方法 | 职责 |
|---|---|---|
| Controller | `WritingCatalogController#listGroups(String level, HttpServletRequest request, @RequestHeader("X-Client-Type") String clientType)` | 取 userId（`requireAuthenticatedAppUserId`）；调 Service |
| Service | `writing/service/WritingGroupService#listGroups(Long userId, String level) → WritingGroupsResponse` | ① 定位课程；② 查内容侧字明细并按组分；③ 查进度明细；④ 按 `item_id` 逐字匹配；⑤ 算 `index` / `passedChars` / `practicedCount` / `completed`；⑥ 按枚举序 + 组号排序 |
| Mapper | `writing/mapper/CourseWritingCharMapper#selectGroupChars`、`common/mapper/CourseLearningProgressMapper#selectProgressDetail` | 两条都是**明细查询**（条件 + `ORDER BY`），用 `LambdaQueryWrapper` 表达即可 |

> **XML 不再必需**：改成明细查询后没有 `GROUP BY` / `CASE WHEN` 了，两条都能用 Wrapper 写。内容侧那条**必须 `.select(...)` 指定那 5 列**，别用全列 `selectList`（会把 MB 级 `stroke_paths` / `guide_svg` 一起拉回来）。原先设计的 `selectGroupStructure` / `selectGroupAgg` 两个聚合语句**作废**；`resources/mapper/writing/CourseWritingCharMapper.xml` 由"必需"降为"可选"（想把列清单固定在 XML 里仍可保留）。

> `resources/mapper/course/CourseLearningProgressMapper.xml` 仍然要建 —— 但那是给 [3.3.1](#331-post-courseprogressreport) 的 upsert 用的，与本接口无关。

> ⚠️ `WritingGroupService` 属于 `writing` 包，但访问的是 `common` 的 `CourseLearningProgressMapper` —— **方向是 writing → common，符合方案 §1.4 的隔离纪律**（common 层不反向依赖 writing）。

##### 为什么新增而不是让客户端聚合

| 方案 | 评价 |
|---|---|
| **A. 新增 `/groups`（本方案）** | 服务端一次聚合，客户端一个请求拿到组列表 + 计数 + 通关 + **已通过的字及其序号**。响应在**未练习时 < 2 KB，随已通过字数线性增长**（每个已通过的字约 45 B）：**按 `level` 拉时单等级满练完约 25 KB**，不传 `level` 拿全部 6 个等级则满量约 130 KB。不可缓存，所以前端应**默认按等级拉**（每次进练习页约 25 KB，而非 130 KB）。判定口径（`status=2`）只有一处实现 |
| B. 组结构塞进 `/course/writing/catalog` | catalog 会变成"用户无关内容 + 需要 join 进度的聚合值"，**破坏它的可缓存性**（最重的缓存包不能再缓存）—— 不可接受 |
| C. 组结构进 catalog，客户端自己聚合进度 | catalog 保持可缓存 ✅，但客户端要自己实现"`status=2` 计数 = 已练习""计数等于字数 = 通关"，且需再拉一次 `/course/progress`。**口径分散到前端**，将来改口径要发版 |
| D. 不提供组列表，前端从全量 chars 推导 | 必须先拉**全部** HSK1-6 的汉字（满量约 7 MB）才能知道有哪些组 —— 完全不可接受 |

**若你认为 C 更合适**（少一个端点、catalog 加个 `levels[]` 组结构字段），说一声我改文档；代价是前端要自己实现通关判定。

##### 数据流向

**① 入参 → ② 查库（两块明细） → ③ 分组索引 → ④ 逐字匹配 → ⑤ 加工 → ⑥ 组装**

```
① 入参    X-Client-Type / Token  ──校验──→  userId（非 APP → 403，无 Token → 401）
           level（可选）  ──→  内容侧 WHERE 的一个等值条件

② 查库    course                ──selectOne──→  写字课 id
           [内容侧] course_writing_char       ──→  每组的字明细（有序，只 5 列）
           [用户侧] course_learning_progress  ──→  该用户的 CHAR 进度明细

③ 分组    内容侧明细  ──按 (hsk_level, group_no) 分组──→  每组一份有序字列表
           用户侧明细  ──按 item_id 建索引──→  Map<itemId, ProgressRow>

④ 匹配    组内逐字：位置 1..N        ──→  index
           命中且 status == 2        ──→  practicedCount++ / passedChars[] 追加
           该组全部行的 last_visit_time  ──MAX──→  lastVisitTime

⑤ 加工    practicedCount == charCount  ──→  completed
           levels  ──按 HSK 枚举序──→  排序；groups 按 groupNo 升序

⑥ 组装    WritingGroupsResponse { courseId, levels[].groups[].passedChars[] }  ──→  JSON
```

**映射对照**

| 响应字段 | 来自 | 取法 |
|---|---|---|
| `courseId` | `course` 那 1 行 | 直取（`code='HANDWRITING'` 定位） |
| `levels[].level` / `groupCount` / `charCount` | 内容侧明细 | 按 `hsk_level` 分组后统计（组数 / 总字数） |
| `groups[].groupNo` / `charCount` | 同上 | 组的天然键 + 该组字列表长度 |
| `groups[].passedChars[].index` | 内容侧明细 | 组内**排序位置**（1 起），不是 `sort_order` 直取 |
| `groups[].passedChars[].charId` | `course_writing_char.id` | 直取 |
| `groups[].passedChars[].hanzi` | `course_writing_char.hanzi` | 直取（不用进度行的 `item_key`，那是写入时的旧副本） |
| `groups[].practicedCount` | 用户侧明细 | 该组 `status = 2` 的字数（**Java 侧计数**） |
| `groups[].lastVisitTime` | 同上 | 该组**全部**行（含 `status=1`）的 `MAX(last_visit_time)` |
| `levels[].practicedCount` | 同上 | 该等级各组 `practicedCount` 之和 |
| `groups[].completed` | 两侧相合 | **服务端算**：`practicedCount == charCount` |
| `dataVersion` | — | **不下发**（本接口不可缓存，版本号无意义） |

**关键 SQL**

```sql
/* ① 内容侧：每组的字（有序；只取 5 列，绝不能用 SELECT *） */
SELECT id, hanzi, sort_order, hsk_level, group_no
FROM course_writing_char
WHERE hsk_level IS NOT NULL AND group_no IS NOT NULL
  AND enabled = 1 AND deleted = 0
ORDER BY hsk_level, group_no, sort_order, id;

/* ② 用户侧：该用户的 CHAR 进度明细 */
SELECT level, group_no, item_id, status, last_visit_time
FROM course_learning_progress
WHERE user_id = ? AND course_id = ? AND item_type = 'CHAR'
  AND level IS NOT NULL AND group_no IS NOT NULL AND deleted = 0;
```

> ⚠️ **`SELECT *` 是这里最容易犯的错** —— `course_writing_char` 带着 `stroke_paths` / `guide_svg`（单字平均 2.4 KB），满量 3000 字全列约 7 MB，而本接口一个字都用不上。**必须显式列这 5 列**。
> ⚠️ **已通过只认 `status = 2`** —— `status=1`（练到一半）的行也在表里，用"该组有进度行"来数会把练一半的字算成已通过。
> ⚠️ **`index` 要现算，不能回显 `sort_order`** —— `sort_order` 是录入排序键，可能跳号或在脏数据下重复；`index` 是排序后的连续位置。当前测试库 `sort_order` 恰好 1..6 连续、两者相等，但别依赖这个巧合。
> ⚠️ **两个 `IS NOT NULL` 不能省** —— `hsk_level` / `group_no` 是练习字专有列（方案 §2.4），缺一就不是练习字。
> ⚠️ 匹配放在 **Java 侧**（按 `item_id` 逐字匹配），不要把进度明细硬塞进内容查询 —— 后者会把"用户无关"的内容查询变成用户相关，破坏两层职责。

### 3.3 进度（通用层）

#### 3.3.1 POST /course/progress/report

##### 接口用处

**上报学习进度**——写字课进度的唯一写入口，同时承担：

1. 单字跟写完成 / 中途退出（`itemType='CHAR'`）
2. 笔画专项练习的"看过演示 / 练过"（`itemType='STROKE'`）
3. **离线补传**（断网期间攒的队列，联网后一次批量提交）

**组通关不上报**——它由服务端对 `CHAR` 行聚合得出（见 [3.2.6](#326-get-coursewritinggroups)），上报组本身没有实体主键可指。

##### 入参

**Header**

| 参数 | 必填 | 说明 |
|---|---|---|
| `X-Client-Type` | **是** | `APP` |
| `Authorization` | **是** | JWT |
| `Content-Type` | **是** | `application/json` |

**Body**

```json
{
  "courseId": 901,
  "items": [
    {
      "itemType": "CHAR",
      "itemId": 105,
      "level": "HSK1",
      "groupNo": 1,
      "status": 2,
      "progressDetail": { "strokes": 2 },
      "lastVisitTime": 1789613781244
    },
    {
      "itemType": "CHAR",
      "itemId": 140,
      "level": "HSK1",
      "groupNo": 1,
      "status": 1,
      "progressDetail": { "strokes": 2 },
      "lastVisitTime": 1789613781000
    },
    {
      "itemType": "STROKE",
      "itemId": 207,
      "status": 1,
      "progressDetail": { "viewed": true, "practiced": false },
      "lastVisitTime": 1789613780000
    }
  ]
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `courseId` | Long | **是** | 课程 id。写字课固定 `901`；**由前端传**（进度是跨课程通用表，服务端无法从 `itemId` 反推课程） |
| `items` | Array | **是** | 进度项列表，长度 1–200。**单条上报就是 1 个元素的数组** |
| `items[].itemType` | String | **是** | `CHAR` / `STROKE`（当前使用）。`LETTER` / `CATEGORY` **暂不支持**，传入 → `400` |
| `items[].itemId` | Long | **是** | 按 `itemType` 指向 `course_writing_char.id` 或 `course_writing_stroke.id` |
| `items[].level` | String | `CHAR` 必填 | `HSK1`-`HSK6`。**`STROKE` 不传** |
| `items[].groupNo` | Integer | `CHAR` 必填 | 组号。**`STROKE` 不传** |
| `items[].status` | Integer | **是** | `0` 未开始 / `1` 进行中 / `2` 已完成 |
| `items[].progressDetail` | Object | 否 | 键**按 `itemType` 分**：`CHAR` → `{"strokes": N}`；`STROKE` → `{"viewed": bool, "practiced": bool}` |
| `items[].lastVisitTime` | Long | **是** | 本次操作时间，毫秒时间戳。**合并时的"谁更新"就靠它** |
| ~~`itemKey`~~ | — | — | **不接收**。由服务端按 `itemId` 查表回填（人读副本，见方案 §2.0.3） |
| ~~`userId`~~ | — | — | **绝不接收**。从 Token 取 |

**为什么是数组而不是单个对象**：离线补传是设计里明确的一环（方案 §3.4：「离线先写 IndexedDB，联网后补传」）。单条上报走 1 元素数组，服务端只有一条 upsert 路径，不需要维护两套。

##### 返回 JSON

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "saved": 3,
    "items": [
      { "itemType": "CHAR",   "itemId": 105, "itemKey": "十", "status": 2, "progressDetail": { "strokes": 2 },               "lastVisitTime": 1789613781244 },
      { "itemType": "CHAR",   "itemId": 140, "itemKey": "六", "status": 1, "progressDetail": { "strokes": 2 },               "lastVisitTime": 1789613781000 },
      { "itemType": "STROKE", "itemId": 207, "itemKey": "HZ", "status": 1, "progressDetail": { "viewed": true, "practiced": false }, "lastVisitTime": 1789613780000 }
    ]
  }
}
```

- **返回的是合并后的最终值**（不是请求值的回显）。若某条上报被既有数据"压过"（例如本地旧数据 `status=2`、本次上报 `status=1`），返回的会是 `2`。
- 客户端拿到后**覆盖本地快照**，这样多设备场景能自然收敛。
- `saved` = 成功落库的条数（去重后的 key 数，不是请求长度）。

##### 业务逻辑

**① 参数校验**

1. `items` 非空、长度 ≤ 200。
2. `itemType` ∈ `{CHAR, STROKE}`；其他值 → `400`。
3. `CHAR` 必须有 `level` + `groupNo`，**两者同时有值**；缺一 → `400`。
4. `STROKE` 的 `level` / `groupNo` 传了也不报错，**服务端置 `null`**（保持与组聚合查询的 `IS NOT NULL` 条件一致）。
5. `status` ∈ `{0, 1, 2}`。
6. `progressDetail` 键校验（**建议但可后置**）：
   - `CHAR` → 只接受 `strokes`，值为非负整数且 ≤ 该字总笔数（`stroke_ids` 长度）
   - `STROKE` → 只接受 `viewed` / `practiced`，布尔
   - 多余键：**丢弃 + warn**，不报错（前端版本不一致时不该直接失败）
7. **同一请求内重复 key**（同 `itemType` + `itemId`）：按 `lastVisitTime` **取最新的一条**，其余丢弃。

**② 存在性校验（按 id）**

| `itemType` | 校验目标 | 失败 |
|---|---|---|
| `CHAR` | `course_writing_char.id` 命中且 `enabled=1 AND deleted=0` | `400`，消息带 `itemId` |
| `STROKE` | `course_writing_stroke.id` 命中且 `enabled=1 AND deleted=0` | `400` |

批量查一次 `IN`，不用逐条查。**这条校验是必要的**：`item_id` 是"关联一律用主键 id"的应用点，脏 id 会让进度永远对不上任何字（用户看到"练了但格子不绿"）。

**③ `itemKey` 回填**

- `CHAR` → `course_writing_char.hanzi`（如「十」）
- `STROKE` → `course_writing_stroke.code`（如 `HZ`）

从第 ② 步已经查出来的结果里取，**不额外查库**。

**④ Upsert（幂等合并）**

唯一键 `uk_course_progress_item (user_id, course_id, item_type, item_id)`，一条语句搞定：

```sql
INSERT INTO course_learning_progress
  (id, user_id, course_id, level, group_no, item_type, item_id, item_key,
   status, progress_detail, last_visit_time, deleted, created_time, updated_time)
VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, 0, ?, ?)
ON DUPLICATE KEY UPDATE
  status          = GREATEST(status, VALUES(status)),
  progress_detail = IF(VALUES(last_visit_time) >= last_visit_time,
                       VALUES(progress_detail), progress_detail),
  item_key        = VALUES(item_key),
  level           = VALUES(level),
  group_no        = VALUES(group_no),
  last_visit_time = GREATEST(COALESCE(last_visit_time, 0), VALUES(last_visit_time)),
  updated_time    = VALUES(updated_time);
```

**合并规则（三条，必须与前端约定一致）**

| 列 | 规则 | 理由 |
|---|---|---|
| `status` | **取最大** | 进度只会前进。旧设备后到的 `status=1` 不该把新设备的 `status=2` 拉回去 |
| `last_visit_time` | **取最大（最新）** | 用于"最近练到哪" |
| `progress_detail` | **整体覆盖，跟随 `last_visit_time` 更大的那次** | 见下方 ⚠️ |

⚠️ **`progress_detail` 是整体覆盖而非逐键合并**。这是方案 §3.4 的明确约定，**前端每次上报必须传全量 detail**：只传 `{"strokes":3}` 会把之前记录的键冲掉。写入逻辑用 `IF(VALUES(last_visit_time) >= last_visit_time, 新值, 旧值)` 实现"跟随较新上报"，避免乱序到达的旧报文覆盖新报文。

**⑤ 批量与事务**

- 整个 `items` 在**一个事务**里落库（`@Transactional`）。部分失败就整体回滚，避免"传了 5 条成功 2 条"的中间态让客户端对不上账。
- 逐条 upsert（200 条上限，量很小），**不做 multi-values 拼接** —— 拼接语句在 200 条时已经很长，且 `ON DUPLICATE KEY UPDATE` 的逐行语义更难保证。
- 反复重试同一次上报（弱网）**必须安全**：唯一键 + `GREATEST` 保证了幂等。

**⑥ 与前端"点完即着色、不等返回"的关系**

前端本地先着色、后台上报；本接口**不承担实时性责任**。因此：

- 接口**不需要**返回最新的全组汇总（省一次聚合查询）
- 但返回合并后的 `items`，让客户端能纠正"本地比服务端更新"这种异常（例如换设备后本地快照过期）

##### 三层逻辑

| 层 | 类 / 方法 | 职责 |
|---|---|---|
| Controller | `common/controller/CourseProgressController#report(@Valid @RequestBody ProgressReportRequest body, HttpServletRequest request, @RequestHeader("X-Client-Type") String clientType)` | 取 userId（`requireAuthenticatedAppUserId`）；`@Valid` 触发 Bean Validation；调 Service；包 `Result` |
| Service | `common/service/CourseProgressService#report(Long userId, ProgressReportRequest req) → ProgressReportResponse` | ① 参数与枚举校验；② 同请求内去重取最新；③ **批量存在性校验 + `itemKey` 回填**（按 `itemType` 分派到 `CourseWritingCharMapper` / `CourseWritingStrokeMapper`）；④ 逐条 upsert；⑤ 回读合并结果；⑥ 组装 |
| Mapper | `common/mapper/CourseLearningProgressMapper#upsertIgnore(...)`（XML 自定义，`ON DUPLICATE KEY UPDATE`）、`writing/mapper/CourseWritingCharMapper#selectIdHanziMap(ids)`、`CourseWritingStrokeMapper#selectIdCodeMap(ids)` | 见上 |

> ⚠️ **跨包依赖说明**：`CourseProgressService` 在 `common`，却要访问 `writing` 的 Mapper 来查 `itemKey` —— 这**违反方案 §1.4 的隔离纪律**（`common` 不应依赖业务包）。
>
> **推荐解法（二选一）**：
> - **A（推荐）**：把 `itemKey` 回填抽成一个**接口**放在 `common`（如 `interface ProgressItemKeyResolver { String resolve(String itemType, Long itemId); }`），`writing` 侧提供实现并注册为 Bean。`common` 只依赖接口，依赖方向仍是 writing → common
> - **B**：`common` 手里只留 `course_learning_progress` 的读写，**`itemKey` 与存在性校验由 `writing` 自己的 Service 先做**，再调 `common` 的写入方法
>
> **不要**直接在 `common` 里 `@Autowired` writing 的 Mapper —— 那会让 `common` 编译期依赖 business 包，后续加课程会越来越乱。

##### 涉及表

| 表 | 操作 | 用到的列 |
|---|---|---|
| `course_learning_progress` | **INSERT … ON DUPLICATE KEY UPDATE** | 全部写列 |
| `course_writing_char` | SELECT | `id` / `hanzi` / `stroke_ids`（笔数上限校验用）/ `enabled` / `deleted` |
| `course_writing_stroke` | SELECT | `id` / `code` / `enabled` / `deleted` |

##### 数据流向

**① 校验 → ② 查库回填 → ③ 加工 → ④ 写库 → ⑤ 回读 → ⑥ 组装**

```
① 入参    请求体 items[]  ──结构 + 枚举 + 必填项校验──→  合法项
           userId         ──从 Token 取──→  不入请求体
           itemKey        ──不由前端传──→  下一步回填

② 查库    CHAR 项   ──selectIdHanziMap(ids)──→  id → hanzi   （兼存在性校验）
           STROKE 项 ──selectIdCodeMap(ids)──→  id → code
                       （一次 IN 批量查，不逐条查）

③ 加工    (itemType, itemId)  ──同请求内取 lastVisitTime 最大者──→  去重后的写集
           itemKey  ──从第 ② 步结果取──→  回填，不额外查库

④ 写库    course_learning_progress  ──逐条 upsert（一个事务）──→  落库
                       （唯一键 uk_course_progress_item 决定插入还是更新）

⑤ 回读    写集  ──按同一批 key 查回──→  合并后的最终行

⑥ 组装    ProgressReportResponse { saved, items[] }  ──→  JSON
```

**映射对照**

| 响应字段 | 来自 | 取法 |
|---|---|---|
| `saved` | 写库结果 | 成功落库的**去重后 key 数**（不是请求长度） |
| `items[].itemType` / `itemId` | 请求项 | 原样回显 |
| `items[].itemKey` | `course_writing_char.hanzi` / `course_writing_stroke.code` | 第 ② 步已查出的结果，**不额外查库** |
| `items[].status` | `course_learning_progress` | **合并后的最终值**（`GREATEST(旧, 新)`），不是请求值 |
| `items[].progressDetail` | 同上 | 跟随 `last_visit_time` 更大的那次（**整体覆盖，非逐键合并**） |
| `items[].lastVisitTime` | 同上 | `GREATEST(旧, 新)` |

**关键 SQL**

```sql
/* ① 回填 itemKey + 存在性校验（两条，按 itemType 分派） */
SELECT id, hanzi FROM course_writing_char  WHERE id IN (?, ?, …) AND enabled = 1 AND deleted = 0;
SELECT id, code  FROM course_writing_stroke WHERE id IN (?, ?, …) AND enabled = 1 AND deleted = 0;

/* ② 逐条 upsert（XML 自定义，见下方合并规则） */
INSERT INTO course_learning_progress
  (id, user_id, course_id, level, group_no, item_type, item_id, item_key,
   status, progress_detail, last_visit_time, deleted, created_time, updated_time)
VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, 0, ?, ?)
ON DUPLICATE KEY UPDATE
  status          = GREATEST(status, VALUES(status)),
  progress_detail = IF(VALUES(last_visit_time) >= last_visit_time,
                       VALUES(progress_detail), progress_detail),
  item_key        = VALUES(item_key),
  level           = VALUES(level),
  group_no        = VALUES(group_no),
  last_visit_time = GREATEST(COALESCE(last_visit_time, 0), VALUES(last_visit_time)),
  updated_time    = VALUES(updated_time);
```

> ⚠️ **`progress_detail` 是整体覆盖**：赋值里用 `IF(新 last_visit_time >= 旧, 新值, 旧值)` 实现"跟随较新上报"，所以**前端每次必须传全量 detail**，只传 `{"strokes":3}` 会把其它键冲掉。
> ⚠️ `ON DUPLICATE KEY UPDATE` 的赋值**从左到右**执行，依赖旧值的列要写在前面（`status` 与 `progress_detail` 都用到了旧值）。
> ⚠️ 整个 `items` 在**一个事务**里落库，不做 multi-values 拼接；弱网重试靠唯一键 + `GREATEST` 保证幂等。

#### 3.3.2 GET /course/progress

##### 接口用处

**拉取进度明细**（跨设备同步、本地快照对账）。三类用法：

1. **笔画页**：拉 `itemType='STROKE'` 的全部行，得到 32 个笔画的「已看演示 / 已练过」标记
2. **练习页**：拉某组的 `CHAR` 行，渲染字格灰/绿 + "从第 3 笔继续"
3. **多设备对账**：全量拉一次覆盖本地快照

##### 入参

| 参数 | 位置 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| `courseId` | Query | Long | **是** | 课程 id（写字课 `901`） |
| `itemType` | Query | String | 否 | `CHAR` / `STROKE`。不传 = 全部 |
| `level` | Query | String | 否 | `HSK1`-`HSK6` |
| `groupNo` | Query | Integer | 否 | 组号 |
| `updatedSince` | Query | Long | 否 | 只返回 `last_visit_time >= ?` 的行，增量同步用 |
| `X-Client-Type` | Header | **是** | — | `APP` |
| `Authorization` | Header | **是** | — | JWT |

##### 返回 JSON

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "courseId": 901,
    "total": 3,
    "items": [
      { "id": 1, "itemType": "CHAR",   "itemId": 102, "itemKey": "二", "level": "HSK1", "groupNo": 1, "status": 2, "progressDetail": { "strokes": 2 }, "lastVisitTime": 1789613781244 },
      { "id": 2, "itemType": "CHAR",   "itemId": 109, "itemKey": "八", "level": "HSK1", "groupNo": 1, "status": 2, "progressDetail": { "strokes": 2 }, "lastVisitTime": 1789613781244 },
      { "id": 3, "itemType": "CHAR",   "itemId": 140, "itemKey": "六", "level": "HSK1", "groupNo": 1, "status": 1, "progressDetail": { "strokes": 2 }, "lastVisitTime": 1789613781244 }
    ]
  }
}
```

> 以上是测试库 `user_id=1001` 的**真实数据**（3 行均为 `CHAR`；「六」`status=1` 表示练到第 2 笔退出）。

| 字段 | 说明 |
|---|---|
| `items[].progressDetail` | `CHAR` → `{"strokes": N}`；`STROKE` → `{"viewed": bool, "practiced": bool}`。**未设置时为 `null`** |
| `items[].itemKey` | 人读副本（汉字 / 笔画 code），供前端调试显示 |
| `total` | 返回条数 |

##### 业务逻辑

1. **取 userId**：`requireAuthenticatedAppUserId`。
2. 查询 `course_learning_progress`：
   ```sql
   SELECT * FROM course_learning_progress
   WHERE user_id = ? AND course_id = ? AND deleted = 0
     [AND item_type = ?] [AND level = ?] [AND group_no = ?]
     [AND last_visit_time >= ?]
   ORDER BY last_visit_time DESC, id;
   ```
   - **必须带 `deleted = 0`**（逻辑删除）。漏掉会让已删除的行混进进度，`COUNT(*)` 口径也一起错
3. **不传筛选条件时全量返回该课程的行**。满量估算：写字课最多 `3000(CHAR) + 32(STROKE)` ≈ 3 千行、约 400 KB —— **可以接受但偏大**；前端应按需带 `itemType` / `level` / `groupNo`。
4. 组级汇总**不在本接口算**（那是 `/groups` 的事），本接口只回明细行。
5. 空结果返回 `items: []`，不报错。

##### 三层逻辑

| 层 | 类 / 方法 | 职责 |
|---|---|---|
| Controller | `CourseProgressController#list(Long courseId, String itemType, String level, Integer groupNo, Long updatedSince, HttpServletRequest request, @RequestHeader("X-Client-Type") String clientType)` | 取 userId、接参、调 Service |
| Service | `CourseProgressService#list(Long userId, ProgressQuery query) → ProgressListResponse` | 条件组装、`itemType` 枚举校验、排序、组装 |
| Mapper | `CourseLearningProgressMapper#selectList` | `LambdaQueryWrapper` 动态条件（`eq` / `ge` / `orderByDesc`） |

##### 涉及表

| 表 | 操作 | 用到的列 |
|---|---|---|
| `course_learning_progress` | SELECT | 全部读列（`deleted` 用于过滤） |

##### 数据流向

**① 入参 → ② 查库 → ③ 加工 → ④ 组装**

```
① 入参    X-Client-Type / Token  ──校验──→  userId
           courseId + 全部筛选条件  ──原样进 WHERE──→  查询条件

② 查库    course_learning_progress
              ──selectList(user_id, course_id, deleted=0 [+ itemType/level/groupNo/updatedSince])──→  N 行

③ 加工    无需运算 —— progress_detail 原样读取（已经是 JSON 对象）

④ 组装    ProgressListResponse { courseId, total, items[] }  ──→  JSON
```

**映射对照**

| 响应字段 | 来自 | 取法 |
|---|---|---|
| `courseId` | 请求参数 | 原样回显 |
| `total` | 查询结果 | 返回条数（Java 侧 `size()`） |
| `items[].id` | `course_learning_progress.id` | 直取（进度行主键，与 `itemId` 不是一回事） |
| `items[].itemType` / `itemId` / `itemKey` / `status` / `lastVisitTime` | 同上 | 直取；`itemKey` 是**写入时回填的人读副本**（汉字 / 笔画 code） |
| `items[].level` / `groupNo` | 同上 | 直取；`STROKE` 行这两列为 `null` |
| `items[].progressDetail` | 同上 | JSON → `Map<String,Object>` 原样返回（**未设置时为 `null`**） |

**关键 SQL**

```sql
SELECT * FROM course_learning_progress
WHERE user_id = ? AND course_id = ? AND deleted = 0
  [AND item_type = ?] [AND level = ?] [AND group_no = ?]
  [AND last_visit_time >= ?]
ORDER BY last_visit_time DESC, id;
```

> ⚠️ **必须带 `deleted = 0`** —— 漏掉会让已逻辑删除的行混进进度，"已练习N个"的口径也跟着错。
> ⚠️ 组级汇总**不在本接口算**（那是 `/course/writing/groups` 的职责），本接口只回行级明细。
> ⚠️ 不带筛选条件时是**整门课全量**（满量约 3 千行 / 400 KB），前端应按需带 `itemType` / `level` / `groupNo`。
