# Obsidian 知识库管理规范

> 本规范是**目标态设计**，不是对现状的描述。它定义这套知识库应当长成什么样、为什么这样设计、边界在哪里。
>
> 设计目标：目录结构十年不用重构，且任何一次 AI 协作都能在 30 秒内建立上下文。

## 一、设计原则

| 原则 | 含义 | 反例 |
|---|---|---|
| **单一归属** | 每篇文档有且只有一个「家」，不存两份 | 同一份接口文档既放项目又放通用 |
| **一屏可达** | 项目级元信息不超过两屏，读完即懂 | 48 个文件散在 7 个目录，全靠翻 |
| **编号不复用** | 目录编号一次性分配，删除后不回收 | `01` 被两个目录同时占用 |
| **内容与状态分离** | 内容写正文，状态写属性 | 文件名标注「最终版」「新版」 |
| **机器可读** | 命名、属性可被脚本与 AI 稳定解析 | 文件名含空格、括号、版本号 |

一条贯穿始终的判断标准：**如果三年后要新增一个分类，现有内容是否需要挪动？** 需要挪动，说明结构设计有问题。

### 2.1 编号登记表

| 编号 | 用途 | 当前占用 |
|---|---|---|
| `00` | 仓库规范 | 当前仓库规范 |
| `01` | 需求暂存（未归属项目） | 功能需求 |
| `02–09` | 项目，按建立顺序占用，一个项目一个号 | 02 云云天平 |
| `10–89` | 预留：知识库、素材库、脚本库 | — |
| `99` | 归档 | 归档 |

新增项目从 `03` 开始，往后续编号，不复用已删除的编号。编号顺序不代表重要性，只代表建立时间。

### 2.2 三类内容的边界

| 目录 | 分类依据 | 生命周期 |
|---|---|---|
| `00当前仓库规范` | **约束性** —— 必须遵守 | 极少变动，一改就是全仓库的事 |
| `01功能需求` | **暂时无主** —— 还没想好归哪个项目 | 7 天内必须转正或删除 |
| `02+ 项目` | **有交付目标** —— 有结束点、有验收标准 | 项目结束整体移入 `99归档` |

`01功能需求` 只是一个暂存区，**不是长期存放需求的地方**。需求一旦明确归属项目，立刻移进项目的 `01产品需求/`。这个目录长期为空是正常状态。

## 三、项目目录结构

这是本规范的核心。一个项目一个顶层目录，项目内部固定分为「定位 / 全局 / 模块」三层。

### 3.1 为什么要在项目内部分需求、架构、进度

先看现在的问题。`02云云天平` 是按业务模块分的：`CSCA练习` `CSCA考试` `HSK3.0` `HSK练习` `manage` `拼音课写字课` `练习`，共 48 个文件。

**按模块分没有错**，问题在于它只有模块这一层，缺了项目这一层。由此产生三个缺口：

| 缺口 | 表现 |
|---|---|
| 没有「项目是什么」的入口 | 新人或 AI 进来，只能靠目录名猜这个项目做什么 |
| 没有「现在做到哪」 | 进度只存在于你的记忆里，AI 每次都要重新问 |
| 跨模块的东西无处安放 | 数据库架构改造、共用题库方案被塞进某个模块目录，归属别扭 |

而 AI 协作（vibe coding）时，它最先需要的恰恰是这三件事，不是接口字段细节。给它 48 个文件，它要全读一遍才敢说话；给它两屏元信息加一个模块目录，它立刻就能干活。

**所以加上需求 / 架构 / 进度是对的。但有一个前提条件：**

> 这三样必须是**项目级、只此一份**的元信息层，不能变成对全部文档的重新分类。

如果把 48 篇接口文档按「需求 / 架构 / 进度」重新归类，结果会是每次写文档都要纠结「这算需求还是算架构」，而同一模块的接口设计、变更记录、验收标准被拆散到三个目录，找东西反而更慢。这是**过度分类**，比不分类更糟。

正确的做法是**分层，不是重分类**：

| 层 | 承担什么 | 数量 | 更新频率 |
|---|---|---|---|
| L0 定位层 | 项目是什么、现在到哪 | 2 个文件 | 进度每次会话更新 |
| L1 全局层 | 要做什么、系统怎么搭 | 各一个目录，少而精 | 低频 |
| L2 模块层 | 某模块的接口、字段、方案 | 文档大头，按模块 | 随开发 |
| 附属层 | 决策、素材、归档 | 按需 | 低频 |

### 3.2 目标结构

### 3.3 每个目录回答什么问题

判断一篇文档该放哪，只问一句：**它主要在回答哪个问题？** 不要问「它是什么类型」。

| 它回答的问题 | 放哪 | 以现有文档为例 |
|---|---|---|
| 这个项目是什么、怎么上手 | `README.md` | 新建 |
| 现在做到哪、下一步干什么 | `00当前进度.md` | 新建 |
| 要做成什么样、怎么算做完 | `01产品需求/` | 听力模块 PRD、题库数据统一检查点与验收标准 |
| 系统怎么搭、表怎么设计、跨模块怎么协作 | `02软件架构/` | practice-service 数据库架构改造、HSK 共用题库方案、HSK 题型枚举 |
| 某个模块的接口字段、页面结构、变更点 | `03业务模块/<模块>/` | CSCA练习-接口设计、写字课-接口设计、错题本批量删除接口变更 |
| 当初为什么这么定 | `04决策记录/` | 科目字典化方案（决策成分大） |
| 原型、导出件、数据样本 | `05素材/` | 错题本 html 原型、HSK 新旧大纲对比 xlsx |
| 已被取代的旧版本 | `99归档/` | `CSCA考试/archive/` 里的 v3.7 全文 |

几个容易放错的位置：

- **接口变更文档不进 `01产品需求`**。它是接口的修订记录，跟接口设计放一起，改动时才找得到对应关系。
- **xx方案 不要一律进 `02软件架构`**。只影响单个模块的方案（写字课 styleJson 字段说明）留在模块目录；影响多个模块的（共用题库）才上提到架构层。
- **归档放项目内 `99归档/`，不是顶层 `99归档/`**。项目内的旧版本要保留上下文；顶层 `99归档` 只收整个项目终结后的搬迁。

### 3.4 两个 L0 文件怎么写

这两份是唯一需要经常动的，其余都是低频。它们决定了 AI 能不能一次读懂项目。

**`README.md` 项目卡**——固定六段，控制在一屏内：

```markdown
# 汉考宝

## 这是什么
一句话：面向中文学习者的多语种考试练习平台（CSCA / HSK / 拼音写字课）。

## 技术栈与代码仓库
Spring Boot 3.5 + MyBatis Plus / iOS 客户端；后端仓库 <地址>。

## 模块清单
| 模块 | 职责 | 文档入口 | 状态 |
|---|---|---|---|
| CSCA练习 | 按科目刷题、错题本、收藏本 | [[CSCA练习-接口设计文档]] | 开发中 |

## 关键约束
- 返回体统一 `Result<T>`，见 [[错误码和统一返回体]]
- 题目数据必须过统一检查点才能上线

## 文档地图
需求 → 01产品需求；架构 → 02软件架构；模块 → 03业务模块。

## 关键决策
| 决策 | 理由 | 日期 |
|---|---|---|
| HSK 与 CSCA 共用题库表 | 题型结构一致，避免两套维护 | 2026-09 |
```

**`00当前进度.md` 活文档**——固定四段，最新状态在上，历史日志倒序追加：

```markdown
# 当前进度

## 一句话状态
CSCA 练习与考试接口已定稿，听力模块在开发，口语模块只有 PRD。

## 正在做
- [[听力模块接口设计]] 接口联调

## 下一步
1. 听力模块音频绑定联调
2. 口语模块建表

## 卡住 / 待决策
- HSK3.0 新旧大纲切换时间点未定

## 变更日志
- 2026-10-29 建立目录结构，模块文档归入 03业务模块
- 2026-10-28 CSCA 邀请与次数接口变更定稿
```

写法要求：

1. **每一项都短**。进度文档不是日报，一句话足够，细节链接出去。
2. **变更日志只追加不复述**。一次会话一行，而不是把做过的每件事列一遍。
3. **全文控制在 150 行内**。超过就把半年前的日志挪到 `99归档/进度-2026H1.md`。
4. **「卡住」这一段最重要**。它记录的是外部依赖和待拍板事项，是下次开工的第一入口。

### 3.5 AI 读取顺序

协作时按这个顺序喂上下文，不要一次把所有文件塞进去：

```
README.md  →  00当前进度.md  →  02软件架构/架构总览.md  →  03业务模块/<相关模块>/
  是什么         到哪了              怎么搭                  具体怎么改
```

前三步约两屏，足够让 AI 判断「该不该动、动了影响谁」。只有真要改某个模块时，才展开第四步。

这也是为什么目录命名要稳定可预测：AI 会按固定路径直接读，名字一改，每次都要重新 grep。

### 3.6 维护纪律

整个规范里只有一个高频动作：

> **每次会话结束前，如果状态变了，更新 `00当前进度.md`。**

其他都是低频的。这条不执行，前面所有设计都会退化成好看的目录树。

## 四、文件命名

| 文档类型 | 命名格式 | 示例 |
|---|---|---|
| 项目卡 | `README` | `README.md` |
| 进度 | `当前进度` | `00当前进度.md` |
| 总览类 | `主题+总览` | `架构总览.md`、`需求总览.md` |
| 模块文档 | `模块-文档类型` | `CSCA练习-接口设计文档.md` |
| 变更记录 | `模块-变更点-接口变更文档` | `CSCA邀请与次数-接口变更文档.md` |
| 规范文档 | 主题名（不带「规范」二字，目录已表明） | `错误码和统一返回体.md` |
| 日志 | `YYYY-MM-DD-主题` | `2026-10-29-周会.md` |

### 4.1 硬性约束

1. **不带序号前缀**。序号只用于目录，文件加序号会在插入新文档时全部失效。
2. **不带版本号**。`方案v2.md` 会让读者不知道该看哪个；版本写进属性或正文，旧版进 `99归档`。
3. **不用空格式片段**。「最终版」「修改后」「新」「(1)」一律禁止。
4. **控制长度**，不超过 30 个字。
5. **不用空格**，用 `-` 连接词。中文语境下 `-` 只用于连接模块名与文档类型。

### 4.2 重名处理

Obsidian 笔记名全局唯一，不同目录下的同名文件会互相干扰链接解析。用模块名做前缀区分：

```
❌ 03业务模块/CSCA练习/接口设计.md
   03业务模块/HSK练习/接口设计.md     ← 链接时会指错

✅ 03业务模块/CSCA练习/CSCA练习-接口设计文档.md
   03业务模块/HSK练习/HSK练习-接口设计文档.md
```

## 五、属性（Frontmatter）

字段少而稳定，不追求全覆盖：

```yaml
---
type: project
status: active
updated: 2026-10-29
tags:
  - 后端
  - 接口
---
```

| 字段 | 取值 | 是否必填 | 说明 |
|---|---|---|---|
| `type` | `note` / `spec` / `project` / `log` / `template` | 必填 | 与所在目录呼应 |
| `status` | `draft` / `active` / `deprecated` | 必填 | 决定这篇能不能被信任 |
| `created` | `YYYY-MM-DD` | 建议 | 创建日期，不做修改 |
| `updated` | `YYYY-MM-DD` | 必填 | 实质修改时更新 |
| `tags` | 1–5 个中文词 | 建议 | 只标主题，不标类型和状态 |

### 5.1 为什么类型和状态不做成标签

标签只承担**主题检索**一个职责。把 `#draft` `#接口设计` 也塞进标签，标签面板里三种维度混在一起，检索反而失效。类型和状态走字段，可以精确查询：

```dataview
TABLE status, updated
FROM "02云云天平/01产品需求"
WHERE status = "draft"
```

### 5.2 标签命名

- 中文、扁平、不用层级标签（不用 `#技术/后端/接口`）
- 单篇不超过 5 个，超过说明该拆分
- 标签是「主题词」不是「分类路径」，分类由目录承担

## 六、附件管理

### 6.1 存放策略：附件跟随笔记

```
03业务模块/CSCA练习/
├── CSCA练习-接口设计文档.md
└── _assets/
    └── CSCA练习-接口设计文档/
        ├── file-20261029103015123.png
        └── file-20261029104530234.png
```

- 目录名统一 `_assets`，下划线开头便于在文件列表中区分（它不是笔记）
- 二级目录名与笔记名一致，一篇笔记一个附件目录
- 文件名由插件生成，格式 `file-<时间戳到毫秒>`，不做语义化命名

### 6.2 与 `05素材` 的区别

| 类型 | 放哪 | 判据 |
|---|---|---|
| 笔记里插的截图、插图 | 笔记旁 `_assets/` | 脱离这篇笔记就没有意义 |
| 原型 html、TAPD 导出 pdf、数据 xlsx | `05素材/` | 独立成件，可能被多篇引用 |

`05素材` 收的是**非 Markdown 的独立交付物**。好处是 Markdown 目录保持干净，AI 扫目录时不会被二进制文件干扰。

### 6.3 三条禁令

1. 不手动往 `_assets` 拖文件 —— 一律通过粘贴或插入，由插件接管命名
2. 不手动重命名附件 —— 改名由「笔记改名联动」统一处理，手动改会让正文链接失效
3. 不把 `_assets` 加入 `.gitignore` —— 附件属于内容，必须同步

### 6.4 重命名联动

依赖插件 **Advanced Rename and Delete Handler**，三个开关都要开：

| 开关 | 作用 |
|---|---|
| `Should handle renames` | 总闸，不开则后面全部无效 |
| `Should rename attachment folder` | 笔记改名时，`_assets/笔记名/` 跟着改 |
| `Should rename attachment files` | 笔记改名时，附件文件名跟着改 |

这三个开关在该插件自己的设置页里，**不在** Custom Attachment Location 里，容易找错地方。

## 七、Git 同步

### 7.1 分支与节奏

- **单分支 `main`**：个人知识库没有并行开发，开分支只增加合并成本
- **自动提交**：obsidian-git 每 5–10 分钟自动 commit
- **手动推送**：每天结束推一次，或双击 `push-all.bat`

提交是本地行为，成本极低；推送会暴露半成品、可能引发跨设备冲突，需要人判断时机。

### 7.2 提交信息

沿用现有约定式提交前缀：

| 前缀 | 用于 | 示例 |
|---|---|---|
| `docs` | 新增或修改文档内容 | `docs: 补充错误码分段规则` |
| `feat` | 新增工具、脚本、模板 | `feat: 添加一键提交推送脚本` |
| `chore` | 配置调整、目录重组 | `chore: 项目目录按三层重构` |
| `fix` | 修正错误内容 | `fix: 修正统一返回体字段名` |

插件自动产生的 `vault backup: <时间>` 提交允许存在，不必强改。但做目录重组这类结构变更时，建议先关掉自动提交，手动提交一条 `chore:`，避免结构变更和内容变更混在一条记录里。

### 7.3 排除规则

必须排除：

| 路径 | 原因 |
|---|---|
| `.obsidian/workspace.json` | 记录窗口布局，本机状态，同步会互相打断 |
| `.obsidian/workspaces.json` | 同上 |
| `.obsidian/cache` | 缓存，可重新生成 |
| `.DS_Store` / `Thumbs.db` | 系统垃圾文件 |

必须纳入（否则换设备无法还原环境）：

| 路径 | 原因 |
|---|---|
| `.obsidian/app.json` | 链接格式、附件路径等核心设置 |
| `.obsidian/appearance.json` | 主题外观 |
| `.obsidian/community-plugins.json` | 插件启用清单 |
| `.obsidian/plugins/*/data.json` | 各插件配置 |
| `.obsidian/plugins/*/main.js` | 插件本体，避免重装时版本漂移 |

### 7.4 体积红线

| 类型 | 规则 |
|---|---|
| 单文件 > 10 MB | 不进仓库，改用外链或本地保存 |
| 数据库备份、导出转储（`*.sql`） | 禁止进仓库，留在项目工作目录 |
| 视频、安装包、镜像 | 禁止进仓库 |
| 文档（md / pdf / docx / xlsx） | 可进，单个控制在 5 MB 内 |

Git 对二进制文件不做增量压缩，每次改动存完整副本。一条 7 MB 的 SQL 备份改三次，仓库就多 21 MB 且难以回收。

### 7.5 跨设备协作

- 开机后等自动拉取完成（状态栏停止转动）再编辑
- 冲突处理顺序：看 `<<<<<<<` 标记 → 保留正确内容 → 删标记行 → 重新提交推送
- 不要两台设备同时长时间离线编辑同一批文档
- 本机 GitHub TLS 吊销检查过不去，已在**仓库级**配置 `http.https://github.com/.sslVerify=false`。换机器后若推送报 TLS 错误，重新执行一次这条命令

## 八、插件基线

### 8.1 最小可用集

| 插件 | 职责 | 缺失后果 |
|---|---|---|
| obsidian-git | 自动提交与推送 | 无法同步 |
| Custom Attachment Location | 决定附件存哪、叫什么 | 附件散落，命名混乱 |
| Advanced Rename and Delete Handler | 笔记改名时迁移附件 | 上一个插件直接不加载 |

### 8.2 版本兼容红线

**装任何插件前，先看 `manifest.json` 里 `minAppVersion` 是否 ≤ 当前 Obsidian 版本。**

不兼容的典型表现：插件装了、目录里有文件，但设置页只显示 `Required plugin missing`，或者列表里根本不出现。

排查顺序：

1. 看 Obsidian 版本（设置 → 关于）
2. 看插件 `manifest.json` 的 `minAppVersion`
3. 版本不满足则**回退插件**到兼容版本，而不是升级 Obsidian（升级会牵连全部插件）

### 8.3 插件只增不滥

每新增一个插件都问：**它解决的问题是否已能用现有插件或核心功能覆盖？**

功能重叠时只留一个。重叠插件会同时监听文件事件，容易出现同一文件被反复改名、链接被来回重写。

## 九、生命周期与归档

```
新建 ──▶ 01功能需求（暂存） ──▶ 归属项目 ──▶ 项目内对应目录
                                                    │
                                        ┌───────────┴───────────┐
                                        ▼                       ▼
                              被新版本取代 → 项目内 99归档    项目终结 → 顶层 99归档
```

| 阶段 | 动作 | 时限 |
|---|---|---|
| 暂存 | 随手记录，不做格式要求 | — |
| 转正 | 补 frontmatter，移入项目对应目录 | 7 天内 |
| 维护 | 实质修改时更新 `updated` | 按需 |
| 归档 | 移入归档目录，`status` 改 `deprecated`，开头加一行取代说明 | 被取代或项目结束时 |

归档不是删除。归档里的文档照样能搜索和链接，只是不再维护。
