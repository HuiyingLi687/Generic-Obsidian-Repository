# Obsidian 知识库管理规范

> 本规范是**目标态设计**，不是对现状的描述。它定义这套知识库应当长成什么样、为什么这样设计、以及边界在哪里。
>
> 设计目标是十年不用重构目录结构，而不是把当前文件摆放方式写成条文。

## 一、设计原则

| 原则 | 含义 | 反例 |
|---|---|---|
| **单一归属** | 每一篇笔记有且只有一个「家」 | 同一文档既放知识库又放项目目录 |
| **编号留白** | 目录编号用 10 递增，留出插入空间 | `01` `02` `03` 连号，中间无法插入 |
| **内容与状态分离** | 内容写在正文，状态写在属性 | 用文件名标注「最终版」「新版」 |
| **机器可读** | 命名、属性可被脚本与插件解析 | 文件名含空格、括号、特殊符号 |
| **渐进固化** | 先能落地，再谈完美 | 一上来要求每篇都写完整属性 |

一条贯穿始终的判断标准：**如果三年后要新增一个分类，现有内容是否需要挪动？** 需要挪动，说明结构设计有问题。

## 二、目录结构

```
vault/
├── 00收件箱/          未整理的临时内容，每周必须清空
├── 10知识/            原子化知识笔记，按领域分二级目录
│   ├── Java/
│   ├── 数据库/
│   ├── 前端/
│   └── 工具/
├── 20项目/            有明确目标与结束时间的交付物
│   └── 汉考宝/
├── 30规范/            约束性文档：规范、SOP、模板说明
│   ├── 编码规范/
│   ├── 文档规范/
│   └── 流程规范/
├── 90归档/            已完成或废弃内容，只读不删
└── 99系统/
    ├── 模板/
    └── 附件/
```

### 2.1 五类内容的划分依据

| 目录 | 分类依据 | 生命周期 | 典型内容 |
|---|---|---|---|
| `00收件箱` | 还没想好放哪 | 7 天内清空 | 剪藏、临时想法、待读链接 |
| `10知识` | **解释性** —— 这个东西是什么、为什么 | 长期迭代 | JVM 内存模型、MySQL 索引原理 |
| `20项目` | 有交付压力、有结束点 | 项目结束即归档 | 接口设计、PRD、验收标准 |
| `30规范` | **约束性** —— 必须这么做 | 极少变动 | 错误码规范、Git 提交规范 |
| `90归档` | 不再维护 | 永久留存 | 旧版本方案、已结束项目 |

`10知识` 与 `30规范` 的区别最容易混淆，判断方法：

- 读完能**理解**某事 → 知识
- 读完必须**遵守**某事 → 规范
- 举例：「JVM 的 GC 算法有几种」是知识；「项目统一使用 G1，禁止 SerialGC」是规范。

### 2.2 编号规则

- 只用两位数，间隔 10：`00` `10` `20` `30` `90` `99`
- 二级目录编号在父目录内独立计数，不受父目录编号影响
- 编号一经确定不再变更；确需调整时只调整新目录，不重排旧目录

### 2.3 目录命名

- 中文名称，不带空格，不使用 `-` `_` 连接（中文本身可读，无需分隔符）
- 不使用文件系统保留字符：`/ \ : * ? " < > |`
- 目录名是名词短语，不是动词或句子

## 三、文件命名

| 文档类型 | 命名格式 | 示例 |
|---|---|---|
| 知识笔记 | 概念名 | `JVM内存模型.md` |
| 规范文档 | 主题名（不带「规范」二字，目录已表明） | `错误码和统一返回体.md` |
| 项目文档 | `模块-文档类型` | `听力模块-接口设计.md` |
| 会议/日志 | `YYYY-MM-DD-主题` | `2026-10-29-周会.md` |
| 模板 | `模板名模板` | `知识笔记模板.md` |

### 3.1 硬性约束

1. **不带序号前缀**。序号只用于目录，文件名加序号会在插入新文档时全部失效。
2. **不带版本号**。`方案v2.md` 这种做法会让读者不知道该看哪个；版本信息写进属性和正文。
3. **不用空格式片段**。「最终版」「修改后」「新」这类词一律禁止。
4. **控制长度**，不超过 30 个字。Obsidian 的标签页和面包屑宽度有限。

### 3.2 重名处理

Obsidian 中笔记名全局唯一，不同目录下的同名文件会互相干扰链接解析。若确实需要同名，用限定词区分：

```
❌ 10知识/Java/接口设计.md
   20项目/汉考宝/接口设计.md        ← 链接时会指错

✅ 10知识/Java/接口设计原则.md
   20项目/汉考宝/听力模块-接口设计.md
```

## 四、属性（Frontmatter）

每篇文档头部统一使用以下字段，字段少而稳定，不追求全覆盖：

```yaml
---
type: spec
status: active
created: 2026-10-29
updated: 2026-10-29
tags:
  - 后端
  - 接口
---
```

| 字段 | 取值 | 是否必填 | 说明 |
|---|---|---|---|
| `type` | `note` / `spec` / `project` / `log` / `template` | 必填 | 决定这篇文档的性质，与所在目录呼应 |
| `status` | `draft` / `active` / `deprecated` | 必填 | 决定这篇文档能不能被信任 |
| `created` | `YYYY-MM-DD` | 必填 | 创建日期，不做修改 |
| `updated` | `YYYY-MM-DD` | 建议 | 实质修改时更新 |
| `tags` | 1–5 个中文词 | 建议 | 只标主题，不标类型和状态 |

### 4.1 为什么类型和状态不做成标签

标签只承担**主题检索**一个职责。把 `#draft` `#接口设计` 这类也塞进标签，会导致标签面板里三种维度混在一起，检索反而失效。

类型和状态用字段表达，可以配合 Dataview 精确查询：

```dataview
TABLE status, updated
FROM "30规范"
WHERE status = "draft"
```

### 4.2 标签命名

- 中文、扁平、不使用层级标签（不用 `#技术/后端/接口`）
- 单篇不超过 5 个，超过说明这篇笔记该拆分
- 标签是「主题词」不是「分类路径」，分类由目录承担

## 五、附件管理

### 5.1 存放策略：附件跟随笔记

```
10知识/Java/
├── JVM内存模型.md
└── _assets/
    └── JVM内存模型/
        ├── file-20261029103015123.png
        └── file-20261029104530234.png
```

- 目录名统一 `_assets`，下划线开头便于在文件列表中一眼区分（它不是笔记）
- 二级目录名与笔记名一致，一篇笔记一个附件目录
- 文件名由插件生成，格式 `file-<时间戳到毫秒>`，不做语义化命名

### 5.2 为什么不用全局 `attachments/` 大杂烩

| 方案 | 优点 | 缺点 |
|---|---|---|
| 全局统一目录 | 只有一个附件目录，好备份 | 上千个文件混在一起，无法判断归属；删笔记后附件变孤儿 |
| **按笔记分目录** | 删笔记连目录一起删；迁移笔记时附件自动跟随 | 目录数量多 |

知识库的生命周期远长于单个项目，孤儿附件是长期维护的主要负担，所以选按笔记分目录。

### 5.3 三条禁令

1. 不手动往 `_assets` 里拖文件 —— 一律通过粘贴或插入，由插件接管命名
2. 不手动重命名附件 —— 改名由「笔记改名联动」统一处理，手动改会让正文链接失效
3. 不把 `_assets` 加入 `.gitignore` —— 附件属于知识内容，必须同步

### 5.4 重命名联动

附件跟着笔记走依赖插件 **Advanced Rename and Delete Handler**，需要开启：

| 开关 | 作用 |
|---|---|
| `Should handle renames` | 总闸，不开则后面全部无效 |
| `Should rename attachment folder` | 笔记改名时，`_assets/笔记名/` 跟着改 |
| `Should rename attachment files` | 笔记改名时，附件文件名跟着改 |

这三个开关在该插件自己的设置页里，不在附件路径插件里，容易找错地方。

## 六、模板

`99系统/模板/` 下维护四份模板，新建文档一律从模板起手，保证属性字段不遗漏：

| 模板 | 对应目录 | 预置内容 |
|---|---|---|
| `知识笔记模板.md` | `10知识` | type=note，含「是什么 / 为什么 / 怎么用 / 参考」四段骨架 |
| `规范文档模板.md` | `30规范` | type=spec，含「适用范围 / 条款 / 违规示例」三段 |
| `项目文档模板.md` | `20项目` | type=project，含「背景 / 目标 / 方案 / 验收」四段 |
| `会议记录模板.md` | `00收件箱` | type=log，含「结论 / 待办 / 决策依据」 |

模板本身放在 `99系统` 下，不会被误当成正式文档；`type: template` 便于排除出检索结果。

## 七、Git 同步

### 7.1 分支与节奏

- **单分支 `main`**：个人知识库不存在并行开发，开分支只增加合并成本
- **自动提交**：间隔 5 分钟，改动自动落进本地仓库
- **手动推送**：每天工作结束推一次，或随时双击推送脚本

自动提交但不自动推送的理由：提交是本地行为，成本极低；推送会暴露半成品、可能引发跨设备冲突，需要人判断时机。

### 7.2 提交信息

遵循约定式提交，前缀与内容之间用冒号加空格：

| 前缀 | 用于 | 示例 |
|---|---|---|
| `docs` | 新增或修改文档内容 | `docs: 补充错误码分段规则` |
| `feat` | 新增工具、脚本、模板 | `feat: 添加周报生成脚本` |
| `chore` | 配置调整、目录重组 | `chore: 调整附件目录命名` |
| `fix` | 修正错误内容 | `fix: 修正统一返回体字段名` |

插件自动备份产生的 `vault backup: <时间>` 提交允许存在，不必强改。

### 7.3 排除规则

以下内容**必须**排除出版本控制：

| 路径 | 原因 |
|---|---|
| `.obsidian/workspace.json` | 记录窗口布局与打开状态，属于本机状态，同步会互相打断 |
| `.obsidian/workspaces.json` | 同上，工作区快照 |
| `.obsidian/cache` | 缓存，可重新生成 |
| `.DS_Store` / `Thumbs.db` | 系统垃圾文件 |

以下内容**必须**纳入版本控制，否则换设备无法还原环境：

| 路径 | 原因 |
|---|---|
| `.obsidian/app.json` | 链接格式、附件路径等核心设置 |
| `.obsidian/appearance.json` | 主题外观 |
| `.obsidian/community-plugins.json` | 插件启用清单 |
| `.obsidian/plugins/*/data.json` | 各插件配置 |
| `.obsidian/plugins/*/main.js` | 插件本体，避免重装时版本漂移 |

### 7.4 体积红线

| 类型 | 规则 |
|---|---|
| 单文件 > 10 MB | 不进仓库，改用外链或本地保存 |
| 数据库备份、导出转储（`*.sql`） | 禁止进仓库，留在项目工作目录 |
| 视频、安装包、镜像 | 禁止进仓库 |
| 文档（md / pdf / docx / xlsx） | 可进，单个控制在 5 MB 内 |

Git 对二进制文件不做增量压缩，每次改动都存完整副本，仓库体积只增不减。一条 7 MB 的 SQL 备份改动三次，仓库就多出 21 MB，且无法通过常规手段回收。

### 7.5 跨设备协作

- 开机后等待自动拉取完成（状态栏图标停止转动）再开始编辑
- 冲突时的处理顺序：先看 `<<<<<<<` 标记 → 保留正确内容 → 删标记行 → 重新提交推送
- 不建议两台设备同时长时间离线编辑同一批文档

## 八、插件基线

### 8.1 最小可用集

| 插件 | 职责 | 缺失后果 |
|---|---|---|
| obsidian-git | 自动提交与推送 | 无法同步 |
| Custom Attachment Location | 决定附件存哪、叫什么 | 附件散落，命名混乱 |
| Advanced Rename and Delete Handler | 笔记改名时迁移附件 | 上一个插件直接不加载 |

### 8.2 版本兼容红线

**安装任何插件前，先看它的 `manifest.json` 里 `minAppVersion` 是否 ≤ 当前 Obsidian 版本。**

不兼容的典型表现：插件装了、目录里有文件、但设置页只显示一句 `Required plugin missing`，或者列表里根本不出现。

出问题时的排查顺序：

1. 看 Obsidian 版本（设置 → 关于）
2. 看插件 `manifest.json` 的 `minAppVersion`
3. 版本不满足则回退插件到兼容版本，而不是升级 Obsidian（升级会牵连全部插件）

### 8.3 插件只增不滥

每新增一个插件，都要问：**它解决的问题是否已经能用现有插件或核心功能覆盖？**

两个插件功能重叠时，只保留一个。重叠的插件会同时监听文件事件，容易出现同一文件被反复改名、链接被来回重写的问题。

## 九、内容生命周期

```
新建 ──▶ 00收件箱 ──▶ 判定类型 ──▶ 10知识 / 20项目 / 30规范
                                        │
                                        ▼
                                   90归档（项目结束或文档废弃）
```

| 阶段 | 动作 | 时限 |
|---|---|---|
| 收件箱 | 随手记录，不做格式要求 | — |
| 整理 | 补 frontmatter，按类型归入对应目录 | 7 天内 |
| 维护 | 实质修改时更新 `updated` | 按需 |
| 归档 | 移入 `90归档`，`status` 改为 `deprecated`，开头加一行状态说明 | 项目结束或内容失效时 |

归档不是删除。`90归档` 里的文档照样能被搜索和链接，只是不再维护。

## 十、从当前结构迁移

现有内容按以下映射归位，迁移时**只移动目录，不改文件名**：

| 现有位置 | 目标位置 |
|---|---|
| `01通用/01Java规范` 等编码类 | `30规范/编码规范/` |
| `01通用/04错误码规范` 等接口类 | `30规范/文档规范/` |
| `01通用/07obsidian规范` | `30规范/流程规范/` |
| `02云云天平/` 全部 | `20项目/汉考宝/` |
| 各类零散笔记 | 按主题进 `10知识/` |

迁移建议分三步走：先建新目录并移动，确认链接仍然有效（Obsidian 会自动更新相对链接），再删除空目录，最后提交推送。不要一次性搬完再验证。

## 十一、月度自查

每月花十分钟过一遍：

- [ ] `00收件箱` 是否清空
- [ ] 是否存在 `status: draft` 超过 30 天的文档
- [ ] 是否有不在任何笔记里的孤儿附件（`_assets` 目录下没有对应笔记）
- [ ] 是否有文件名包含「最终」「新版」「副本」的文档
- [ ] 仓库体积是否异常增长（`git count-objects -vH`）
- [ ] 是否有超过 10 MB 的文件被误提交
