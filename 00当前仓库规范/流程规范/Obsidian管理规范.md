# Obsidian 知识库管理规范

> **适用范围：本仓库的所有项目。** 仓库装多个项目，本规范只规定「每个项目应当长什么样」，不规定任何单个项目的业务内容。
>
> 与 [README](../../README.md) 的分工：README 是导航（有哪些项目、先读什么、脚本怎么用），本文件是约束（目录怎么建、文件怎么命名、附件放哪、什么能进仓库）。
>
> 设计目标：目录结构十年不用重构，且任何一次 AI 协作都能在 30 秒内建立上下文。

## 一、设计原则

| 原则 | 含义 | 反例 |
|---|---|---|
| **单一归属** | 每篇文档有且只有一个「家」，不存两份 | 同一份接口文档既放项目又放通用 |
| **项目隔离** | 一个项目一个顶层目录，项目之间的文档不互相引用 | B 项目的需求写在 A 项目目录里 |
| **一屏可达** | 项目级元信息不超过两屏，读完即懂 | 几十个文件散在 7 个目录，全靠翻 |
| **编号不复用** | 目录编号一次性分配，删除后不回收 | `03` 被两个项目同时占用 |
| **内容与状态分离** | 内容写正文，状态写属性 | 文件名标注「最终版」「新版」 |
| **机器可读** | 命名、属性可被脚本与 AI 稳定解析 | 文件名含空格、括号、版本号 |

一条贯穿始终的判断标准：**如果三年后要新增一个项目或一个分类，现有内容是否需要挪动？** 需要挪动，说明结构设计有问题。

## 二、顶层结构

```
Generic-Obsidian-Repository/
├── 00当前仓库规范/          约束性文档：所有项目通用，必须遵守
│   ├── 编码规范/
│   │   ├── Java规范/
│   │   ├── 数据库设计规范/
│   │   ├── 日志规范/
│   │   ├── Git 提交规范/
│   │   └── 错误码规范/
│   ├── 文档规范/
│   │   └── 接口设计文档模板/
│   └── 流程规范/
│       └── Obsidian管理规范.md
├── 01通用/                 需求暂存区（未归属任何项目），7 天内清空
├── 02云云天平/             第 1 个项目：汉考宝
├── 99归档/                 整个项目终结后的归宿

├── push-all.bat            提交并推送
├── 检查链接.bat            全库链接体检
├── README.md               仓库总入口
└── .obsidian/              配置，不要手改
```

### 2.1 编号登记表

| 编号 | 用途 | 当前占用 |
|---|---|---|
| `00` | 仓库规范 | 当前仓库规范 |
| `01` | 需求暂存（未归属项目） | `01通用`（空，名称待纠正） |
| `02–09` | **项目**，按建立顺序占用，一个项目一个号 | `02` 云云天平 |
| `10–89` | 预留：知识库、素材库、脚本库 | — |
| `99` | 归档 | 空 |

新增项目从 `03` 开始往后续，**不复用已删除的编号**。编号顺序不代表重要性，只代表建立时间。

### 2.2 三类内容的边界

| 目录 | 分类依据 | 生命周期 |
|---|---|---|
| `00当前仓库规范` | **约束性** —— 所有项目都必须遵守 | 极少变动，一改就是全仓库的事 |
| `01通用` | **暂时无主** —— 还没想好归哪个项目 | 7 天内必须转正或删除 |
| `02–09 <项目>` | **有交付目标** —— 有结束点、有验收标准 | 项目结束整体移入 `99归档` |

`01通用` 只是暂存区，**不是长期存放需求的地方**。需求一旦明确归属项目，立刻移进该项目的 `01功能需求/`。这个目录长期为空是正常状态。

### 2.3 通用规范与项目规范的分界

这是多项目仓库最容易搞乱的地方。判据只有一条：

> **换一个项目，这条规则还成立吗？** 成立 → 进 `00当前仓库规范`；不成立 → 写进那个项目的 `README.md`。

| 内容 | 放哪 | 例 |
|---|---|---|
| 目录结构、文件命名、附件落点、Git 规则 | `00当前仓库规范` | 本文件 |
| 接口返回体、错误码分段、日志格式 | `00当前仓库规范/编码规范` | 错误码和统一返回体 |
| 某项目用哪个框架、几个服务共用一个库 | `<项目>/README.md`「关键约束」 | 汉考宝：Spring Boot 3.5 + 11 服务共用一库 |
| 某项目的业务术语、科目分类、上线检查点 | `<项目>/` 内 | 汉考宝：题目数据统一检查点 |

**不要为了「看起来统一」把项目约束上提。** 一旦上提，第二个项目就会被一条本不适用的规则绑住。

### 2.4 已知偏差（改与不改）

规范描述目标态，实际目录可能落后一步。当前存在的偏差：

| 偏差 | 说明 | 处理 |
|---|---|---|
| `01通用/` 名称不符 | 编号 `01` 的用途是需求暂存，名字应体现用途 | 空目录，直接删或改名，二选一 |
| 根目录 `2026-10-29.md` | 0 字节，误创建后被提交 | 删除 |
| `<项目>/02软件架构/03数据字典/` 为空 | 枚举、字典类文档应上提到此，现散在各模块目录 | 按需迁移，非必须 |

多项目并存后，偏差只会更多。**处理原则：以各项目 `README.md` 里写的实际路径为准，本文件不强制改造存量目录。** 强迫存量项目对齐模板，成本远高于收益。

## 三、项目内部结构

这是本规范的核心。一个项目一个顶层目录，项目内部固定分为「定位 / 全局 / 模块」三层。

### 3.1 为什么要分这三层

常见的失败形态是**只有模块层**：一个项目目录下直接平铺一堆模块文件夹（如 `订单/` `支付/` `后台管理/`），除此之外什么都没有。

按模块分没有错，问题在于只有模块这一层，缺了项目这一层。由此产生三个缺口：

| 缺口 | 表现 |
|---|---|
| 没有「项目是什么」的入口 | 新人或 AI 进来，只能靠目录名猜这个项目做什么 |
| 没有「现在做到哪」 | 进度只存在于你的记忆里，AI 每次都要重新问 |
| 跨模块的东西无处安放 | 数据库改造、共用方案被塞进某个模块目录，归属别扭 |

AI 协作时，它最先需要的恰恰是这三件事，不是接口字段细节。给它几十个文件，它要全读一遍才敢说话；给它两屏元信息加一个模块目录，它立刻就能干活。

**所以加上需求 / 架构 / 进度是对的。但有一个前提条件：**

> 这三样必须是**项目级、只此一份**的元信息层，不能变成对全部文档的重新分类。

如果把几十篇接口文档按「需求 / 架构 / 进度」重新归类，结果会是每次写文档都要纠结「这算需求还是算架构」，而同一模块的接口设计、变更记录、验收标准被拆散到三个目录，找东西反而更慢。这是**过度分类**，比不分类更糟。

正确的做法是**分层，不是重分类**：

| 层 | 承担什么 | 数量 | 更新频率 |
|---|---|---|---|
| L0 定位层 | 项目是什么、现在到哪 | 2 个文件 | 进度每次会话更新 |
| L1 全局层 | 要做什么、系统怎么搭 | 各一个目录，少而精 | 低频 |
| L2 模块层 | 某模块的接口、字段、方案 | 文档大头，按模块 | 随开发 |
| 附属层 | 决策、素材、归档 | 按需 | 低频 |

### 3.2 标准结构

所有项目长同一个样。`<编号><项目名>` 替换成实际目录名即可：

```
<编号><项目名>/
├── README.md                项目卡：唯一入口，AI 第一读
├── 00当前进度/               活文档：现在到哪，AI 第二读
│   ├── 当前进度.md
│   ├── 00当前进度模板.md
│   └── 00数据库变更台账/      按月分文件，编号倒序（越小越新）
├── 01功能需求/               要做什么
│   ├── 00需求索引.md         全项目需求清单 + 优先级 + 状态
│   └── 00功能点模板.md
├── 02软件架构/               怎么做
│   ├── 01架构总览/           服务划分、技术栈、部署拓扑
│   ├── 02数据库/             库在哪、表归属、变更影响面
│   ├── 03数据字典/           枚举、字典表
│   └── 04关键算法/           跨模块的机制与算法
├── 03业务模块/               文档大头在这里，按模块分
│   └── <模块名>/
├── 04决策记录/               为什么当初这么定（少于 5 篇时不要建）
├── 90素材/                   粘贴的截图与插图；独立交付物也可放这
└── 99归档/                   项目内被取代的旧版本
```

几点说明：

- **`04决策记录` 空着就别建**。空目录会让 AI 以为那里该有东西。
- **素材不单独占一个编号层**。`90素材` 是项目内目录，不参与 `01/02/03` 的语义编号，也不会和模块目录抢位置。
- **`00数据库变更台账/` 是唯一必须按月维护的目录**。代码合并到生产而漏迁库，是这类项目最常见的事故，台账就是防它的。

### 3.3 每个目录回答什么问题

判断一篇文档该放哪，只问一句：**它主要在回答哪个问题？** 不要问「它是什么类型」。

| 它回答的问题 | 放哪 |
|---|---|
| 这个项目是什么、怎么上手 | `README.md` |
| 现在做到哪、下一步干什么、什么不能动 | `00当前进度/当前进度.md` |
| 某个字段、某张表什么时候加的 | `00当前进度/00数据库变更台账/` |
| 要做成什么样、怎么算做完 | `01功能需求/` |
| 系统怎么搭、表怎么设计、跨模块怎么协作 | `02软件架构/` |
| 某个模块的接口字段、页面结构、变更点 | `03业务模块/<模块>/` |
| 当初为什么这么定 | `04决策记录/` |
| 原型、导出件、数据样本 | `90素材/` 或模块目录内 |
| 已被取代的旧版本 | 项目自己的 `99归档/` |

几个容易放错的位置：

- **接口变更文档不进 `01功能需求`**。它是接口的修订记录，跟接口设计放一起，改动时才找得到对应关系。
- **「xx方案」不要一律进 `02软件架构`**。只影响单个模块的方案留在模块目录；影响多个模块的才上提到架构层。
- **归档放项目内 `99归档/`，不是顶层 `99归档/`**。项目内的旧版本要保留上下文；顶层 `99归档` 只收整个项目终结后的搬迁。

### 3.4 两个 L0 文件怎么写

这两份是唯一需要经常动的，其余都是低频。它们决定了 AI 能不能一次读懂项目。模板在项目目录内，**新建项目时复制模板，不要在本文档里找样例**：

| 文件 | 模板 | 最低要求 |
|---|---|---|
| `<项目>/README.md` | 无模板，写作规范见下 | 五段齐全，一屏内 |
| `<项目>/00当前进度/当前进度.md` | `00当前进度模板.md` | 按模板八节写，150 行内 |

**项目卡的五段**（顺序固定）：

1. **这是什么** —— 一句话，别写成公司介绍
2. **技术栈与代码仓库** —— 语言/框架版本 + 仓库地址
3. **模块清单** —— 模块 / 职责 / 文档入口，**不写开发状态**（状态只写进当前进度，两处必对不上）
4. **关键约束** —— 这个项目独有的硬规则（如「返回体统一 `Result<T>`」），本项目内优先级最高
5. **文档地图** —— 需求、架构、模块分别去哪个目录

**进度文档的四条写法要求**：

1. **每一项都短**。进度文档不是日报，一句话足够，细节链接出去
2. **变更日志只追加不复述**。一次会话一行，而不是把做过的每件事列一遍
3. **全文控制在 150 行内**。超过就把半年前的日志挪到 `99归档/`
4. **「卡点与未定」这一段最重要**。它记录外部依赖和待拍板事项，是下次开工的第一入口；没想清楚的必须显式写「未定」，否则 AI 会自己编一个方案

### 3.5 AI 读取顺序

协作时按这个顺序喂上下文，不要一次把所有文件塞进去：

```
<项目>/README.md  →  00当前进度/当前进度.md  →  02软件架构/  →  03业务模块/<相关模块>/
     是什么              到哪了、别动什么          怎么搭            具体怎么改
```

前三步约两屏，足够让 AI 判断「该不该动、动了影响谁」。只有真要改某个模块时，才展开第四步。多个项目并存时，先由根 `README.md` 确定这次是哪个项目。

这也是为什么目录命名要稳定可预测：AI 会按固定路径直接读，名字一改，每次都要重新 grep。

### 3.6 维护纪律

整个规范里只有两个高频动作：

> 1. **每次会话结束前，如果状态变了，更新 `当前进度.md`。**
> 2. **每次改表，同一次提交里登记变更台账。**

其他都是低频的。这两条不执行，前面所有设计都会退化成好看的目录树。

## 四、文件命名

| 文档类型 | 命名格式 | 示例 |
|---|---|---|
| 项目卡 | `README` | `README.md` |
| 进度 | `当前进度` | `当前进度.md` |
| 总览类 | `主题+总览` | `架构总览.md`、`需求总览.md` |
| 模板 | `00+主题+模板` | `00功能点模板.md` |
| 模块文档 | `模块-文档类型` | `<模块>-接口设计文档.md` |
| 变更记录 | `模块-变更点-接口变更文档` | `<模块>-<变更点>-接口变更文档.md` |
| 规范文档 | 主题名（不带「规范」二字，目录已表明） | `错误码和统一返回体.md` |
| 台账 | `序号-YYYY-MM` | `999-2026-05.md` |
| 日志 | `YYYY-MM-DD-主题` | `2026-10-29-周会.md` |

### 4.1 硬性约束

1. **不带版本号**。`方案v2.md` 会让读者不知道该看哪个；版本写进属性或正文，旧版进 `99归档`。
2. **不用空格式片段**。「最终版」「修改后」「新」「(1)」一律禁止。
3. **控制长度**，不超过 30 个字。
4. **不用空格**，用 `-` 连接词。中文语境下 `-` 只用于连接模块名与文档类型。
5. **目录带序号前缀，文件不带**（模板文件与台账除外，它们靠序号保证排序稳定）。序号只用于目录时，插入新文档不会让已有排序失效。

### 4.2 重名处理

Obsidian 笔记名全局唯一，不同目录下的同名文件会互相干扰链接解析。用模块名做前缀区分：

```
❌ 03业务模块/模块A/接口设计.md
   03业务模块/模块B/接口设计.md     ← 链接时会指错

✅ 03业务模块/模块A/模块A-接口设计文档.md
   03业务模块/模块B/模块B-接口设计文档.md
```

### 4.3 改名与移动

**改名、移动一律在 Obsidian 窗口内做（右键 → 重命名）。** 在资源管理器、VS Code、git、脚本里改名，Obsidian 完全不知道，`[文本](相对路径.md)` 形式的链接必断。

`alwaysUpdateLinks: true` 能自动跟随改名，但有三个隐含前提，少一个就不触发：

| 前提 | 会踩的情况 |
|---|---|
| 在 Obsidian 窗口内改名 | 外部程序改名 |
| Obsidian 当时开着，且已索引到「谁引用了它」 | 刚由脚本写入、缓存未刷新的文件 |
| 链接在索引那一刻是有效的 | 已经断了的链接，它只做跟随，永不回头修 |

兜底手段：改完跑一次 `检查链接.bat`（见 [README](../../README.md) 第七节），它会报告断链并反查「原名现在叫什么」。

## 五、属性（Frontmatter）

字段少而稳定，不追求全覆盖：

```yaml
---
type: note
status: active
updated: 2026-11-02
tags:
  - 后端
  - 接口
---
```

| 字段 | 取值 | 是否必填 | 说明 |
|---|---|---|---|
| `type` | `note` / `spec` / `project` / `log` / `template` | 必填 | 与所在目录呼应 |
| `status` | `draft` / `active` / `deprecated` | 必填 | 决定这篇能不能被信任 |
| `created` | `YYYY-MM-DD` | 建议 | 创建日期，不做修改 |
| `updated` | `YYYY-MM-DD` | 必填 | 实质修改时更新 |
| `tags` | 1–5 个中文词 | 建议 | 只标主题，不标类型和状态 |

### 5.1 为什么类型和状态不做成标签

标签只承担**主题检索**一个职责。把 `#draft` `#接口设计` 也塞进标签，标签面板里三种维度混在一起，检索反而失效。类型和状态走字段，可以精确查询：

```dataview
TABLE status, updated
FROM "<项目>/01功能需求"
WHERE status = "draft"
```

### 5.2 标签命名

- 中文、扁平、不用层级标签（不用 `#技术/后端/接口`）
- 单篇不超过 5 个，超过说明该拆分
- 标签是「主题词」不是「分类路径」，分类由目录承担
- **多项目环境下不加项目名前缀**。项目由目录隔离，标签里再带一遍会让同一主题散成多组

## 六、附件管理

### 6.1 落点

目标落点：`<项目>/90素材/`。粘贴的截图和插图统一进这里，不跟着笔记散落。

### 6.2 现状与限制（重要）

**Obsidian 核心设置里只有一个全局附件目录，无法按项目分别配置。** 这是多项目仓库绕不过去的限制，三个选项：

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 不配（当前状态） | 核心设置「附件默认位置」留空，图片落在笔记同级目录 | 图片散落在各模块目录里 |
| B. 全局指向一个目录 | 设置里指定一个库内文件夹 | 只能选一个，所有项目共用，跨项目混放 |
| C. 插件按笔记路径分流 | 需要写 token 模板 | 配置复杂、易失效，收益不足以抵消维护成本 |

**推荐 A，即维持现状。** 图片散落只是不整齐，不影响链接正确性（相对路径自动维护）；B 和 C 都要引入一条「改一次就要全局回头检查」的配置。附件管理不是本仓库的瓶颈，不值得为它增加脆弱点。

如果哪天确实要统一到 B，只需改核心设置一处，**不要同时在插件里也填一遍**——两处都填，将来一定对不上。插件的 `shouldFollowObsidianAttachmentLocation` 保持开启，它自己的路径字段始终留空；`markdownUrlFormat` 也必须留空，填了会按模板硬写链接，粘贴出来就是坏链。

### 6.3 三条禁令

1. **不手动重命名附件**。手动改会让正文链接失效
2. **不把素材目录加入 `.gitignore`**。附件属于内容，必须同步
3. **不把大文件当附件粘贴**。超过 10 MB 的走外链或本地保存，见 7.4

### 6.4 重命名联动

是否让插件接管改名（Advanced Rename and Delete Handler 的三个开关），取决于附件命名方式：

| 场景 | `Should handle renames` | 说明 |
|---|---|---|
| 附件名不跟随笔记（时间戳/随机名） | **关** | 由 Obsidian 原生处理改名，最简单 |
| 附件名跟随笔记（一笔记一附件目录） | 开 | 需要同时开 rename attachment files / folder |

三个开关都在 **Advanced Rename and Delete Handler 自己的设置页**里，不在 Custom Attachment Location 里，容易找错地方。

## 七、Git 同步

### 7.1 分支与节奏

- **单分支 `main`**：个人知识库没有并行开发，开分支只增加合并成本
- **自动提交**：obsidian-git 每 5–10 分钟自动 commit
- **手动推送**：每天结束推一次，或双击 `push-all.bat`

提交是本地行为，成本极低；推送会暴露半成品、可能引发跨设备冲突，需要人判断时机。

### 7.2 提交信息

沿用约定式提交前缀：

| 前缀 | 用于 | 示例 |
|---|---|---|
| `docs` | 新增或修改文档内容 | `docs: 补充错误码分段规则` |
| `feat` | 新增工具、脚本、模板 | `feat: 添加一键提交推送脚本` |
| `chore` | 配置调整、目录重组 | `chore: 项目目录按三层重构` |
| `fix` | 修正错误内容 | `fix: 修正统一返回体字段名` |

插件自动产生的 `vault backup: <时间>` 提交允许存在，不必强改。但做目录重组这类结构变更时，建议先关掉自动提交，手动提交一条 `chore:`，避免结构变更和内容变更混在一条记录里。

### 7.3 排除规则

必须排除：

| 路径 | 原因 |
|---|---|
| `.obsidian/workspace.json` | 记录窗口布局，本机状态，同步会互相打断 |
| `.obsidian/workspaces.json` | 同上 |
| `.obsidian/cache` | 缓存，可重新生成 |
| `.DS_Store` / `Thumbs.db` | 系统垃圾文件 |

必须纳入（否则换设备无法还原环境）：

| 路径 | 原因 |
|---|---|
| `.obsidian/app.json` | 链接格式、附件路径等核心设置 |
| `.obsidian/appearance.json` | 主题外观 |
| `.obsidian/community-plugins.json` | 插件启用清单 |
| `.obsidian/plugins/*/data.json` | 各插件配置 |
| `.obsidian/plugins/*/main.js` | 插件本体，避免重装时版本漂移 |

### 7.4 体积红线

| 类型 | 规则 |
|---|---|
| 单文件 > 10 MB | 不进仓库，改用外链或本地保存 |
| 数据库备份、导出转储（`*.sql`） | 禁止进仓库，留在项目工作目录 |
| 视频、安装包、镜像 | 禁止进仓库 |
| 文档（md / pdf / docx / xlsx） | 可进，单个控制在 5 MB 内 |

Git 对二进制文件不做增量压缩，每次改动存完整副本。一条 7 MB 的 SQL 备份改三次，仓库就多 21 MB 且难以回收。

### 7.5 跨设备协作

- 开机后等自动拉取完成（状态栏停止转动）再编辑
- 冲突处理顺序：看 `<<<<<<<` 标记 → 保留正确内容 → 删标记行 → 重新提交推送
- 不要两台设备同时长时间离线编辑同一批文档
- 本机 GitHub TLS 吊销检查过不去，已在**仓库级**配置 `http.https://github.com/.sslVerify=false`。换机器后若推送报 TLS 错误，重新执行一次这条命令

## 八、插件基线

### 8.1 最小可用集

| 插件 | 职责 | 缺失后果 |
|---|---|---|
| obsidian-git | 自动提交与推送 | 无法同步 |
| Custom Attachment Location | 决定附件叫什么名、落点规则（当前落点用默认，见 6.2） | 附件名冲突，粘贴时重名覆盖 |
| Advanced Rename and Delete Handler | 笔记改名时迁移附件 | 上一个插件直接不加载 |

### 8.2 版本兼容红线

**装任何插件前，先看 `manifest.json` 里 `minAppVersion` 是否 ≤ 当前 Obsidian 版本。**

不兼容的典型表现：插件装了、目录里有文件，但设置页只显示 `Required plugin missing`，或者列表里根本不出现。

排查顺序：

1. 看 Obsidian 版本（设置 → 关于）
2. 看插件 `manifest.json` 的 `minAppVersion`
3. 版本不满足则**回退插件**到兼容版本，而不是升级 Obsidian（升级会牵连全部插件）

### 8.3 插件只增不滥

每新增一个插件都问：**它解决的问题是否已能用现有插件或核心功能覆盖？**

功能重叠时只留一个。重叠插件会同时监听文件事件，容易出现同一文件被反复改名、链接被来回重写。

## 九、生命周期与归档

```
新建 ──▶ 01通用（暂存） ──▶ 归属项目 ──▶ 项目内对应目录
                                            │
                                ┌───────────┴───────────┐
                                ▼                       ▼
                      被新版本取代 → 项目内 99归档    项目终结 → 顶层 99归档
```

| 阶段 | 动作 | 时限 |
|---|---|---|
| 暂存 | 随手记录，不做格式要求 | — |
| 转正 | 补 frontmatter，移入项目对应目录 | 7 天内 |
| 维护 | 实质修改时更新 `updated` | 按需 |
| 归档 | 移入归档目录，`status` 改 `deprecated`，开头加一行取代说明 | 被取代或项目结束时 |

归档不是删除。归档里的文档照样能搜索和链接，只是不再维护。

## 十、存量项目接入本规范

新项目按 §3.2 直接建，不需要迁移。**已有项目**（目录已经长起来、几十上百个文件）按三步走，**不要一次全拆**。

### 第一步：只做目录搬迁（零拆文件）

把所有模块目录收进 `03业务模块/`，把跨模块文档抽到 `02软件架构/`。**只改目录名和层级，不动文件名。**

搬迁前先提交一次，出问题能回退。在 Obsidian 内用拖拽或右键移动，让相对链接自动重写；搬完跑一次 `检查链接.bat` 确认。

### 第二步：按需抽文档到全局层

判断标准是「它被几个模块引用」：

| 现有文档特征 | 目标位置 |
|---|---|
| 正式 PRD、验收标准 | `01功能需求/` |
| 影响两个以上模块的架构方案 | `02软件架构/` |
| 枚举、字典、字段口径 | `02软件架构/03数据字典/` |
| 只影响单个模块的方案 | 留在 `03业务模块/<模块>/` |
| 非 Markdown 交付物（html / pdf / xlsx） | `90素材/` 或模块目录内 |

这一步是增量优化，**不必一次做完**。抽错了比不抽更糟——反复搬迁会让链接和记忆都乱。

### 第三步：补 L0 层

搬迁完成后，唯一必须补的是 L0：

1. `<项目>/README.md` —— 项目卡，模块清单从目录名一次性整理
2. `<项目>/00当前进度/当前进度.md` —— 按当前实际状态写，别写成愿望清单
3. `<项目>/01功能需求/00需求索引.md` —— 需求清单表

这三个文件是整套结构的价值所在。**目录搬完但没补这三个文件，等于白搬**——只是多了一层壳。

## 十一、月度自查

每月十分钟，逐个项目过一遍：

- [ ] `01通用` 是否清空
- [ ] 每个项目的 `当前进度.md` 是否在一周内更新过
- [ ] `00数据库变更台账/` 是否与代码里的 SQL 变更一一对应
- [ ] 是否存在 `status: draft` 超过 30 天的文档
- [ ] 是否有素材目录里没有被任何笔记引用的孤儿图片
- [ ] 是否有文件名含「最终」「新版」「副本」「(1)」
- [ ] `03业务模块` 里是否有跨模块方案没上提到 `02软件架构`
- [ ] 仓库体积是否异常增长（`git count-objects -vH`）
- [ ] 是否有超过 10 MB 的文件被误提交
- [ ] 根 `README.md` 的项目清单是否与实际目录一致
