# 一、命名规约

## 1.1 通用原则

- 见名知意，**拒绝缩写**（除公认缩写：id、url、dao、dto），不要拼音、不要无意义 a/b/c/tmp1
- 禁止纯拼音、中英文混合命名，必须使用完整英文单词
- 【强制】代码和注释中都避免使用任何语言的歧视性词语
- 【推荐】如果模块、接口、类、方法使用了设计模式，命名时体现具体模式，如 `OrderFactory`、`LoginProxy`

## 1.2 命名风格

1. 【强制】命名不能以下划线、`$` 开头或结尾。禁止 `_name`、`$obj`、`name_`、`name$`
2. 【强制】类名大驼峰 `UpperCamelCase`；但 DO/BO/DTO/VO/AO/PO/UID 等缩写全部大写，例：`UserDO`、`HtmlDTO`、`XmlService`
3. 【强制】方法名、参数名、成员变量、局部变量：小驼峰 `lowerCamelCase`
4. 【强制】常量：全大写，下划线分隔，语义完整，例：`MAX_STOCK_COUNT`
5. 【强制】包名全小写，**单数形式**，点分隔符之间有且仅有一个自然语义的英文单词。例：`com.alibaba.ai.util`
6. 【强制】抽象类以 `Abstract` 或 `Base` 开头；异常类以 `Exception` 结尾；测试类以它要测试的类名开头、`Test` 结尾
7. 【强制】POJO 布尔属性**禁止加 is 前缀**：用 `deleted`，不要 `isDeleted`，避免序列化（如 RPC 反序列化）丢失字段
8. 【强制】接口实现类用 `Impl` 后缀，与接口区分：`UserServiceImpl implements UserService`
9. 【强制】枚举类名带 `Enum` 后缀，枚举成员名称全大写、下划线分隔：`ProcessStatusEnum.SUCCESS`
10. 【强制】数组定义用 `String[] args`，不要 `String args[]`
11. 【推荐】反例命名：`DaZhePromotion`（打折）、`getPingfenByName()`（评分）、`int 某变量 = 3`

```java
// 正例
public class UserDO {}
public class UserServiceImpl implements UserService {}
public class OrderAbstractFactory {}
public enum PayStatusEnum { UNPAID, PAID, REFUNDED }

// 反例
public class userDTO {}          // 类名未大驼峰
public class UserDTOImpl {}      // DTO 不该有实现类
private boolean isDeleted;       // POJO 布尔带 is
```

## 1.3 分层命名（强制）

各层方法名必须让调用方一眼看出行为，**禁止在 Service 层用 `get` 表示查询单个对象、用 `list` 表示分页**这种混用。

| 层 | 动作 | 方法名前缀 |
|---|---|---|
| Service / DAO | 获取单个对象 | `get` |
| Service / DAO | 获取多个对象 | `list` |
| Service / DAO | 获取统计值 | `count` |
| Service / DAO | 插入 | `save` / `insert` |
| Service / DAO | 删除 | `remove` / `delete` |
| Service / DAO | 修改 | `update` |
| Service / DAO | 批量 | `batch` + 上述动词，如 `batchSave` |

领域模型命名：

| 后缀 | 含义 | 出现位置 |
|---|---|---|
| `DO` | Data Object，与数据库表一一对应 | DAO 层 |
| `DTO` | Data Transfer Object，对外传输 | Service / RPC |
| `VO` | View Object，显示层对象 | Web 层 |
| `BO` | Business Object，业务内部聚合 | Service 内部 |
| `Query` | 查询对象，超过 2 个参数的查询封装 | 各层接收上层查询 |

> 【强制】超过 2 个参数的查询封装，**禁止用 Map 传输**，必须定义 `XxxQuery`。

## 1.4 禁止项

- 一个名字同时干两件事
- 名字加类型后缀冗余：`userInfoDTO` 没问题，但 `userDtoObj` 多余
- 在子父类成员变量间、不同代码块的局部变量间**重复命名**，降低可读性
- 完全不规范的缩写：`AbstractClass` 缩成 `AbsClass`、`condition` 缩成 `condi`，这类随意缩写严重降低可读性

> 布尔变量推荐 `enabled` / `hasPermission` / `success`，一眼看懂真假；对应数据库字段则用 `is_enabled` 这类带 `is_` 的写法（见 13.4）。

# 二、常量与枚举

1. 【强制】禁止魔法值，数值、字符串全部抽为常量或枚举。不允许任何魔法值直接出现在代码中
2. 【强制】`long` 常量必须使用大写 `L`，防止误判：`1000L`，不要 `1000l`
3. 【强制】不要用一个常量类维护所有常量，**按功能归类**，分开维护
4. 【推荐】常量的复用层次有五层，按范围放对位置：

| 复用范围 | 放置位置 |
|---|---|
| 跨应用共享 | 二方库的 constant 包 |
| 应用内共享 | 一方库的 constant 包 |
| 子工程内共享 | 当前子工程的 constant 包 |
| 包内共享 | 当前包的 constant 包 |
| 类内共享 | 类内 `private static final` |

5. 【推荐】如果变量值仅在一个固定范围内变化，用 `enum` 类型，不要用常量类堆

```java
// 反例
if (type == 3) {}

// 正例
public static final Integer TYPE_SLEEP = 3;
if (type == TYPE_SLEEP) {}
```

```java
// 推荐：枚举带描述，比纯常量自解释
public enum PayStatusEnum {
    /** 未支付 */
    UNPAID(0, "未支付"),
    /** 已支付 */
    PAID(1, "已支付");

    private final int code;
    private final String desc;
    PayStatusEnum(int code, String desc) { this.code = code; this.desc = desc; }
}
```

# 三、代码格式

1. 【强制】大括号的使用约定：左大括号前不换行、后换行；右大括号前换行；右大括号后有 `else` 等则不换行
2. 【强制】`(` 和 `)` 与字符之间不加空格；但 `if` / `for` / `while` / `switch` / `do` 等保留字与括号之间必须加空格
3. 【强制】任何二目、三目运算符的左右两侧必须加一个空格
4. 【强制】缩进统一 4 空格，禁止 Tab。IDEA 设置 `Use tab character` 关闭
5. 【强制】单行字符数不超过 120（手册为 120；若团队沿用 80，以团队为准）
6. 【强制】方法参数在定义和传入时，多个参数逗号后必须加空格
7. 【强制】IDE 的 text file encoding 设为 UTF-8；文件换行符使用 Unix 格式，不要 Windows 格式
8. 【推荐】没有必要增加若干空格，来使某一行的字符与上一行对应位置的字符对齐
9. 【推荐】方法和方法之间、成员变量与常量块之间、逻辑块之间空一行；**不要连续空 2 行以上**
10. 【推荐】单个方法代码行数（不含注释）≤ 80 行，超长逻辑拆分为子方法

```java
// 正例
if (status == 1) {
    doSomething();
} else {
    doOther();
}

// 反例
if (status ==1)          // 运算符左侧无空格
{
    doSomething();
}
```

> **关键**：不要手动调空格换行！开启 IDE 保存自动格式化（IDEA：Reformat code on save；VSCode：formatOnSave），从根源避免排版混乱。

# 四、OOP 规约

## 4.1 基础

1. 【强制】避免通过一个类的对象引用访问此类的静态变量或静态方法，**直接用类名访问**
2. 【强制】所有的覆写方法，必须加 `@Override`
3. 【强制】相同参数类型、相同业务含义，才可以使用可变参数，避免使用 `Object`
4. 【强制】接口过时必须加 `@Deprecated` 注解，并清晰地说明采用的新接口或新实现是什么
5. 【强制】禁止使用已废弃（`@Deprecated`）的类与方法
6. 【强制】POJO 实体属性全部使用**包装类型**（`Integer`/`Long`/`Boolean`），禁止基本类型，防止 NPE；**不要给 POJO 字段设置默认值**
7. 【强制】构造方法里面禁止加入任何业务逻辑，如果有初始化逻辑，请放在 `init` 方法中
8. 【强制】POJO 类必须写 `toString` 方法。使用 IDE 工具生成时，如果继承了另一个 POJO 类，注意在前面加一下 `super.toString()`
9. 【强制】禁止在 POJO 类中，同时存在对应属性 `xxx` 的 `isXxx()` 和 `getXxx()` 方法
10. 【强制】严格控制访问权限：成员变量一律 `private`；仅子类使用的成员设为 `protected`；工具类必须私有化构造器，禁止无参 public 构造
11. 【强制】接口方法不加 public 修饰，保持简洁；接口只定义契约，不写业务逻辑
12. 【推荐】类、类属性、类方法的访问控制从严：

| 场景 | 修饰符 |
|---|---|
| 不允许包外直接 `new`（工厂模式） | `private` |
| 仅包内可用 | `default`（不写） |
| 仅子类可用 | `protected` |
| 对外可用 | `public` |

13. 【推荐】内部类访问外部类的私有成员时，用 getter 而不是直接引用成员名

## 4.2 equals、hashCode 与数值比较（强制）

1. 【强制】只要重写 `equals`，就必须重写 `hashCode`
2. 【强制】因为 `Set` 存储的是不重复的对象、`Map` 用 key 做哈希，所以自定义对象作为 `Map` 的键、`Set` 的元素时，必须重写这两个方法
3. 【强制】`Object` 的 `equals` 方法容易抛空指针异常，应使用**常量或确定有值的对象**来调用 `equals`

```java
// 反例：unknown 可能为 null
unknown.equals("yes");

// 正例
"yes".equals(unknown);
Objects.equals(unknown, "yes");   // 两边都可能为 null 时用这个
```

4. 【强制】所有整型包装类对象之间**值的比较，全部使用 `equals` 方法**。`==` 在 `Integer` 超过缓存范围（-128~127）时不成立
5. 【强制】**`BigDecimal` 的等值比较应使用 `compareTo()`，而不是 `equals()`**。`equals` 会比较精度（scale），`1.0` 与 `1.00` 返回 false
6. 【强制】禁止使用 float、double 做**等于**比较。浮点数精度丢失，必须用 `BigDecimal` 或判断差值小于阈值
7. 【强制】金额、费率等精确计算必须用 `BigDecimal`，且构造时**用 String 入参**，不要用 double 入参

```java
// 反例：0.1 + 0.2 != 0.3
if (a == b) {}

// 正例
new BigDecimal("0.10").compareTo(new BigDecimal("0.1")) == 0;   // true
new BigDecimal(0.1);   // 反例：得到 0.1000000000000000055511151231257827
new BigDecimal("0.1"); // 正例
```

## 4.3 字符串、拷贝与序列化

1. 【强制】循环体内字符串拼接必须用 `StringBuilder`，禁止用 `+`
2. 【强制】使用 `String.split()` 得到数组后，**取最后一个分隔符后的内容时要注意下标越界**；有 `limit` 参数时要显式传入，防止结果与预期不符
3. 【推荐】慎用 `Object` 的 `clone` 方法来拷贝对象。它是**浅拷贝**，对象内部的引用类型成员仍指向同一对象
4. 【强制】序列化类新增属性时，**不要修改 `serialVersionUID`**；如果完全不兼容升级，才修改它，避免反序列化失败

```java
// 反例
String result = "";
for (Order o : list) {
    result += o.getName();       // 每次循环新建对象
}

// 正例
StringBuilder sb = new StringBuilder(list.size() * 8);
for (Order o : list) {
    sb.append(o.getName());
}
```

# 五、日期时间

1. 【强制】`SimpleDateFormat` 是线程不安全的类，**不要定义为 static 变量**；如果定义为 static，必须加锁，或改用 `DateTimeFormatter`
2. 【强制】获取当前毫秒数用 `System.currentTimeMillis()`，而不是 `new Date().getTime()`
3. 【强制】获取当前日期用 `LocalDate.now()` / `LocalDateTime.now()`，禁止用 `new Date()` 再取年月日
4. 【强制】**格式化时 `y` 表示年，`Y` 表示 week in which year**，混用会得到跨年错误；月份用大写 `M`，小写 `m` 是分钟
5. 【强制】禁止使用 `java.sql.Date`，它的年月日时分秒行为与 `java.util.Date` 不一致，且已过时
6. 【强制】禁止在程序中写死一年为 365 天，避免闰年出现逻辑错误
7. 【推荐】使用 `enum` 指代月份，而不是魔法数字（`Calendar.JANUARY` 是 0）
8. 【强制】时间存储统一用 `datetime`，不要用 `timestamp`（2038 问题）；时区统一为东八区
9. 【推荐】时间字段传输格式统一 `yyyy-MM-dd HH:mm:ss`（前后端约定，见 14.2）

```java
// 反例：Y 会按周算年份，2026-12-31 可能格式化成 2027
new SimpleDateFormat("YYYY-MM-dd");

// 正例
private static final DateTimeFormatter FMT =
        DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");
FMT.format(LocalDateTime.now());
```

# 六、集合处理

1. 【强制】判断集合空：使用 `isEmpty()`，不要 `size() == 0`
2. 【强制】集合转数组必须用 `toArray(T[] array)`，指定对应类型数组，避免类型转换异常；推荐传入空数组 `new T[0]`
3. 【强制】遍历集合时，禁止在循环内新增/删除元素；如需修改，使用 `Iterator`
4. 【强制】不要在 foreach 循环里进行元素 `remove`/`add` 操作
5. 【强制】**`Arrays.asList()` 返回的是 `Arrays` 内部类，不是 `ArrayList`**，调用 `add`/`remove` 会抛 `UnsupportedOperationException`
6. 【强制】`ArrayList` 的 `subList` 返回的是内部类 `SubList`，**不能强转为 `ArrayList`**，否则抛 `ClassCastException`
7. 【强制】使用 `Map` 的 `keySet()`、`values()`、`entrySet()` 返回的集合对象时，**不可以对其进行添加元素操作**
8. 【强制】`Collections.emptyList()` / `singletonList()` 等返回的都是**不可变对象**，不能对其做修改
9. 【强制】在集合初始化时指定集合的初始值大小（`HashMap` 建议 `(预期元素数 / 0.75) + 1`）
10. 【强制】使用 `entrySet` 遍历 `Map` 类集合 K/V，而不是先 `keySet` 再 `get`
11. 【强制】高度注意 `Map` 类集合 K/V 能不能存储 null 值的情况：

| 集合 | Key | Value | 说明 |
|---|---|---|---|
| `HashMap` | 可为 null | 可为 null | — |
| `ConcurrentHashMap` | **禁止 null** | **禁止 null** | 会抛 NPE |
| `TreeMap` | 不许 null | 不许 null | 排序时需要比较 |

12. 【推荐】集合泛型定义在左侧用 diamond 写法：`Map<String, User> map = new HashMap<>(16);`
13. 【推荐】使用 `Collections.sort()` 排序时，自定义比较器必须遵循「比较结果与相等结果一致」的自反、传递、对称原则
14. 【参考】利用 `PECS` 原则（Producer Extends Consumer Super）提高 API 灵活性：只读容器用 `<? extends T>`，只写用 `<? super T>`

```java
// 反例：UnsupportedOperationException
List<String> list = Arrays.asList("a", "b");
list.add("c");

// 正例
List<String> list = new ArrayList<>(Arrays.asList("a", "b"));
list.add("c");
```

# 七、并发处理

1. 【强制】获取单例对象需要保证线程安全，其中的方法也要保证线程安全
2. 【强制】创建线程或线程池时请指定有意义的线程名称，方便出错时回溯
3. 【强制】**线程池不允许使用 `Executors` 去创建**，而是通过 `ThreadPoolExecutor` 的方式明确各参数，避免 OOM 风险
4. 【强制】线程池各参数必须按业务评估：核心线程数、最大线程数、队列容量、拒绝策略
5. 【强制】`SimpleDateFormat` 线程不安全（见第五章）
6. 【强制】**`ThreadLocal` 必须 `remove()`**：线程池场景下线程复用，不清理会造成内存泄漏和脏数据
7. 【强制】必须回收自定义的 `ThreadLocal` 变量，尤其在业务代码 finally 块中显式 `remove`

```java
// 正例
try {
    CONTEXT.set(userId);
    // 业务
} finally {
    CONTEXT.remove();      // 不写这句，线程池里的线程会带着上一个请求的 userId
}
```

8. 【强制】`volatile` 只解决多线程内存不可见问题，**不能保证原子性**，不能替代锁
9. 【强制】双重检查锁实现单例时，`instance` 必须加 `volatile`
10. 【强制】避免 `Random` 实例被多线程使用，虽然共享该实例是线程安全的，但会因竞争同一 seed 导致性能下降；多线程用 `ThreadLocalRandom`
11. 【强制】使用 `CountDownLatch` 进行异步转同步操作时，每个线程必须调用 `countDown`，**catch 块里也要 `countDown`**，否则主线程无法唤醒
12. 【强制】多线程并行处理定时任务时，`Timer` 运行多个 `TimeTask` 时只要其中之一没有捕获抛出的异常，其它任务便会自动终止；推荐用 `ScheduledExecutorService`
13. 【强制】使用 `CountDownLatch`、`Semaphore`、`CyclicBarrier` 等同步工具时，注意锁的释放时机
14. 【强制】并发修改同一记录时，避免更新丢失，需要加锁：应用层加锁、缓存加锁、数据库层乐观锁（版本号）或悲观锁（`select ... for update`）
15. 【推荐】资金相关的金融敏感信息操作，优先使用悲观锁策略（`for update`），而不是乐观锁
16. 【强制】禁止在锁内执行网络请求、RPC、IO 等耗时操作（与 13.3 的事务要求同源）
17. 【强制】不要随便用 `static` 存业务数据，多线程环境会出现数据错乱
18. 【推荐】用 Map 做本地缓存时必须考虑容量上限与过期策略，推荐 Caffeine 或 Guava Cache，不要手写 `static HashMap` 无限增长

# 八、控制语句

1. 【强制】在 `if` / `else` / `for` / `while` / `do` 语句中必须使用大括号，即使只有一行代码
2. 【强制】优先使用**提前 return**，减少嵌套 if，代码扁平化
3. 【强制】禁止多层嵌套（if 嵌套不超过 3 层）；复杂分支拆成独立方法
4. 【强制】`switch` 语句必须写 `default` 分支；每个 case 要么 `break`/`return`，要么注释说明程序将继续执行到哪一个 case
5. 【强制】三目运算符只用于简单赋值，不要嵌套多层三目运算
6. 【强制】表达式过大时，需要使用括号表达优先级，不要依赖默认优先级
7. 【推荐】避免采用取反逻辑运算符，`if (!isValid)` 不如 `if (isInvalid)` 直观
8. 【推荐】**禁止在 `finally` 块中使用 `return`**。`finally` 中的 `return` 会覆盖 try 块中的返回值，且吞掉异常

```java
// 反例：永远返回 2，异常也被吞掉
try {
    return 1;
} finally {
    return 2;
}

// 正例
try {
    return 1;
} finally {
    release();
}
```

# 九、注释规约

## 9.1 三类注释，各司其职

### 1. 类 / 接口 / 枚举注释（Javadoc）

说明这个类是干嘛的、适用场景、核心职责。

```java
/**
 * 打卡记录 DTO
 * 用于前端展示打卡项目、连续天数、打卡人信息
 *
 * @author Li Huiying
 * @date 2026-11-11
 */
@Data
public class CheckRecordDTO {}
```

### 2. 方法注释

复杂方法写；简单 get/set 不用写。写明入参含义、返回值、异常、业务约束。

### 3. 行内注释

**只写【为什么这么写】，不要写代码在干什么。**

```java
// 正例：说明原因
// 这里不能直接删除记录，需要保留历史用于连续天数统计
recordMapper.updateDelFlag(id);

// 反例：翻译代码（代码本身已经能看懂）
// 更新 delFlag 字段
recordMapper.updateDelFlag(id);
```

## 9.2 注释规约（强制）

1. 【强制】类、类属性、类方法必须使用 Javadoc 注释，写明业务用途、入参、出参、异常
2. 【强制】所有抽象方法（含接口中的方法）必须用 Javadoc 注释说明其功能、参数、返回值、异常
3. 【强制】枚举每个枚举值必须加注释
4. 【强制】所有的类都必须添加创建者和创建日期（`@author`、`@date`）
5. 【强制】方法内部单行注释，在被注释语句**上方另起一行**；方法内部多行注释使用 `/* */`
6. 【强制】代码修改后同步更新注释，杜绝注释与代码不一致
7. 【推荐】谨慎注释掉代码。在上方详细说明原因，而不是简单地注释掉；如果无用，则删除（在 git 里留有历史）
8. 【推荐】`TODO` / `FIXME` 必须注明标记人和标记时间，格式 `TODO: [人][日期] 事项`，便于排查过期 TODO
9. 【推荐】注释只写业务意图，不要重复翻译代码；不要大量行内注释

> 原则：好代码优先做到自解释，注释是补充，不是翻译代码。

# 十、异常处理与错误码

## 10.1 异常处理

1. 【强制】不要捕获 `RuntimeException` 这类运行时异常，也不要用 `catch (Exception)` 兜底后不处理
2. 【强制】捕获异常是为了处理它，不要捕获了却什么都不处理而抛弃之。**禁止吞掉异常不打印日志**
3. 【强制】捕获具体异常，而不是 `Exception`
4. 【强制】捕获异常与抛异常必须完全匹配，或者捕获异常是抛异常的父类
5. 【强制】不要在 `finally` 中使用 `return`（见第八章第 8 条）
6. 【强制】不要用异常做流程控制、条件控制。异常只处理意外场景
7. 【强制】自定义业务异常应继承 `RuntimeException`，并区分业务异常与系统异常
8. 【强制】在 `catch` 中抛出新的异常时，必须带上**原始异常信息**（`e`），否则丢失堆栈

```java
// 反例：丢栈
catch (IOException e) {
    throw new BizException("读取失败");
}

// 正例
catch (IOException e) {
    throw new BizException("读取失败, file=" + path, e);
}
```

9. 【强制】**事务场景中，被 `try-catch` 捕获后的异常如果不再抛出，事务不会回滚**。必须手动 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`，或把异常抛出方法签名
10. 【强制】资源（流、连接、锁）必须自动释放，优先使用 try-with-resources
11. 【强制】异常日志打印要带上业务标识（id、单号），方便排查；但**禁止打印敏感信息**（密码、密钥、完整身份证）
12. 【推荐】统一在 Controller / 全局异常处理器（`@RestControllerAdvice`）中捕获异常并转换为统一返回体，不要层层 try-catch

```java
// 反例：事务不回滚
@Transactional
public void create(Order o) {
    try {
        orderMapper.insert(o);
        throw new BizException("库存不足");
    } catch (Exception e) {
        log.error("创建失败", e);      // 吞掉了，事务照常提交
    }
}
```

## 10.2 错误码规约（强制）

1. 【强制】错误码必须用枚举维护，禁止魔法数字散落各处
2. 【强制】错误码按业务模块分段，段内连续，**全局不重复**
3. 【强制】错误码含义固定，一个码不承担两种语义
4. 【强制】跨应用 RPC 调用优先返回 `Result`（含 `success` 标志 + 错误码 + 简短错误信息），而不是抛异常
5. 【推荐】错误码编码规则统一为「模块段 + 错误类型段 + 序号」，如 `401001`（认证失败-未登录）
6. 【推荐】错误提示面向使用者，不要暴露内部实现细节（表名、SQL、类名）
7. 【推荐】正常返回使用统一固定码（如 `00000`），不要让成功场景每次返回不同的码
8. 【强制】错误码制定遵循三条原则：**快速溯源**（看到码就知道哪个模块哪类问题）、**简单易记**（不搞超长编码）、**沟通标准化**（前后端、运维、客服能用同一个码对话）

> 本项目的具体实现见 [错误码和统一返回体](../错误码规范/错误码和统一返回体.md)。

## 10.3 NPE 防范（推荐）

1. 【推荐】方法返回值可以是 null 时，在 Javadoc 中明确说明；对外接口优先返回空对象/空集合
2. 【推荐】判断对象是否为 null 时，用 `Objects.nonNull()` / `Objects.isNull()`，比 `!= null` 语义更清晰
3. 【推荐】链式取值（`a.getB().getC()`）必须逐段判空，或改用 `Optional`

```java
// 反例
String city = user.getAddress().getCity();

// 正例
String city = Optional.ofNullable(user)
        .map(User::getAddress)
        .map(Address::getCity)
        .orElse(null);
```

4. 【推荐】`Optional` 只用于返回值，**不要用作方法参数、成员变量**

# 十一、日志规约

1. 【强制】禁止使用 `System.out` / `System.err` 或 `e.printStackTrace()` 打印，统一使用 SLF4J 门面
2. 【强制】**使用占位符 `{}`，禁止字符串拼接**

```java
// 反例：无论日志级别是否开启，字符串都会拼接
log.debug("user id: " + userId + ", name: " + name);

// 正例
log.debug("user id: {}, name: {}", userId, name);
```

3. 【强制】严格区分日志级别：`debug` 调试、`info` 正常业务、`warn` 告警、`error` 系统错误
4. 【强制】打印日志必须携带业务 ID（订单 ID、用户 ID、traceId），方便排查问题
5. 【强制】手机号、身份证、银行卡等敏感信息必须脱敏输出
6. 【强制】异常日志必须打印**完整堆栈**：`log.error("xxx, id={}", id, e)`，把 `e` 作为最后一个参数，不要写成 `e.getMessage()`
7. 【强制】日志文件至少保存 15 天，按天滚动，避免磁盘占满
8. 【推荐】大量日志输出时注意性能，循环体内不要打印 info 及以上级别日志
9. 【推荐】不要重复打印同一异常（上层已打，下层不必再打），避免日志风暴
10. 【推荐】使用 MDC 埋入 traceId / userId，便于全链路检索
11. 【推荐】禁止在日志中输出完整请求体（可能含密码、证件号），必要时白名单字段

# 十二、入参校验与安全

## 12.1 入参校验

1. 【强制】参数校验位置：Controller 层校验（JSR380：`@NotBlank`、`@NotNull`、`@Min`、`@Pattern` 等）
2. 【强制】校验失败返回统一错误码，不要直接抛原生异常给前端
3. 【强制】入参、出参边界校验：长度、范围、枚举值、必填
4. 【强制】**禁止信任前端传来的权限、用户 ID、价格、状态等参数**，后端必须二次校验或从会话中取
5. 【推荐】接口入参必须做边界校验，限制超大分页（如 `pageSize ≤ 100`），防止恶意参数导致 OOM

## 12.2 安全编码

1. 【强制】禁止直接拼接 SQL 字符串，必须使用参数绑定，防止 SQL 注入；MyBatis 用 `#{}` 不用 `${}`
2. 【强制】用户请求参数必须做有效性校验：长度、范围、枚举、特殊字符过滤
3. 【强制】防 XSS：用户输入内容要转义；禁止直接把用户输入渲染到页面
4. 【强制】反序列化禁止接收不可控对象，防止反序列化漏洞
5. 【强制】用户敏感数据禁止直接展示，必须脱敏（手机号 `138****1234`、身份证、银行卡）
6. 【强制】权限校验至少覆盖三层：URL 级、Service 方法级、数据级（只能操作自己的数据）
7. 【强制】文件上传必须校验类型白名单、大小上限，并重命名存储，禁止用原始文件名拼接路径（防目录穿越）
8. 【强制】密码存储必须加盐哈希（BCrypt / PBKDF2），禁止明文或简单 MD5
9. 【推荐】对外接口做 CSRF 防护与防重放（时间戳 + nonce + 签名）
10. 【推荐】用户敏感操作（改密码、改手机号、提现）记录操作日志，含操作人、IP、时间、结果

# 十三、MySQL 数据库

## 13.1 建表规约

1. 【强制】每张表必须包含三字段：`id`（bigint unsigned 自增主键）、`create_time`、`update_time`，类型为 `datetime`
2. 【强制】表名、字段名必须使用小写字母或数字，禁止出现数字开头，禁止两个下划线中间只出现数字；**禁止驼峰**，用下划线分隔
3. 【强制】表名不使用复数形式，字段名不使用保留字（如 `desc`、`order`、`key`）
4. 【强制】小数金额类型统一使用 `decimal`，禁止 `float`、`double`，避免精度丢失
5. 【强制】禁止使用外键、级联更新，所有关联逻辑在代码层处理
6. 【强制】布尔字段用 `tinyint(1)`，命名 `is_xxx`；不要用 `bit`
7. 【强制】存储引擎必须为 `InnoDB`（支持事务、行锁）
8. 【强制】表字符集必须为 `utf8mb4`，排序规则 `utf8mb4_general_ci` 或 `utf8mb4_0900_ai_ci`，禁止 `utf8`（存不了 emoji）
9. 【强制】字段尽可能定义为 `NOT NULL`，并给默认值；NULL 值参与运算、聚合、索引统计时都有坑
10. 【推荐】字段允许适当冗余，以提高查询性能，但必须考虑数据一致；冗余字段应遵循「不是频繁修改的字段、不是 varchar 超长字段」
11. 【推荐】单表行数超过 500 万行或单表容量超过 2GB，才推荐进行分库分表
12. 【推荐】`create_time` / `update_time` 设置默认值 `CURRENT_TIMESTAMP`，`update_time` 加 `ON UPDATE CURRENT_TIMESTAMP`
13. 【参考】使用 `unsigned` 存储非负整数（如 id）

## 13.2 索引规约

1. 【强制】业务上具有唯一特性的字段，**即使是组合字段，也必须建成唯一索引**
2. 【强制】**超过三个表禁止 join**。需要 join 的字段，数据类型必须保持绝对一致；多表关联查询时，保证被关联的字段需要有索引
3. 【强制】页面搜索**严禁左模糊或者全模糊**（`%xx`、`%xx%`），如需要请走搜索引擎
4. 【强制】如果有 `order by` 的场景，请注意利用索引的有序性。`order by` 最后的字段是组合索引的一部分，并且放在索引组合顺序的最后
5. 【强制】索引列上禁止使用函数、计算、类型转换，会导致索引失效
6. 【推荐】建组合索引的时候，**区分度最高的在最左边**
7. 【推荐】存在非等号和等号混合判断条件时，在建索引时，请把等号条件的列前置

```sql
-- 反例：索引里含范围查找，有序性无法利用
WHERE a > 10 ORDER BY b;      -- 索引 (a, b) 无法排序

-- 正例：等号在前，范围在后，排序字段在最后
WHERE b = ? AND a > ? ORDER BY c;   -- 索引 (b, a, c)
```

8. 【推荐】单表索引数量控制在 5 个以内（手册口径；此前个人记录为 6，统一按 5 执行），索引不是越多越好
9. 【推荐】索引命名规范：

| 类型 | 前缀 | 示例 |
|---|---|---|
| 主键 | `pk_` | `pk_user_id` |
| 唯一索引 | `uk_` | `uk_user_mobile` |
| 普通索引 | `idx_` | `idx_create_time` |

10. 【推荐】尽量使用覆盖索引（查询列全部在索引中），减少回表
11. 【推荐】利用最左前缀原则设计组合索引，避免建 `(a)`、`(a,b)` 这种冗余索引

## 13.3 SQL 语句

1. 【强制】禁止 `select *`，只查询需要的字段
2. 【强制】行数统计用 `count(*)`。`count(*)` 统计所有行，`count(列名)` **不统计该列为 NULL 的行**，两者结果可能不同；`count(1)` 与 `count(*)` 等价但可读性差
3. 【强制】禁止在 where 条件上对字段做函数运算或类型转换，避免索引失效（隐式转换）
4. 【强制】分页必须用 `limit`，禁止一次性查出全量数据；大分页用游标分页（`where id > lastId limit n`）
5. 【强制】禁止在 for 循环内执行 SQL 查询，杜绝 N+1 问题，改批量查询
6. 【强制】`in` 后的集合元素数量控制在 1000 个以内，超过则分批查询或改用 `join`；能避免 `in` 就避免
7. 【强制】事务尽量短小，禁止大事务；**不要在事务里执行网络请求、RPC、消息发送**
8. 【强制】数据订正（特别是删除、修改记录）时，**要先 select**，避免出现误删除，确认无误才能执行更新语句
9. 【强制】禁止在线上环境做数据库压力测试
10. 【强制】禁止使用存储过程，存储过程难以调试和扩展，更没有移植性
11. 【推荐】`TRUNCATE TABLE` 比 `DELETE` 快，且不可回滚，使用前必须确认
12. 【推荐】避免使用子查询 `in`，改为 `join` 或分批查询；子查询在旧版 MySQL 里可能无法命中索引
13. 【推荐】判断 NULL 用 `IS NULL` / `IS NOT NULL`，不要用 `= NULL`
14. 【推荐】批量插入用 `insert into t (...) values (...),(...)`，比循环单条插入快一个数量级

## 13.4 ORM 映射（MyBatis）

1. 【强制】在表查询中，一律不要使用 `*` 作为查询的字段列表，需要哪些字段必须明确写明
2. 【强制】POJO 类的布尔属性**不能加 `is`**，而数据库字段必须加 `is_`，要求在 resultMap 中进行字段与属性之间的映射
3. 【强制】不要用 `resultClass` 当返回参数，即使所有类属性名与数据库字段一一对应，也需要定义 resultMap，使字段与 DO 类解耦
4. 【强制】**sql.xml 配置参数使用 `#{}`，禁止使用 `${}`**，`${}` 会引起 SQL 注入
5. 【强制】不要写一个大而全的数据更新接口。传入为 POJO 类时，**不要更新全部字段**，自己 `update` 时也要写清楚改了哪些字段
6. 【强制】`<isEqual>` 等标签比较两个值是否相等时，注意数据类型一致，避免因类型不同导致判断失效
7. 【推荐】不要在 `@Transactional` 方法内自己 `try-catch` 吞异常（见 10.1 第 9 条）
8. 【推荐】大批量操作分批提交，单批 500~1000 条，避免长事务与锁表

```xml
<!-- 反例：SQL 注入 -->
<select id="get" resultType="UserDO">
    select id, name from user where name = '${name}'
</select>

<!-- 正例 -->
<select id="get" resultMap="BaseResultMap">
    select id, name from user where name = #{name}
</select>
```

# 十四、返回体与接口约定

## 14.1 统一返回体（强制）

1. 【强制】统一返回包装体 `Result<T>`，所有对外接口一致
2. 【强制】错误码全局枚举，含义固定，不重复
3. 【强制】集合返回约定：优先返回空集合而不是 null，减少前端判空
4. 【强制】返回体不包含敏感字段（密码、密钥、内部标识）
5. 【推荐】返回体带 `traceId`，便于前端报错时定位后端日志

> 具体字段与编码规则见 [错误码和统一返回体](../错误码规范/错误码和统一返回体.md)。

## 14.2 前后端规约（强制）

1. 【强制】前后端交互的 API 必须明确：协议、域名、路径、请求方法、请求内容、状态码、响应体
2. 【强制】HTTP 状态码与业务码职责分离：传输层失败用 4xx / 5xx，业务失败用返回体的 `code`。**同一项目内必须保持一种风格**，不要有的接口返回 200、有的返回 500
3. 【强制】时间格式统一 `yyyy-MM-dd HH:mm:ss`，时区东八区；**禁止前后端各自解析时间戳**导致时区错乱
4. 【强制】请求参数必须显式声明必填/选填、类型、长度、枚举取值
5. 【强制】分页参数统一命名（`pageNum`/`pageSize` 或 `offset`/`limit`），全项目只保留一种
6. 【强制】后端返回给前端的数据**不得包含敏感信息**，按需裁剪字段，不要直接把 DO 扔出去
7. 【强制】明确 Cookie / Session / Token 的使用方式与过期策略，三者不混用
8. 【推荐】接口保证幂等性（见 17.2），前端重复提交不应产生重复数据
9. 【推荐】大文件、图片走 CDN 或对象存储，不要经过应用服务器中转
10. 【推荐】接口变更必须向下兼容；不兼容变更走版本号（`/v2/`），不要直接改老接口语义

# 十五、工程结构

## 15.1 应用分层（强制）

推荐分层（自上而下）：

```
开放接口层（OpenAPI）  →  可直接封装 Service 方法暴露成 RPC 接口；通过 Web 封装成 HTTP 接口
终端显示层（Web）       →  各端的模板渲染、参数接收、视图组装
Web 层                 →  主要是对访问控制进行转发，各类基本参数校验，或者不复用的业务简单处理
Service 层             →  相对具体的业务逻辑服务层，事务边界在这一层
Manager 层             →  通用业务处理层：对第三方平台封装、对 DAO 层通用能力下沉、多 DAO 组合复用
DAO 层                 →  数据访问层，与底层 MySQL、Oracle、Hbase 等进行数据交互
外部接口 / 第三方      →  包括 RPC 或其他公司的 HTTP 接口
```

各层职责与禁令：

| 层 | 做什么 | 禁止 |
|---|---|---|
| Controller / Web | 接收参数、参数校验、组装返回、捕获异常 | 写 SQL、写业务规则 |
| Service | 业务逻辑、事务、规则判断 | 直接拼装前端 VO、做 HTTP 相关处理 |
| Manager | 通用能力下沉、第三方封装、多 DAO 组合 | 写强业务规则 |
| Mapper / DAO | 只做数据库读写，一个方法只做一件事 | 写复杂业务判断 |

1. 【强制】分层领域模型严格区分：`DO`/`DTO`/`VO`/`BO`/`Query`，不要混用（定义见 1.3）
2. 【强制】禁止跨层调用：Controller 不能直接调 Mapper，DAO 不能反向调 Service
3. 【强制】全局异常处理统一放在 Web 层（`@RestControllerAdvice`），Service 层只抛业务异常
4. 【推荐】领域模型转换用 MapStruct 或显式转换方法，不要用反射 BeanUtils 全量拷贝（性能差且易误覆盖）

## 15.2 二方库依赖（强制）

1. 【强制】定义 GAV 遵从以下规则：
   - **GroupID**：`com.{公司/BU}.业务线.[子业务线]`，最多 4 级。例：`com.taobao.jstorm`
   - **ArtifactID**：`产品线名-模块名`，语义不重复不遗漏，先到中央仓库查证。例：`dubbo-client`
   - **Version**：见下条
2. 【强制】版本号命名方式 `主版本号.次版本号.修订号`：

| 位 | 何时递增 |
|---|---|
| 主版本号 | 产品方向改变，或大规模 API 不兼容、架构不兼容升级 |
| 次版本号 | 保持相对兼容，增加主要功能特性，或影响范围极小的 API 不兼容修改 |
| 修订号 | 保持完全兼容，修复 BUG、新增次要功能特性 |

> 起始版本号必须为 `1.0.0`，不是 `0.0.1`。正式发布的类库必须先去中央仓库查证，版本号要有延续性，正式版本号不允许覆盖升级。

3. 【强制】**线上应用不要依赖 SNAPSHOT 版本**（安全包除外），保证发布幂等性，也加快编译构建
4. 【强制】二方库的新增或升级，保持除功能点之外的**其它 jar 包仲裁结果不变**。若有改变必须评估验证，用 `dependency:tree` 找出差异点排除
5. 【强制】**接口返回值不允许使用枚举类型**，或者包含枚举类型的 POJO 对象（枚举序列化在版本不一致时兼容性差）；方法入参可以使用枚举
6. 【强制】依赖于一个二方库群时，必须定义一个统一版本变量，避免版本号不一致
7. 【强制】禁止在子项目的 pom 依赖中出现相同的 GroupId、相同的 ArtifactId，但是不同的 Version
8. 【推荐】所有 pom 文件中的依赖声明放在 `<dependencies>` 语句块中，所有版本仲裁放在 `<dependencyManagement>` 中
9. 【推荐】二方库尽量不要有配置项，最低限度不要再增加配置项
10. 【参考】二方库设计遵循「精简可控」和「稳定可追溯」：移除一切不必要依赖；每个版本变化要记录、可查

## 15.3 服务器与 JVM（推荐）

1. 【推荐】高并发服务器建议调小 TCP 协议的 `time_wait` 超时时间，加快回收
2. 【推荐】调大服务器所支持的最大文件句柄数（`ulimit -n`），避免 `Too many open files`
3. 【推荐】JVM 参数 `-Xms` 与 `-Xmx` 设置成一样大小，避免堆动态调整带来的抖动
4. 【推荐】JVM 参数加 `-XX:+HeapDumpOnOutOfMemoryError`，OOM 时保留现场
5. 【推荐】服务器时区显式指定 `-Duser.timezone=Asia/Shanghai`，避免容器内默认 UTC 导致时间错乱
6. 【推荐】容器化部署时显式限制内存，并让 JVM 感知容器内存（`-XX:MaxRAMPercentage`）

# 十六、单元测试

1. 【强制】单元测试必须覆盖正常场景、边界值、异常场景
2. 【强制】测试用例不能依赖数据库、外部接口；做好数据隔离，执行后自动回滚
3. 【强制】单元测试必须写在 `src/test/java` 下，不允许写在业务代码目录
4. 【强制】保持单元测试的**独立性**，为了保证单元测试稳定可靠且便于维护，单元测试用例之间决不能互相调用，也不能依赖执行的先后次序
5. 【强制】单元测试**不能依赖外部环境**，如数据库、Redis、MQ、外部 RPC；必要时用 Mock
6. 【推荐】单元测试方法命名规范：`test_方法名_场景`，或 `should_Xxx_when_Yyy`
7. 【推荐】**AIR 原则**：

| 字母 | 含义 |
|---|---|
| A（Automatic） | 单元测试应该是全自动执行的，并且非交互式的 |
| I（Independent） | 保持独立性，用例之间不互相调用、不依赖执行顺序 |
| R（Repeatable） | 可重复执行，不受外部环境影响 |

8. 【推荐】**BCDE 原则**，保证被测试代码的质量：

| 字母 | 含义 |
|---|---|
| B（Border） | 边界值测试，包括循环边界、特殊取值、数据边界、时间边界 |
| C（Correct） | 正确的输入，并得到预期的结果 |
| D（Design） | 与设计文档相结合，来编写单元测试 |
| E（Error） | 强制错误信息输入（如非法数据、异常流程），并得到预期结果 |

9. 【推荐】核心业务、核心模块、核心代码，增量代码的测试覆盖率应达到 80% 以上
10. 【推荐】每个测试方法必须有断言，且建议只测一个场景，避免一个方法里几十个 assert
11. 【推荐】不要在测试里写 `System.out` 看结果，用断言
12. 【推荐】Mock 外部依赖（`Mockito`），只测自己的逻辑；集成测试另建目录（`*IT.java`），不混在单测里

# 十七、设计规约

## 17.1 设计原则

1. 【强制】存储方案和底层数据结构的设计获得评审一致通过，并沉淀成文档，不要口头约定
2. 【推荐】需求分析阶段使用图表达：用例图（角色与功能）、状态图（状态流转）、时序图（交互顺序）、类图（领域模型）、活动图（业务流程）
3. 【推荐】类设计遵循 SOLID：单一职责、开闭、里氏替换、接口隔离、依赖倒置
4. 【推荐】慎用继承，优先组合；继承层次不超过 3 层
5. 【推荐】依赖抽象而不是具体实现，接口与实际实现分离，便于替换与测试
6. 【推荐】系统设计时考虑：扩展性（未来加模块要不要改老代码）、容错（下游挂了怎么办）、降级（核心链路兜底）、限流

## 17.2 接口设计（强制）

1. 【强制】接口入参必须做边界校验，防止超大分页、恶意参数导致 OOM
2. 【强制】接口幂等性设计，防止重复请求造成数据重复：

| 场景 | 幂等手段 |
|---|---|
| 查询 / 删除 | 天然幂等 |
| 新增 | 唯一索引、token 去重、业务流水号 |
| 更新 | 版本号、状态机校验（只允许单向流转） |

3. 【强制】分布式场景禁止依赖本地事务，使用可靠消息、TCC、Saga 等分布式事务方案
4. 【推荐】接口粒度适中：不要一个大接口返回全部数据，也不要为每个字段开一个接口
5. 【推荐】对外接口设计时预留扩展位，但不要为「将来可能」写一堆空实现

# 十八、代码结构与坏味道

## 18.1 方法要短，单一职责

一个方法**只做一件事**，长度尽量控制在 50 行以内。

- 如果里面出现两段完全独立逻辑 → 抽成私有方法
- 超长 if 嵌套、if-else 瀑布 → 重构：策略模式、枚举、提前 return

```java
if (record == null) {
    return null;
}
if (!record.getEnable()) {
    return Collections.emptyList();
}
// 业务逻辑...
```

## 18.2 变量作用域最小化

不要在类顶部一次性定义一堆变量；变量在哪里用，就在哪里声明。

```java
public void calcContinuous() {
    LocalDate lastDate = record.getCheckDate();
    // ...
}
```

## 18.3 五类坏味道

1. 【强制】不要重复复制粘贴相同逻辑 → 抽公共工具方法/组件
2. 【强制】参数不要太多：方法参数超过 4 个，优先封装成 DTO / Query
3. 【强制】避免深嵌套：if 套 if 套 if，超过 3 层就要警惕重构
4. 【强制】不要一个大类几千行，大类拆分，按领域拆分
5. 【强制】集合返回：接口返回集合不要返回 null，优先 `Collections.emptyList()`

# 十九、工具与落地流程

## 19.1 校验工具（自动化检查，比肉眼靠谱）

| 工具 | 作用 |
|---|---|
| **Alibaba Java Coding Guidelines（P3C）插件** | 实时扫描手册强制规约，IDEA 内直接标红 |
| **SonarLint** | 修复空指针、资源未关闭、重复代码等坏味道 |
| **阿里格式化 xml** | 一键统一空格、换行、缩进 |
| **Checkstyle** | CI 阶段做硬性卡口，不通过不合并 |
| **SpotBugs** | 字节码层面找空指针、并发隐患 |

> 流程：写代码 → 保存自动格式化 → SonarLint 实时标红 → 修复 → 提交前跑 Checkstyle。

## 19.2 极简落地流程（个人开发直接照这个来）

1. 导入规范插件（Alibaba + SonarLint）
2. 配置 IDE 保存自动格式化 + UTF-8 + LF 换行
3. 新建类、方法，先想名字，保证见名知意
4. 写的时候控制方法长度，复杂逻辑抽小方法、提前 return
5. 魔法值抽常量/枚举
6. 集合、字符串、数值比较按第六章和 4.2 的坑对照一遍
7. 注释只写业务意图，不翻译代码
8. 写完扫一遍 SonarLint，处理警告
9. 改表了？同一次提交里登记项目变更台账（见项目规范）
