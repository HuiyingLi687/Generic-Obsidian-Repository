# SDD 软件设计文档模板

> 定位：**SRS 需求文档回答【做什么】；SDD 设计文档回答【怎么做】**
> 适用：后端项目、Obsidian 知识库、飞书知识库直接使用，与接口文档、ADR 搭配。
> 使用方式：复制全文，把 `【占位内容】` 替换成你的实际内容即可。
> 
> 

---

## 1\. 概述

### 1\.1 文档目的

说明本文档用来描述本模块/系统的技术方案，供开发、测试、评审使用，作为编码依据。

### 1\.2 范围

包含哪些功能，不包含哪些功能（**边界很重要**）。

### 1\.3 术语与缩略词

|缩写|全称|说明|
|---|---|---|
|SRS|Software Requirement Specification|需求规格说明书|
|SDD|Software Design Document|软件设计文档|
|DO|Data Object|数据库实体|
|DTO|Data Transfer Object|传输对象|

## 2\. 总体设计

### 2\.1 业务目标

一句话：这个模块要解决什么业务问题。

### 2\.2 系统上下文（上下文图）

外部依赖系统、调用方、被调用方。例如：前端页面 → 本服务 → 数据库 / 第三方接口。

### 2\.3 架构方案

- 整体分层：Controller / Service / Domain / Repository

- 技术栈：SpringBoot / MySQL / Redis 等

- 核心设计思路（复用、解耦、异步、缓存等）

### 2\.4 模块划分

列出子模块，每个模块职责。例：

1. 登录模块：身份校验、令牌下发

2. 答题模块：题目加载、答题提交、结果统计

## 3\. 详细设计

### 3\.1 领域模型（核心业务对象）

- 领域实体、领域行为（业务规则放在这里）

- 实体之间关系：一对一 / 一对多

### 3\.2 数据库设计

表清单（单表：表名、字段、类型、注释、主键、索引、唯一约束），并区分 DO 实体与 DTO 入出参隔离。

### 3\.3 接口设计

> 可直接引用接口设计文档，不必重复展开
> 
> 

- 接口清单（路径、方法、功能）

- 入参、出参、错误码

- 服务端内部执行顺序（重点）

- 异常处理逻辑

### 3\.4 核心流程设计

关键业务时序，用文字/简单时序图描述。例：用户提交答题 → 参数校验 → 查题目 → 校验答题权限 → 保存答卷 → 异步统计成绩 → 返回结果。

### 3\.5 缓存设计（如有）

缓存 key、过期时间、更新策略、击穿/雪崩防护。

### 3\.6 异步设计（如有）

线程池、消息队列、异步任务内容、失败重试策略。

### 3\.7 权限设计

哪些接口需要登录、角色校验、数据权限。

## 4\. 异常与错误码设计

- 全局统一返回结构

- 公共错误码 \+ 模块私有错误码（号段隔离）

- 业务异常、系统异常区分

## 5\. 安全设计

- 参数防注入、XSS

- 敏感数据脱敏

- 令牌有效期、签名校验

## 6\. 性能\&容量设计

预估并发、数据量、慢查询注意点、分页方案。

## 7\. 依赖与第三方

依赖的外部接口、中间件、版本，调用超时、降级方案。

## 8\. 测试要点

重点测试场景、边界 case、异常 case。

## 9\. 风险与备选方案

当前方案存在什么风险，备选方案是什么（简单 ADR）。

## 与已有文档的搭配规则（笔记重点）

1. **SRS：需求文档** → 产品视角，功能、用户场景

2. **SDD：软件设计文档** → 开发视角，技术实现方案（本模板）

3. **接口文档** → 可作为 SDD 里【3\.3 接口设计】的附件/子文档

4. **ADR：架构决策记录** → SDD 里重大选择（为什么选这个方案而不是别的）单独写成 ADR

## 新手容易踩坑

- SDD 不要写得像需求文档，不要堆业务描述，重点是**怎么实现**

- 不要把代码粘贴进 SDD，写模型、流程、规则

- 简单小模块可以精简 SDD；复杂模块拆分，一个模块一份 SDD
